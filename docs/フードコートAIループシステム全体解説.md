# フードコート AIループシステム 全体解説

MARUGO S（東京ドーム内フードホール「FOOD STADIUM TOKYO」）の分析基盤に組み込まれた、
**2つの「自己改善ループ」** の全体像を解説する。

初版: 2026-07-07（両ループの本番デプロイと同日）
関連: [フードコート学習システム構造.md](フードコート学習システム構造.md)（データフロー）、[フードコート来客予測モデル.md](フードコート来客予測モデル.md)（予測モデル詳細）、[AI_LOOP_ENGINEERING_DESIGN.md](AI_LOOP_ENGINEERING_DESIGN.md)（品質評価ループの設計書・実装ログ）、[フードコートAI分析システム_設計解説.md](フードコートAI分析システム_設計解説.md)（5エージェントAI）

## 1. 「ループ」とは何か（この文書での定義）

単にデータを毎日読み直すことではなく、**「過去の誤差・品質の実績が、次の動作そのものを自動的に変える」** 閉じた仕組みを指す。

このシステムには性質の異なる2つのループがある。

| | ループ① 来客予測のモデル選択ループ | ループ② AI回答の品質評価ループ |
|---|---|---|
| 対象 | 数値予測（客数・売上） | 文章生成（Q&A・日次/期間サマリー） |
| 何を測る | バックテスト誤差（MAPE） | 評価AIによる採点（5軸100点） |
| 何が変わる | 翌晩どの予測モデル・パラメータを使うか | その場で回答を改善して再生成するか |
| 頻度 | 毎晩1回（cron JST 05:00） | リクエストごと（最大Nループ） |
| 状態 | **本番で稼働中** | **Q&Aのみ本番稼働中**（日次・期間・週次は明示OFF） |

どちらも「AIに数字を作らせない・自己申告を信用しない」という既存の設計原則の延長にある。
ループ①は自分の予測の外れ具合を、ループ②は自分の文章の品質を、**外部の物差しで測ってから次の行動を決める**。

## 2. ループ① 来客予測のモデル選択ループ

### 2-1. 仕組み（毎晩 JST 05:00・foodcourt-forecast-cron）

2つの予測モデルを**毎晩バックテストで競わせ、その晩に精度が良かった方を本番予測に採用**する。

```
蓄積実績（foodcourt_daily_facts・毎日1日分増える）
   │
   ├─ A) レガシー乗算モデル (mult-factor-v1)
   │     客数 = ベース × 曜日係数 × イベント種別係数 × 天気係数
   │     （平均比＋shrink。解釈しやすい「倍率」の形）
   │
   └─ B) ポアソン回帰GLM (glm-poisson-v1)
         log(客数) = 切片 + 曜日 + イベント種別 + 天気
                    + log(1+予想動員数) + トレンド（経過日数）
         （IRLS＋リッジ正則化。動員数という「規模」と開店後の伸びを扱える）
              │
              ├─ λ自動選択: リッジ強度の候補 {1,2,4,8,16} を
              │   それぞれバックテストし、最も当たるλを採用
              ▼
   拡張窓バックテスト（その日より前のデータだけで学習→当日を予測）
   を A / B(最良λ) の両方で全日程実行 → guests の MAPE を比較
              │
              ▼
   MAPEが小さい方を「今晩の採用モデル」に決定
   → forecast_predictions（当日〜+14日）を採用モデルで生成
   → どちらが勝ったかを foodcourt_forecast_factors.model_selection と
     foodcourt_forecast_history.model_version に記録
```

### 2-2. なぜ2モデル並走なのか

- **レガシー乗算モデル**は係数が「土曜=×1.2」のような倍率で出るため、AI解説がそのまま根拠に使える。データが少ない時期は単純さゆえに安定して強い。
- **GLM**は「予想動員数（連続値）」と「トレンド（開店後の客数の伸び）」を扱える。データと動員数入力が貯まるほど有利になる。
- どちらが良いかは事前に決めず、**誤差の実績だけで毎晩決め直す**。これが「ループを閉じる」ということ（人間がモデルを切り替える判断をしなくてよい）。

なお、AI解説（統計的パターン）に渡す係数は**勝敗に関係なく常にレガシーの倍率**を使う。解説の語り口が夜ごとに変わらないようにするため。

### 2-3. 予想動員数の手入力（ループ①の燃料）

イベントの「規模」は公開されていないため、[foodcourt.html](../foodcourt.html) の「📃 東京ドーム イベント一覧」の各行にある **「👥予想」入力欄** から手入力する。

- 保存先: `tokyo_dome_events.expected_attendance`（admin-api `PUT /foodcourt/events/attendance` 経由）
- 店舗スタッフがLINEリンクから開いた画面（店舗スコープ）でも入力可能
- 入力が無いイベントは動員数の効果ゼロとして扱われる（GLMは種別ダミーだけで推定）
- **入力が貯まるほどGLMがレガシーに勝ちやすくなる**＝予測が賢くなる直接の手段

### 2-4. 監視方法

| 見る場所 | 分かること |
|---|---|
| [foodcourt-evolution.html](../foodcourt-evolution.html)（AI学習 進化トラッキング） | MAPEの推移＝賢くなっているか。model_versionの切り替わり＝GLMが勝ち始めたか |
| `foodcourt_forecast_factors.model_selection` | 直近の勝敗・採用λ・両モデルのMAPE |
| `GET /functions/v1/foodcourt-forecast-cron?dry_run=1` | 保存せずにその場で学習・比較結果を確認（非破壊） |

### 2-5. 本番初回の結果（2026-07-07 時点）

- 学習40日・バックテスト36日
- レガシー MAPE 52.6% vs GLM 59.7%（λ=16）→ **レガシーを自動採用**
- 動員数が未入力のためGLMの強みが出ていない＝想定どおりの初期状態。動員数入力とデータ蓄積で逆転が期待される

## 3. ループ② AI回答の品質評価ループ（AIループエンジニアリング）

### 3-1. 仕組み

既存の5エージェントAI（専門AI×3 → 反証AI → 統合AI）が作った**統合回答を、第6の「評価AI」が採点**し、
不合格なら**改善点だけ**を統合AIに渡して再生成させる。

```
既存の5エージェント・パイプライン
（専門AI①②③ 並列 → 反証AI④ → 統合AI⑤）
        │  ※専門AI・反証AIの実行は初回の1回だけ
        ▼
   統合回答（1回目）
        ▼
   [評価AI⑥] 5軸で採点（JSONのみ返す・回答は書き直さない）
     正確性 / 論理性 / 専門性 / 実用性 / 根拠
        ▼
   合格？（総合90点以上 かつ 全項目80点以上）
     ├─ YES → その回答を返却（ループ終了）
     └─ NO  → 改善点だけを抽出（前回回答の全文は渡さない）
              → 統合AI⑤だけ再生成 → 再評価
              → 最大Nループ。全部不合格なら最高得点の回答を返す
```

- 合否は評価AIの自己申告を信用せず、**コード側が閾値から算出し直す**
- 全ループの生成物・スコア・改善点・トークン使用量をDBに保存（将来のRAG・蒸溜・回答ランキングの素材）

### 3-2. 適用範囲とループ上限（コスト設計）

| 対象 | surface | ループ上限（既定） | 理由 |
|---|---|---|---|
| Q&A（データに質問） | `ask` | 2 | 自由質問で品質評価の効果が最大。初回＋最大1回の改善 |
| 日次サマリー | `daily_summary` | 2 | 1レポート初回閲覧時のみ生成（以降キャッシュ） |
| 期間サマリー | `period_summary` | 2 | 有効化する場合も初回＋最大1回の改善 |
| 週次レポート | `weekly_report` | 2 | 有効化する場合も初回＋最大1回の改善 |

再ループは**統合AIだけ**を再生成する（専門AI3体＋反証AIは使い回し）ため、
1ループ追加あたりの増分は「統合AI1回＋評価AI1回」に抑えられる。合格したら即終了。

### 3-3. 本番の段階導入設定（2026-07-22）

品質ループは環境変数未設定時にOFFとなる fail-closed 設計とし、2026-07-22時点の本番ではQ&A・日次・期間・週次の全surfaceを明示的に有効化している。
Supabase Edge Functions Secrets の設定は次のとおり:

```
FOODCOURT_LOOP_ENABLED=true
FOODCOURT_LOOP_APPLY_TO_ASK=true
FOODCOURT_LOOP_APPLY_TO_DAILY=true
FOODCOURT_LOOP_APPLY_TO_PERIOD=true
FOODCOURT_LOOP_APPLY_TO_WEEKLY=true
```

現在の安全運用値:

```
FOODCOURT_LOOP_PASS_TOTAL=70
FOODCOURT_LOOP_PASS_EACH=65
FOODCOURT_LOOP_MAX_ASK=2
FOODCOURT_LOOP_MAX_DAILY=2
FOODCOURT_LOOP_EVALUATOR_PROVIDER=claude
FOODCOURT_AI_REQUEST_BUDGET_MS=110000
```

管理画面の合格ライン設定 `foodcourt_evolution_passing_score` が存在する場合は、その整数値が
総合点・各評価軸の両方へ優先適用される。2026-07-22時点の本番値は70点。

反証AI④は全 surface で Claude Haiku（→ Gemini → Groq）を使う。専門AI①は Groq 上の `openai/gpt-oss-120b` を全 surface 共通で使う。

**キャッシュ挙動**: 現行の通常版・loop版はどちらも `foodcourt-analysis-ai-v16-loop-learning`
であり、日次ループをOFFにしてもキャッシュバージョンは変わらない。

### 3-4. 記録テーブル

| テーブル | 役割 |
|---|---|
| `foodcourt_ai_loop_runs` | 1回の質問/生成の最終結果（採用ループ・最終スコア・返却理由） |
| `foodcourt_ai_loop_iterations` | 各ループの生成物・5軸スコア・改善点・使用量（run_idで紐づく） |

`returned_reason` の値: `passed`（合格）/ `max_loop_best`（上限到達→最高点採用）/
`evaluation_failed`（評価AI失敗→その回の生成物を採用）/ `generation_failed`（生成自体が失敗）。

AI使用料は従来どおり `ai_usage_events` に全AI呼び出し（評価AI・再生成分を含む）が記録され、
AI使用料ページに合算される。

## 4. 2つのループの関係と今後

```
              ┌──────────  数値の世界  ──────────┐
   実績蓄積 → モデルA/Bを毎晩競わせる → 良い方が明日の予測を作る   …ループ①
              │
              │ 予測係数・自己採点(MAPE)をAI解説の根拠として供給
              ▼
              ┌──────────  文章の世界  ──────────┐
   5エージェントが回答 → 評価AIが採点 → 不合格なら改善して再生成   …ループ②
```

- ループ①の学習係数と自己採点は、ループ②が評価する「回答の根拠」そのものとして流れ込む
  （予測とAI解説が同じ学習結果を参照する既存の1本化設計）。
- 将来拡張（設計書14章）: 合格回答の再利用（RAG）、初回回答→改善→最終回答ペアの蒸溜、
  ユーザーフィードバック（役に立った/違う）による回答ランキング。
- ループ①の次段階: 交互作用項（曜日×イベント）、客単価のイベント別化、GBDT化。

- [ ] 大きなイベントは「👥予想」に動員数を入力する（GLMの精度に直結）
- [ ] 週1回程度 [foodcourt-evolution.html](../foodcourt-evolution.html) でMAPEの低下とmodel_versionを確認
- [ ] ループ②を有効化したら、`foodcourt_ai_loop_runs` の `returned_reason` 分布と
      AI使用料ページのコスト推移を最初の1週間は確認する（評価が厳しすぎて毎回最大ループまで回っていないか）
- [ ] 週次レポートは手動force生成せず、次回の自然cron後に `weekly_report` の初回本番確認を行う。
      確認日は次回月曜9時台（JST）を目安にし、以下を確認する:
      - `foodcourt_weekly_reports` に対象週の新規レポートが作成されていること
      - `foodcourt_ai_loop_runs.surface='weekly_report'` に新規runがあり、`status='completed'`、`final_score`、`final_loop_index`、`returned_reason` が記録されていること
      - `ai_usage_events` に `claude-haiku-4-5`（反証AI・評価AI）と `openai/gpt-oss-120b`（専門AI①）が記録されていること
      - `final_loop_index` が毎回2に張り付かず、コストが想定内であること
