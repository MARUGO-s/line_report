## 1. 「ループ」とは何か（この文書での定義）

単にデータを毎日読み直すことではなく、**「過去の誤差・品質の実績が、次の動作そのものを自動的に変える」** 閉じた仕組みを指す。

このシステムには性質の異なる2つのループがある。

| | ループ① 来客予測のモデル選択ループ | ループ② AI回答の品質評価ループ |
|---|---|---|
| 対象 | 数値予測（客数・売上） | 文章生成（Q&A・日次/期間サマリー） |
| 何を測る | 朝の事前予測と確定実績（WAPE/MAE/偏り） | 評価AIによる採点（5軸100点） |
| 何が変わる | 条件を満たした候補へ採用方式を切り替えるか | その場で回答を改善して再生成するか |
| 頻度 | 予測発行は毎朝05:00、方式の採用判定は月曜のみ | リクエストごと（最大Nループ） |
| 状態 | **本番で稼働中** | **Q&Aのみ本番稼働中**（日次・期間・週次は明示OFF） |

どちらも「AIに数字を作らせない・自己申告を信用しない」という既存の設計原則の延長にある。
ループ①は自分の予測の外れ具合を、ループ②は自分の文章の品質を、**外部の物差しで測ってから次の行動を決める**。

## 2. ループ① 来客予測のモデル選択ループ

### 2-1. 仕組み（毎朝05:00 JST）

```text
完了実績（発行日より前）＋発行時点のイベント・天気
    ↓ 毎朝05:00 JST、5方式で当日〜14日先を計算
改変不可の発行台帳・75予測（5方式×15日）
    ↓ 後日の確定実績と照合
本番評価：同じ対象日・方式・先行日数でWAPE/MAE/偏りを計算
    ↓ 月曜のみ、共通日数・改善幅・前後半・冷却期間の条件を検査
条件を満たした候補だけ採用／不足なら現行方式を維持
```

5方式は安全補正乗算（`mult-factor-v4-safe`）、直近4回同曜日（`weekday-4-v1`）、類似日（`similar-days-v1`）、客数・売上別の正則化回帰（`ridge-direct-v1`）、3候補の等重み平均（`ensemble-v1`）。詳細正本は [FOODCOURT-FORECAST-AUDIT.md](./FOODCOURT-FORECAST-AUDIT.md)。

### 2-2. 毎日再学習と採用切替は別

実績を追加して各方式の予測を更新する処理は毎朝行う。一方、採用方式は日々の参考バックテストの勝敗では変更しない。

主評価は朝の1日前予測・直近28暦日。月曜日に、現行・候補・同曜日基準の共通21日以上で客数と売上のMAEがともに現行より5%を超えて改善し、前後半（各7日以上）でも両方改善することを確認する。同曜日基準以外の候補は同曜日基準にも両方勝つ必要がある。採用後28日は再切替を待つ。条件未達なら現行方式を維持する。

過去再計算は当時の天気予報・イベント更新履歴を復元していないので、本番評価・採用判定には使わない。改変不可の発行台帳で実際の事前予測を評価する。

### 2-3. 動員・天候・日報

動員の入力と保存は背景分析のため継続できるが、事後の実測動員を現行5方式へ使わない。未知の天候を晴れで埋めず、発行時点の入力・出所・時刻を保存する。日報から休業・台風の因果を自動確定する仕様でもない。

### 2-4. 監視方法

| 見る場所 | 確認すること |
| --- | --- |
| [本番の進化画面](https://marugo-s.github.io/line_report/foodcourt-evolution.html) | 本番/参考、発行時刻、方式、期間、先行日数、母数、WAPE/MAE/偏り |
| `foodcourt_forecast_issuances` / `foodcourt_forecast_snapshots` | 1日1発行・75予測、入力、採用理由、朝の評価対象か |
| `foodcourt_forecast_factors.model_selection` | 最新の採用方式・変更有無・理由・前回昇格日 |
| `foodcourt-forecast-cron?dry_run=1` | 通常と同じ認証で、保存せず計算・品質を確認 |

### 2-5. 本番移行時の確認

2026-09-10にDB・API・Pagesを本番反映し、完了実績105日から初回75予測を保存した。同日再実行で発行ID・件数不変、未認証401を確認。夜間の初回発行は本番評価から除外し、翌朝から朝の事前予測を蓄積する。実運用の精度向上は今後の確定実績で検証する。

## 3. ループ② AI回答の品質評価ループ（AIループエンジニアリング）

### 3-1. 仕組み

既存の5エージェントAI（専門AI×3 → 反証AI → 統合AI）が作った**統合回答を、第6の「評価AI」が採点**し、
不合格なら**改善点だけ**を統合AIに渡して再生成させる。

```
既存の5エージェント・パイプライン
（専門AI①②③ 並列 → 反証AI④ → 統合AI⑤）
        │  ※専門AI・反証AIの実行は初回の1回だけ
        ▼
   統合回答（1回目）
        ▼
   [評価AI⑥] 5軸で採点（JSONのみ返す・回答は書き直さない）
     正確性 / 論理性 / 専門性 / 実用性 / 根拠
        ▼
   合格？（総合90点以上 かつ 全項目80点以上）
     ├─ YES → その回答を返却（ループ終了）
     └─ NO  → 改善点だけを抽出（前回回答の全文は渡さない）
              → 統合AI⑤だけ再生成 → 再評価
              → 最大Nループ。全部不合格なら最高得点の回答を返す
```

- 合否は評価AIの自己申告を信用せず、**コード側が閾値から算出し直す**
- 全ループの生成物・スコア・改善点・トークン使用量をDBに保存（将来のRAG・蒸溜・回答ランキングの素材）

### 3-2. 適用範囲とループ上限（コスト設計）

| 対象 | surface | ループ上限（既定） | 理由 |
|---|---|---|---|
| Q&A（データに質問） | `ask` | 2 | 自由質問で品質評価の効果が最大。初回＋最大1回の改善 |
| 日次サマリー | `daily_summary` | 2 | 1レポート初回閲覧時のみ生成（以降キャッシュ） |
| 期間サマリー | `period_summary` | 2 | 有効化する場合も初回＋最大1回の改善 |
| 週次レポート | `weekly_report` | 2 | 有効化する場合も初回＋最大1回の改善 |

再ループは**統合AIだけ**を再生成する（専門AI3体＋反証AIは使い回し）ため、
1ループ追加あたりの増分は「統合AI1回＋評価AI1回」に抑えられる。合格したら即終了。

### 3-3. 本番の段階導入設定（2026-07-22）

品質ループは環境変数未設定時にOFFとなる fail-closed 設計とし、2026-07-22時点の本番ではQ&A・日次・期間・週次の全surfaceを明示的に有効化している。
Supabase Edge Functions Secrets の設定は次のとおり:

```
FOODCOURT_LOOP_ENABLED=true
FOODCOURT_LOOP_APPLY_TO_ASK=true
FOODCOURT_LOOP_APPLY_TO_DAILY=true
FOODCOURT_LOOP_APPLY_TO_PERIOD=true
FOODCOURT_LOOP_APPLY_TO_WEEKLY=true
```

現在の安全運用値:

```
FOODCOURT_LOOP_PASS_TOTAL=70
FOODCOURT_LOOP_PASS_EACH=65
FOODCOURT_LOOP_MAX_ASK=2
FOODCOURT_LOOP_MAX_DAILY=2
FOODCOURT_EVALUATOR_PROVIDER=groq
FOODCOURT_AI_REQUEST_BUDGET_MS=110000
```

管理画面の合格ライン設定 `foodcourt_evolution_passing_score` が存在する場合は、その整数値が
総合点・各評価軸の両方へ優先適用される。2026-07-22時点の本番値は70点。

反証AI④は全surfaceでGemini 3.5 Flash（→ Groq）、評価AI⑥はGroq GPT-OSS（→ Gemini）が標準。統合はOpenAI→Gemini→Groq。旧Claude設定は新しい役割設定へ自動継承しない。Moonshotは構成外。

**キャッシュ挙動**: 現行の通常版・loop版はどちらも `foodcourt-analysis-ai-v30-plausibility-check`
であり、日次ループをOFFにしてもキャッシュバージョンは変わらない。旧記録の `v16-loop-learning` は当時の値。

### 3-4. 記録テーブル

| テーブル | 役割 |
|---|---|
| `foodcourt_ai_loop_runs` | 1回の質問/生成の最終結果（採用ループ・最終スコア・返却理由） |
| `foodcourt_ai_loop_iterations` | 各ループの生成物・5軸スコア・改善点・使用量（run_idで紐づく） |

`returned_reason` の値: `passed`（合格）/ `max_loop_best`（上限到達→最高点採用）/
`evaluation_failed`（評価AI失敗→その回の生成物を採用）/ `generation_failed`（生成自体が失敗）。

AI使用料は従来どおり `ai_usage_events` に全AI呼び出し（評価AI・再生成分を含む）が記録され、
AI使用料ページに合算される。

## 4. 2つのループの関係と今後

```
              ┌──────────  数値の世界  ──────────┐
   実績蓄積 → 5方式を事前発行 → 後日採点 → 条件達成時だけ週次切替   …ループ①
              │
              │ 採用予測・参考係数・評価の注意点をAI解説へ供給
              ▼
              ┌──────────  文章の世界  ──────────┐
   5エージェントが回答 → 評価AIが採点 → 不合格なら改善して再生成   …ループ②
```

- AIへ渡す乗算係数・統計は解釈用。採用方式が別なら、その方式の数式や因果的根拠と同一視しない。数値予測の採用条件とAI回答の品質点は独立する。
- 将来拡張（設計書14章）: 合格回答の再利用（RAG）、初回回答→改善→最終回答ペアの蒸溜、
  ユーザーフィードバック（役に立った/違う）による回答ランキング。
- ループ①の次段階: 休業・短縮営業、警報・交通、祝日、予約等を発行前に取得できる形で蓄積し、新IDの候補で事前評価する。高度化だけで精度が上がるとは限らない。
