# 分析の整合性・正確性・発展性の監査

2026-09-20。対象はフードコートQ&AとJournalの共通KPI試算、KGI/KPI/KFI出力、前提入力、品質評価への接続。実績データ・DB・過去回答は変更しない。

## 結論と修正

「AIは解釈を担当し、数値はコードと出所付きデータを正本にする」という分離、認可済み店舗の取得、入力参照と試算同意の分離は維持する。ただし、コード計算であっても母集団・丸め・費用範囲が不適切なら結果は誤るため、以下を修正した。

| 重要度 | 問題 | 修正 |
|---|---|---|
| 高 | 月次代替値を含む総客数を少数の日別レコード数で割る | 同日の売上・正の客数が揃う重複なしの日だけで客数/客単価を算出。同日競合は除外し件数を明示 |
| 高 | 部分月の観測日数を月間営業日数と表示 | 全暦日を観測した月だけ売上発生日数を代理値に使用。部分月は実績なし・シナリオ扱い |
| 高 | 貢献利益が非正でも損益分岐/縮小0個と表示 | 不成立はnull。「導入前に価格・原価を見直す」と表示 |
| 高 | 生産上限・時間帯内訳・売上で丸め方が違う | 廃棄後販売上限を整数化しランチ＋各ディナーで共有。最大剰余法で内訳の和を保持。表示単価×表示個数で売上を再現 |
| 高 | 改善提案やKPI達成状況の確認だけで試算起動 | 明示的試算/数値目標設定と通常提案/評価を分離。FC・Journal・サーバーの一致を検証 |
| 中 | 値引きセットから負の追加原価を生成 | 未入力はシナリオ原価。値引きから原価を逆算しない |
| 中 | 仮定係数の廃棄警戒値が入力ラベル、100%超 | シナリオラベル・100%上限。0%許容なら0%超、その他は警戒値以上。縮小の整数境界も修正 |
| 中 | 商品購入額を客単価上昇額と表現 | 商品購入額へ改称。店舗純増・既存商品置換・最終利益と区別 |
| 中 | 範囲外入力を上限/下限の別値へ変換 | 型・範囲・整数検証。不正値は未入力として再確認。自由文の負数を正数化しない |
| 中 | 評価資料の途中省略で最後のシナリオを失う | 既存14,000文字上限内で入力/確定試算ブロックを優先保持。省略箇所をデータなしと断定しない |
| 中 | 効果量を必ず数値で添える指示が創作禁止と矛盾 | コード提供の計算値がある場合だけ引用。未算出なら判定保留 |

## 分析で守る関係

- KGIは利用者が求める成果。目標値・期限が未合意なら候補/未設定とする。
- KPIは客数・客単価などの要因。回転率をさらに掛けて売上を二重計上しない。共有席を自店専有席と仮定しない。
- KFIは現場行動。担当候補・実施時・記録方法を示し、行動→KPI変化→KGI寄与を検証する。販売目標から声かけ件数を創作しない。
- 採算は別の確認軸。売上増だけで継続を決めず、一般的な原価率・FLR率の例を当店目標へ転用しない。
- 実績・入力仮定・シナリオ仮定を分け、同一期間・単位・税区分で比較する。仮定を含む結果は実績ではない。

## 正確性の限界

現行試算器は焼成商品の導入を想定した参考モデルで、全業態・全KPIの汎用予測器ではない。購入率、イベント需要、販売構成、月間日数等の既定値は作業仮説。保守/標準/強気は確率や信頼区間ではない。

売価と原価は同じ税区分と仮置きするが、税額を自動換算しない。家賃・光熱費・包装費・決済手数料等は未算入。算入人件費の回収個数を店舗全体の損益分岐と解釈しない。廃棄は加重原価全体へ一律適用する簡易モデル。セット率は個数、テイクアウト比率は会計数が分母。

円単位に丸めた加重価格・加重原価・貢献利益・人件費を以後の計算に使い、表示値との再現性を優先する。元の精密値との差があるため実際の会計・発注とは区別する。月間営業日数は全暦日観測月の売上発生日数という代理値で、ゼロ売上営業日は識別できない。

AIの自己採点は正確性の保証ではない。数値監査は主に数値の存在照合であり、同じ数字を別指標へ転用する誤りを完全には防がない。外部AIモックのテストは規則/データの接続を検証するが、実AIの文章が毎回規則を守ることは保証しない。

## 発展性と推奨順序（今後の設計・未実装）

1. **実測の整備**: 税区分、正確な営業日、商品別出数/原価、廃棄、案内/提案件数を同じ日付・時間帯で記録する。入力負担と店舗権限を先に合意する。
2. **指標定義の共通化**: 指標ID、分母、期間、単位、税込/税抜、実績/仮定、出所を構造化し、表示と計算を同じ定義から作る。
3. **意味の検証**: 回答値を元の指標IDへ照合し、式・単位・期間の不一致を表示前に検出する。自由文の規則だけに依存しない。
4. **モデルの分離・実測校正**: 焼成商品、予約、リピート、原価管理を別モデルにする。実測が揃ってから購入率・行動→購買率を校正し、曜日/イベント/天候の交絡を考慮する。
