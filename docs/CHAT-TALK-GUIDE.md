# トーク（chat.html）ガイド

社内連絡用のグループチャット。`public/chat.html`（1ファイル・約9,900行、UI/CSS/ロジックを全て内包）が
Supabase Auth / Realtime / Storage / Edge Function と組んで動く、M-talkの1画面SPA。

- 本番: `https://marugo-s.github.io/line_report/chat.html`
- Supabase プロジェクト: `hocbnifuactbvmyjraxy`
- 管理画面: `chat-admin.html`（本部フル管理セッション専用）。詳細は
  [CHAT-ADMIN-PERMISSIONS.md](./CHAT-ADMIN-PERMISSIONS.md)。
- ここに endpoint、暗号鍵、VAPID 秘密鍵、メッセージ本文、顧客名を書かない。

この文書は `chat.html` が実際に持つ機能を、画面構成から1件ずつのメッセージ操作まで
網羅した参照資料。行番号や関数名は 2026-08-26 時点のコードに基づく。

---

## 0. 全体構成

```
public/chat.html
├─ <style>            … 全CSS（テーマは1色固定、ダーク基調のUI）
├─ <body>             … サイドバー / メイン画面 / 各種オーバーレイの静的マークアップ
└─ <script>           … 状態管理・Supabaseクエリ・DOM描画（約6,800行、関数400個超）
```

画面は3カラム構成。

| 領域 | id | 内容 |
| --- | --- | --- |
| ナビレール | `#navRail` | 自分のアバター、M-talkアイコン、通知トグル、通知テストボタン |
| トーク一覧 | `#sidebar` | タブ、検索、ルーム一覧、新規トークFAB |
| メイン画面 | `#mainContent` | ヘッダー、メッセージ、入力欄、各種オーバーレイ |

CSSカスタムプロパティ `--chat-viewport-height` 等は `syncChatViewport()` がモバイル実機の
アドレスバー・ソフトキーボード分だけ動的に書き換える（後述 §2）。

## 1. 認証・利用開始

### ログイン／新規登録

- メール＋パスワードでログイン（`login()`）。8文字以上のパスワードでセルフ登録（`signup()`）。
- ログイン失敗時のエラーメッセージは「メールアドレスまたはパスワードが違います」
  「メールアドレスの確認が完了していません」など、Supabaseのエラー文字列を判定して日本語化する。
- 「この端末にメールとパスワードを保存する」チェックで `localStorage`（キー
  `chat_saved_credentials`）へ**平文**保存し、次回訪問時に自動入力する
  （`applySavedCredentials()`）。共用端末では使わせないこと。
- 初回のみ `#profileForm` で表示名とアイコンを決める（`createProfile()`）。
  `chat_users` への insert が許可リスト外だと「このアカウントはチャットの利用を
  許可されていません」で弾かれる。
- プロフィール作成後、`chat_user_access.signup_status` は `pending`、
  `access_enabled` は false。所属店舗は必須（複数可）。許可／不許可カードは
  管理者専用の「管理者通知」ルームへ届き、予約通知の1対1や店舗ルームの一般メンバーには見えない。
  許可されると閲覧のみで、申請した所属店舗が反映される。
  所属の後からの変更も管理者許可後に `chat_user_stores` へ書き込む。
  新しい1対1は所属店舗が重なる相手だけ（既存の1対1はそのまま）。

### 利用可否ゲート（`chat_user_access`）

ログイン成功後、`loadCurrentChatAccess()` で自分の行を読み、以下のいずれかなら
`showChatAccessBlocked()` を表示してM-talk本体には入れない。

- `access_enabled !== true`
- `deleted_at` が入っている（論理削除）
- `restricted_until` が未来（一時制限中）

制限解除時刻には `setTimeout` で自動的に画面を更新するタイマー
（`scheduleChatAccessExpiryCheck()`）を仕込み、開いたままの画面がブロック解除に
気づけるようにする。Realtimeで `chat_user_access` のUPDATEも購読しており、
管理画面から状態を変えられた場合も即座に反映される。

`chat_user_access` は個別権限も持つ（`can_start_direct` / `can_create_group` /
`can_browse_users`）。これらは「友だち」「登録ユーザー」「Bot」タブの表示、FABの
表示、1対1開始ボタンの活性・非活性などUI全体に反映される（`syncGlobalCapabilityUi()`）。

## 2. 画面のレスポンシブ対応・PWA

- `isMobileLayout()` は `matchMedia('(max-width: 768px), (max-height: 600px) and (pointer: coarse)')`
  で判定し、PC向け注釈（「Shift+Enterで改行」等）とモバイル向け簡易文言を出し分ける。
- モバイルでは `visualViewport` の `resize`/`scroll` を監視して `syncChatViewport()` を呼び、
  ソフトキーボード表示時も入力欄が隠れないよう `--chat-viewport-height` /
  `--chat-viewport-top` / `--chat-composer-height` を再計算する。入力欄の高さは
  `ResizeObserver` でも監視し、複数行入力・文章内アイコンプレビューの出し引きに追従する。
- `chat-sw.js` を `scope: './'` で登録する（Service Worker）。新しいWorkerが有効化されたら
  1回だけ自動リロードし（`sessionStorage`で二重発火を防止）、画面を開いたままの端末が
  旧UIを保持し続けないようにする。
- iOSは「ホーム画面に追加」したstandalone版のみPWA機能（通知等）の対象。通常Safariタブでは
  ホーム画面追加を案内する（`isIosDevice()` / `isStandaloneApp()`）。
- `gesturestart`/`touchmove` 等でピンチズームを抑止する（`preventMobileZoomGesture`）。

## 3. トーク一覧（サイドバー）

### タブ

`すべて` / `友だち` / `グループ` / `登録ユーザー` / `Bot` / `ゴミ箱` の6つ（`setTalkTab()`）。
`登録ユーザー`と`Bot`は `can_browse_users` が無ければ非表示。

- **すべて**: 自分が参加しているルーム＋「未参加のグループ」（招待リンクを知らなくても
  一覧には出る非DM・非店舗ルーム）。ボタンは「招待で参加」。リンクを貼ると
  `chat_join_by_invite` で入る。グループID指定の無断参加はしない。
- **友だち**: 自分がDMを持っている相手、および「登録ユーザーから友だちにする」の
  候補一覧（未DMの人間ユーザー）。
- **グループ**: DMでも店舗固定ルームでもない複数人ルーム。
- **登録ユーザー**: 全ユーザー（Bot以外）を一覧し、チェックして「招待する」で
  既存ルームへ一括招待 or 新規グループ作成できる。
- **Bot**: 店舗Botの一覧。「1対1」（`can_start_direct`必須）と「招待」ボタンを持つ。
- **ゴミ箱**: `trashed_at` が付いたルーム。復元・完全削除のみ操作可能。

### 検索

`#talkSearch` は文脈で挙動が変わる。

- 通常タブ: ルーム名・最終メッセージ本文をクライアント側でフィルタしつつ、250ms
  デバウンスで `chat_messages` への `ILIKE` 全文検索も別枠（`#messageSearchWrap`）に表示する。
- `登録ユーザー`/`Bot`タブ: ユーザー名でのフィルタのみ。

### 並び順・装飾

- ピン留めルームを先頭にまとめ、以降は最終発言時刻の降順。ピン留めは**5件まで**
  （`TALK_PIN_LIMIT`）。
- 行の装飾: ピン留めマーク、非通知マーク、`店舗`バッジ（店舗固定ルーム）、`BOT`バッジ
  （Bot参加ルーム。ロビー担当のBotがいるだけで人間だけのルームには出さない）、
  `ゴミ箱`バッジ。未読は99+で頭打ちの丸バッジ。
- 店舗Botのアイコンは `STORE_BOT_LOGOS`（22店舗ぶんのSVG対応表）を最優先し、
  対応表にない店舗は `icon_url` かイニシャルへフォールバックする。

### スワイプ操作・右クリックメニュー

各行はポインタドラッグで左右にスワイプでき（`bindTalkSwipe()`）、開閉は72px単位。

| 方向 | 通常ルーム | ゴミ箱内のルーム |
| --- | --- | --- |
| 右へスワイプ（左に出る） | ピン留め切替 / 非通知切替 | （操作なし） |
| 左へスワイプ（右に出る） | 非表示 / 退出 | 復元 / 完全削除（権限に応じて出し分け） |

PCではポインタの右クリック（`contextmenu`）で同じ操作をメニュー形式
（`openTalkContextMenu()`）に出す。メニューにはルーム設定への導線も含む。

非表示にしたルーム（`hidden_at`）は検索していない限り一覧から消えるが、新着が来ると
自動的に再表示される（`handleIncomingMessage()` が `hidden_at` をクリアして
`chat_set_hidden` を呼び直す）。

## 4. ルーム種別と権限モデル

`chat_groups` は3種類の性質を持つ（組み合わせ可）。

- `is_direct`: 1対1（自動生成。相手は `attachDirectPeers()` で解決）
- `is_store_room`: 店舗固定ルーム（退出・削除不可、店舗Botが常駐）
- 上記どちらでもない: 通常の複数人グループ

各メンバーは `chat_group_members` に4つの真偽値権限を持つ（`membershipFor()` /
`roomCapability()` で判定）。

| 権限 | 意味 | UIへの影響 |
| --- | --- | --- |
| `can_view` | 閲覧できる | falseになった瞬間、開いていれば強制的にチャットを閉じる |
| `can_send` | 送信できる | falseなら入力欄が読み取り専用表示（`composer-read-only`）。送信系の全操作前に `requireCurrentRoomSend()` でガード |
| `can_invite` | 招待できる | 招待ボタン・招待シートの表示可否 |
| `can_manage` | ルーム管理 | ルーム設定・アイコン変更・メンバー退出・ゴミ箱操作・予約/予定管理の可否 |

権限変更はRealtimeで即時反映される（`chat_group_members` のUPDATE/DELETEを購読）。

### 退出・ゴミ箱・完全削除

- **退出**（`leaveTalk`）: 店舗固定ルーム以外、確認ダイアログの上で自分を抜ける。
- **ゴミ箱へ移動**（`trashTalk`、`can_manage`必須）: 店舗固定ルーム以外が対象。
  移すと一覧から隠れ、送信不可になる。
- **復元**（`restoreTalk`）。
- **完全削除**（`purgeTalk`）: ゴミ箱にあり、かつ**ルーム作成者本人**だけが実行可能。
  ルーム名の再入力一致を要求する二重確認の上、`admin-api` の
  `/chat-room-purge` を叩く（クライアントの直接DELETEではない）。メッセージ・画像・
  `mtalk-group-{id}` の予定だけが消え、他ルームや店舗の予約・売上には影響しない。

## 5. メンバー・招待

- 複数人ルームのヘッダーをタップすると `#memberStrip` にメンバーの横並びアイコンが開く
  （`toggleMemberStrip()`）。DMや1人ルームでは出さない。
- **招待シート**（`openInvite()`）: 招待リンクの表示・コピー・共有（`navigator.share`
  対応）・再発行、現在のメンバー一覧（`can_manage`なら「退出させる」ボタン付き。
  予約通知Botや店舗固定ルームのBotは退出させられない）、友だち検索して個別招待、
  ルーム設定への導線、自分の退出ボタン。
- **登録ユーザー一覧からの招待**（`openUserInviteTarget()`）: 複数選択したユーザーを
  既存ルームへ一括招待するか、「新しいグループを作って招待」で新規作成する。
  Botは新規グループの初期メンバーにはできない（既存ルームへの招待か1対1のみ）。
- ルーム設定本体（メンバーごとの権限変更、ルーム名変更等）は `room_settings.html`
  へ遷移して行う（`openRoomSettings()`）。`can_manage` が無ければ開けない。

## 6. メッセージ入力・送信

### 入力欄

- 高さは内容に応じて自動リサイズ（40〜120px、`resizeComposer()`）。プレースホルダーの
  折り返しでも読める最小高さを`canvas`で実測して決める。
- **PC**: Enterで送信、Shift+Enterで改行。**モバイル**: Enterは常に改行（送信は
  ボタンのみ）。IME変換確定のEnter（`isComposing`/keyCode229）は送信扱いにしない。
- 店舗Botがいるルームでは、プレースホルダーに「#メモ で資料保存」のヒントが付く。

### 「＋」ツールシート（`#composerSheet`）

入力欄左の「＋」（`toggleComposerSheet()`）から開く機能一覧。

| ボタン | 機能 |
| --- | --- |
| 画像・ファイル | ファイル選択ダイアログ（§8） |
| スタンプ | 感情イラストピッカー（§9） |
| 予約配信 | 日時指定送信（§12） |
| 通知せず送る | サイレント送信トグル（下記） |
| 個人メモ | 個人メモモードトグル（下記、§11とは別） |
| Keepメモ | Keepメモ一覧（§11） |
| アルバム | ルーム共有アルバム（§11） |
| ジャーナルに聞く | 電子ジャーナルAI埋め込み（§13、条件を満たすルームのみ表示） |
| 予定を見る | 予約・予定カレンダー（§10と同じ画面） |

### 送信モードのトグル（相互排他）

- **通知せず送る（サイレント）**: 送るメッセージは全員に届くが、Web Push配信だけを
  スキップする。保存先は `chat_messages.is_silent`。受信側の吹き出しに🔕マークが付く。
  ルーム設定や予約通知の複製には影響しない、メッセージ単位のトグル。
- **個人メモモード**: 入力欄の見た目はそのままに、送信すると誰にも届かず自分だけの
  個人メモとして保存される（§11「個人メモ」と同じ保存先）。送信ボタンの表示が
  「メモを保存」に変わる（`syncComposerModeUi()`）。
- どちらのモードも `#composerModeChip` に状態が表示され、×で解除できる
  （`clearComposerMode()`）。

### 返信・メンション

- メッセージの「…」メニューから「返信」を選ぶと `#replyBar` に引用元が表示され、
  送信時に `reply_to_id` として保存される（`setReplyTarget()`）。
- 入力中に `@`/`＠` を打つと、そのルームの参加者候補がポップアップする
  （`updateMentionPicker()`）。↑↓で選択、Enter/Tabで確定、Escで閉じる。
  実際にメンションとして保存されるのは、本文中に `@表示名` の形で実在する参加者名が
  含まれる場合だけ（`collectMentions()`）。サーバー側トリガでも参加者に絞り直される。

### カードメッセージへの応答

予約通知などのカード（`kind='card'`）に埋め込まれたボタンは、`data-card-command`
属性を押すと`sendCardCommand()`が定型文をテキストメッセージとして送信する
（Botの次の応答を引き出す入力ショートカット）。`data-card-action` がURLなら
新規タブで開く（`mtalk_schedule.html` へのリンクは同一画面内の予約・予定オーバーレイに
差し替える特別扱い）。

## 7. メッセージ表示・1件ごとの操作

### 種別ごとの描画（`buildMessageNode()`）

| kind | 表示 |
| --- | --- |
| `text` | 吹き出し＋本文（メンションハイライト、リンクプレビュー付き） |
| `image` | 署名URLで読み込む画像（タップで拡大ビューア） |
| `file` | ファイル札（アイコン・ファイル名・サイズ・保存ボタン、タップで内蔵ビューア） |
| `sticker`（大きく送る） | 画像単体 |
| `sticker`（文章内に入れる） | 64px相当のイラスト＋本文を1つの吹き出しに同居 |
| `card` | 見出し・項目リスト・区切り線・ボタンを持つリッチカード（Botのみ生成可） |

返信元がある場合は吹き出し内（画像/ファイル/カード/スタンプの場合は上部）に
引用プレビューを表示し、タップで元の発言へジャンプする（読み込み済みでなければ
その位置を読み直す）。

### 操作メニュー（「…」ボタン、`openMessageMenu()`）

- 上段: リアクション15種を5列×3段で表示（送信権限がある場合のみ）。
- 下段: 返信・コピー・**Keepに保存**・転送・（自分のテキストのみ）編集・（自分の発言のみ）削除。
- 背景は60%透明＋ぼかしで、下の吹き出しが透けて見える。

### リアクション

- 絵文字15種（👍✅🙏😂❤️😮😡😓🤔🙄😭🎉👏👀🤷）。1人1メッセージにつき1つまで、
  別の絵文字を選ぶと自動的に置き換わり、同じものをもう一度選ぶと取り消せる。
- 通信を待たず画面を先に更新し、失敗時のみ巻き戻す楽観更新（`toggleReaction()`）。
- 吹き出し下のリアクションチップをタップすると、誰が押したかをアイコン・名前・
  絵文字で一覧表示する（`openReactionDetails()`）。

### 既読

- 自分の発言の下に「既読」（1対1）または「既読 N」（グループ、自分以外の既読者数）を表示。
- 既読はグループ全員が閲覧開始時刻を共有する仕組み（`chat_read_states`）。開いている
  ルームでもアプリがバックグラウンド中に届いた発言は未読のまま数え、再表示時に既読化する。
- 未読数はDBの `chat_unread_counts()` を正本とし、既読保存の成否にかかわらず
  必ず再取得する（画面だけ先に既読になったまま乖離しない）。

### コピー・転送・削除・Keepへの保存

- **コピー**: 画像は`[画像]`、ファイルは`[ファイル] 名前`、それ以外は本文をクリップボードへ。
- **転送**: 転送先ユーザーを選ぶと1対1トークを開始/流用し、スタンプ・画像・テキストを
  種別に応じて作り直して挿入する（画像は署名URLを取得→再アップロードで新規パスを発行）。
- **編集**: 自分の`text`、および文章付き（compact）スタンプのみ。入力欄が編集モードになり、
  「保存」で`content`と`mentions`を更新する。直す前の本文は`edit_history`へサーバが積み、
  吹き出しでは取り消し線で残す（クライアントから履歴削除不可）。`edited_at`と
  「編集済み」も付ける。kind・payload・送信者・返信先・サイレントはDBトリガが固定する。
  Pushも資料登録もINSERT専用のため再送されない。画像・ファイル・カード・大きく送った
  スタンプは対象外。
- **削除**: 自分の発言のみ。Realtimeで他参加者の画面からも消える。
- **Keepに保存**: 本文（または`[画像]`）をKeepメモへコピーする1クリック操作
  （§11のKeepメモ本体とは別入口）。

### 画像ビューア（`openImageViewer()`）

拡大表示に加えて、保存／名前を付けて保存／転送／Keepメモへ転送の4アクションを持つ。

## 8. 添付ファイル・画像

送信できる形式と上限は次の通り。全て非公開バケット `chat-images` の
`groups/<group_id>/<uuid>.<拡張子>` へ入り、表示のたびに署名URL（1時間）を発行する。

| 種類 | 形式 | アプリ内プレビュー |
| --- | --- | --- |
| 画像 | JPEG / PNG / WebP / GIF | ✅ 画像ビューア |
| PDF | `.pdf` | ✅ ブラウザ内蔵ビューア（iframe） |
| Excel | `.xls` / `.xlsx` | ✅ 表として表示（シートはタブ切替、先頭500行×40列まで） |
| Word | `.docx` | ✅ 本文を整形表示（`.doc` 旧形式は不可） |
| テキスト | `.txt` / `.csv` | ✅ 等幅整形表示（先頭512KBまで） |
| PowerPoint | `.ppt` / `.pptx` | ❌ 保存して外部アプリで開く |
| 書庫 | `.zip` | ❌ 保存して外部アプリで開く |
| iPhone写真 | `.heic` / `.heif` | ✅ 送信時にJPEGへ自動変換してから画像扱い |
| 電子ジャーナル | `.lzh` | 添付不可（§8-4） |

上限は**25MB**（`CHAT_FILE_MAX_BYTES`）。`text/html` と `image/svg+xml` は許可しない
（署名URLで開いた際にスクリプトが動くため）。

### アップロード〜送信の流れ

1. 「画像・ファイル」ボタン、ドラッグ&ドロップ、クリップボード貼り付け（画像のみ）の
   いずれかでファイルを選ぶ。
2. 画像は送信前に長辺1600px・JPEG品質0.82へ縮小（`prepareChatImage()`）。
3. `askSendModeForFiles()` が「今すぐ送る／予約配信」の選択を挟む
   （非画像ファイルは予約配信不可。「まず今すぐ送信してください」と案内）。
4. 画像を送ると、店舗の売上解析用メディア台帳へもアーカイブを試みる
   （`archiveChatImageInMediaLibrary()`。失敗してもメッセージ送信自体は成功扱い）。

### アプリ内プレビューの実装

重い描画ライブラリは `public/vendor/` に自己ホストし、実際に開いたときだけ遅延読込する
（`loadVendorScript()`。外部CDNは使わない）。

- `xlsx.full.min.js`（SheetJS CE 0.20.3）: `sheet_to_json`で値だけ取り出し、
  HTML出力は使わず自前でテーブルを組む。
- `mammoth.browser.min.js`（1.8.0）: 変換結果は `sandbox=""` のiframeに閉じ込め、
  スクリプトも`javascript:`遷移も効かないようにする。
- `heic2any.min.js`（1.3MB）: SafariのネイティブHEICデコード（`createImageBitmap`）が
  失敗したときだけ読み込む。

Office文書を外部の変換サービス（Office Online等）へ渡すことはしない。署名URLごと
資料が社外へ出ると、`chat-images`を非公開にしている判断と矛盾するため。

### HEIC自動変換

iPhoneの「高効率」設定で出る`.heic`は、送信時にJPEGへ変換してから通常の画像経路
（縮小・圧縮）に乗る（`convertHeicToJpeg()`）。変換に失敗したら原本のままファイル
添付として送る。即時送信・予約配信の両方で変換する。

### 電子ジャーナル（.lzh）の特別扱い

`.lzh`/`.lha`はトークへの添付として扱わない。店舗ルーム（または店舗Botのいるルーム）に
落とすと、そのルームの店舗として `chat-knowledge` 経由で電子ジャーナルへ登録され、
営業日・総売上のカードが返る。取込先の店舗が決まらないルームでは確認ダイアログから
`pos-journal.html` へ誘導する（`promptJournalArchive()`。原本の二重管理を避けるため、
汎用の添付として置きっぱなしにはしない）。

> ⚠️ 2026-08-25時点、この取込が使えるのは Bistro CAVACAVA（店舗コード1015）のみ。
> 他店舗の登録は `pos_journal_store_codes` へのinsertだけで完了し、デプロイ不要。

## 9. 感情イラスト（スタンプ）

- 入力欄の大きな `☺`（28px）を押すとピッカーが開く（`toggleStickerPicker()`）。
- カテゴリは「感情」（約93点）と「漫符・記号」（約39点）の2タブ。狭い画面では
  タブ行を横スライドでき、ピッカー本体もスワイプ／マウスドラッグ／トラックパッドの

- 送信モードは「大きく送る」と「文章内に入れる」の2つ。**入力中に文字があった状態で
  ピッカーを開くと自動的に「文章内に入れる」が選ばれる**。文章内モードでは選んだ
  イラストが入力欄上にプレビュー表示され（`#inlineStickerPreview`）、その後に打った
  文章と一緒に1件のメッセージとして送信される。
- カタログ（`chat_stickers`）は端末に24時間キャッシュし（`localStorage`）、初回起動時に
  アイドル時間を使って先読みする（`warmImageAssets()`）。
- 送信データはDBトリガが有効なIDから正規化して作り直すため、クライアントの申告した
  ラベル・パスは信用されない。

## 10. 検索ランチャー

トーク下部メニューの「検索」（`openSearchLauncher()`）は、投稿せず自分だけに見える
ダイアログを開く。3つの入口はいずれもトーク発言や他メンバーへの通知を発生させない。

1. **トーク履歴・メッセージ検索**: サイドバー上部の検索欄にフォーカスを移すだけ
   （実体は§3の全文検索）。
2. **予定・予約カレンダーを開く**: `mtalk_schedule.html` を開く。予約タブ（Gmail予約
   取込＋手入力の店舗データ）と予定タブ（同じM-talkルーム・同じ店舗キーのM-talkルームの
   カレンダー予定）をタブ切替で見る。閲覧は`can_view`、追加・編集・キャンセルは
   `can_manage`が必要。
3. **写真・メディアライブラリ**: 店舗Botがいるルームでのみ表示。既存の`media.html`を、
   ワンタイムログイン（発行後5分で失効、交換後のセッションは15分で失効）付きで開く。
   閲覧セッションはそのルーム対応の店舗のメディアだけに絞られる。

メッセージ検索は日本語が空白で区切られないため`to_tsvector`ではなく`pg_trgm`の
GINインデックスを使う（`public`スキーマ配置、`extensions`と書くと索引作成に失敗する
点に注意）。2文字以上で発火、250msデバウンス。結果をタップすると前後25件を読み込んで
その発言へジャンプする。

## 11. 個人用ストレージ機能（3種類、混同注意）

名前が紛らわしい3つの機能は、保存先・見え方が完全に別。

| 機能 | 保存先 | 範囲 | 送信される？ |
| --- | --- | --- | --- |
| 個人メモ | `chat_private_notes` | ルーム単位（そのルームのタイムライン上に挟んで表示） | されない |
| Keepメモ | `chat_keep_items` | ルーム横断（自分専用の保存棚） | されない |
| アルバム | `chat_albums` / `chat_album_items` | ルーム単位・**メンバー共有** | 既存の投稿画像を整理するだけ |
| `#メモ` | `chat_messages`（店舗ルームへ実際に送信） | 店舗ルーム | **される**（Journal Reportの資料になる） |

### 個人メモ

「＋」→「個人メモ」でモードに入り、そのまま入力→送信すると、実際には送信されず
`chat_private_notes`へ保存される。ルームのタイムライン上、書いた時刻の位置に
破線・付箋色の吹き出しとして挟まれる（通常の発言と区別するため中央寄せ）。
RLSで本人限定（`user_id = auth.uid()`）、編集は不可（削除して書き直す）。返信・引用・
メンション・検索・転送のいずれの対象にもならない。本人ならどの端末からも同じ内容が
見える（Realtime同期）。

### Keepメモ

「＋」→「Keepメモ」で開く、ルームをまたいで使える自分専用の保存棚。最大5,000文字の
テキストを追加・削除できる。メッセージの「…」メニューから「Keepに保存」で本文を
直接送り込むこともできる。画像ビューアの「Keepメモに転送」で画像も保存できる。
ログアウトでは消えない（DB保存のため）。

### アルバム

「＋」→「アルバム」で開く、ルーム単位の画像整理機能。名前を付けて作成し、そのルームに
投稿済みの画像から選んで追加する（他ルームの画像は追加不可、DBトリガで再検証）。
作成者または`can_manage`を持つメンバーが編集・削除できる。一覧はサムネイルのモザイク
表示、詳細はグリッド表示で画像を拡大・ダウンロードできる。

## 12. 予約配信（スケジュール送信）

- 対応する内容: テキスト、感情イラスト（単独／文章と同時）、画像。
- 「＋」→「予約配信」、または画像送信時の「予約配信」選択から開く

  ポーリングしない）。

## 13. 電子ジャーナルに聞く（AI埋め込み）

**M-talk自体はAIロジックを持たない。** 1対1トークの「＋」→「ジャーナルに聞く」から
`mtalk_journal_ai.html`を開き、その中にジャーナルレポートのAIチャットをそのまま
`iframe`で埋め込む（`openJournalAi()`）。ページ遷移した体感は無く、利用者から見れば
M-talkの画面のまま。

### 表示条件

`currentRoomAllowsJournalAi()`が満たされる場合のみボタンが出る。

1. `currentRoomHasOnlyMeAndBots()`: そのルームの**人間メンバーが自分1人だけ**
   （`is_direct`ではなく実際の人数で判定。利用者が自分でBotを招待して作った
   2人部屋も対象になる）。
2. `groupMembers`に`store_key`を持つ店舗Botがいる（取込先の店舗が一意に決まる）。

満たさない場合はボタン自体が出ないか、押しても理由付きのアラートで案内する。

### なぜ埋め込みか

ジャーナルレポートのAI（質問解釈・期間解決・`systemInstruction`組み立て・聞き返し）は
`jnl2txt.html`（17,000行超）の中にあり、サーバー側へ切り出すと「よく似た別物」になって
答えが一致しなくなる。そのまま動かすのが唯一、同じ答えを保証する方法。

### つなぎ方（概略）

```
chat.html → mtalk_journal_ai.html?group_id=<id>
  → POST /auth/chat-journal-login （M-talkのSupabase JWT）
  → iframe: jnl2txt.html?mtalk_embed=1&lt=…&mtalk_group_id=…
```

発行されるのは**その店舗にスコープを固定した**ワンタイムリンク（5分）。
`?mtalk_embed=1`ではAIチャットパネル以外を隠し全面表示にする（CSSと起動条件のみで、
AIロジックには一切触れない）。回答に「💬 M-talkに貼る」が出るのは`mtalk_group_id`
付きアクセス時のみで、押すとMarkdownを読みやすいプレーンテキストへ整形してから
（`mtalkPlainTextFromMarkdown()`）そのトークへ投稿する。本文2,000文字制限のため、
長い回答は`buildMtalkJournalPasteMessages()`が1,900文字以内の複数メッセージへ
行単位で分割し、`[電子ジャーナル]（続き 2/N）`のように連番で順次投稿する。この接頭辞を
`chat-knowledge`が検出し、店舗Bot（雑談AI）が反応しないようにしている。

> ⚠️ 2026-08-25時点、この機能はジャーナルレポート側の制約でBistro CAVACAVA専用。

## 14. Web Push通知

### 有効化・無効化

- ナビレールまたはサイドバー上部の🔔/🔕トグルで切替（`togglePushNotifications()`）。
- iOS/iPadOSは「ホーム画面に追加」したstandalone版でしか有効化できない
  （非standaloneではアラートで案内）。
- 有効化のたびに`chat_push_user_preferences`へ状態を保存し、Realtimeで他タブ・他端末にも
  同期する（`subscribePushPreferenceChanges()`）。

### 購読切れからの復旧

- `chat-sw.js`は**登録URLを固定**する（`chat-sw.js?v=...`のようにURL自体を変えると、
  ブラウザが別Workerとして扱い既存購読がHTTP 410になる端末がある）。資産更新は
  Worker内の`CHAT_CACHE`名の更新で行う。
- 通知ONのまま`PushManager.getSubscription()`がnullになっていたら、自動で権限
  プロンプトは出さず、画面上部に「通知が切れたので、ここをタップして再開」バーを表示する
  （`showPushRestoreBar()`）。任意の画面タップでは再作成しない（endpointの増殖防止）。
- 再開時は古い購読をサーバーへ明示的に停止依頼してから`unsubscribe()`し、新規
  `subscribe()`後に`activate=true`で保存する（先に旧購読を消すと新規保存失敗時に
  通知を全て失うため、保存→停止の順）。

### 通知テスト・診断

- 「通知テスト」ボタン（`sendPushTest()`）は自分の現在の端末endpointへ4秒遅延の
  テスト通知を送る。iPhoneでホーム画面に戻る猶予を作るための遅延。
- 送信後は`pollPushDiagnosticStatus()`が数秒おきに診断APIをポーリングし、
  「Apple Pushへの送信に失敗」「通知表示に失敗」「通知センターへ登録済み」等の
  結果をトースト/アラートで返す。診断ログはブラウザキャッシュにも一時保存し
  （`flushPushDiagnostics()`）、次回起動時にサーバーへアップロードする。

### アプリバッジ

未読合計を`navigator.setAppBadge`（対応ブラウザ）またはService Worker経由で
ホーム画面アイコンに反映する（`syncAppBadge()`）。既読処理・通知設定変更のたびに
再計算する。

## 16. 店舗Botのロゴ・表示

- `chat_users.is_bot=true`かつ`store_key`がある店舗Botは、`public/icons/store-bots/`の
  専用ロゴを`icon_url`より優先して表示する（`STORE_BOT_LOGOS`、22店舗ぶん）。

- 店舗ロゴは白背景・`object-fit: contain`・4px余白（一般ユーザー画像は`cover`）。

- Bot参加ルームには一覧で青い`BOT`バッジが付く（通常ユーザーだけのルームには出さない）。
- 店舗Botは通常のM-talk画面から退出・削除できない。削除・復元は`chat-admin.html`だけで
  行い、物理削除せず`bot_deleted_at`を設定する（過去メッセージ・所属履歴は保持）。

## 17. 店舗固定ルームと `#メモ`

店舗固定ルームへ`#メモ`／`#日報`／`#note`（全角シャープ可）を送ると、`chat-knowledge`が
Journal Reportの「資料」へ登録し、Botが結果を返す。

- テキスト: `#メモ 本文`でそのまま資料になる。
- 画像・ファイル: `#メモ`が無ければ画像はメディア閲覧へ保存し、レシートなら同じ
  解析・同じ売上レポートカードを返す。
- URL: 本文中の`http(s)`リンクは安全なリンクカードとして表示する（別タブで開くのみ、
  M-talk側では外部ページの本文や認証情報を取得しない）。
- `chat-knowledge`はpg_netの内部シークレットで認可され、ゲートウェイのJWT検証は
  無効（`verify_jwt=false`）。設定を忘れると`UNAUTHORIZED_INVALID_JWT_FORMAT`で無反応になる。

## 18. 予約通知の複製（Bot発のカードメッセージ）

予約通知のトーク配信は**同じcronで発火するが、送信は独立**（M-talkへの送信成功で
通知を完了し、外部要因の遅延や失敗の影響を受けない）。対応するM-talkルームは`room_summary_settings.chat_group_id`、無ければ
同じ店舗キーのトーク。カードの本文は`kind='card'`として`service_role`のみが作成でき、
クライアントからの`card`偽装は`chat_set_message_author`トリガで弾かれる。

- 新規予約・変更・キャンセル: `gmail-alert-cron`
- 本日の予約まとめ: `reservation-today-cron`（トークは0件でも送る）
- 予定まとめ: `calendar-tomorrow-cron`（ルームごとに最大5スロット設定可）
- 共通処理: `supabase/functions/_shared/chat_bridge.ts`

投稿後は`chat-push?action=dispatch`を叩き、Web Pushまで配信する。

## 19. 雑談・簡単な相談（1対1・自分以外の人間がいない部屋）

店舗Botとの1対1、または利用者が自分でBotを招待して作った部屋で、既存のどのコマンドにも
一致しなかった発言に、`openai/gpt-oss-120b`が雑談・簡単な相談として応答する
（サーバー側`mtalk_casual_chat.ts`、判定条件は§13の`currentRoomAllowsJournalAi`と同じ
「人間メンバーが本人1人だけか」）。**売上・客数など店舗の実データには答えず**、
数字が必要な質問は「ジャーナルに聞く」へ誘導する。会話履歴はそのルームの
`chat_messages`（直近12件）をそのまま使い、Markdownは使わずプレーンテキストへ
整形してから通常の`text`メッセージとして保存する。

雑談AIはM-talk・Journal Reportの使い方に関する自然文の質問にも、
統合ヘルプ資料（`supabase/functions/_shared/mtalk_help_manual.ts` /
`line_report_help_manual.ts`、人間向け自動生成版は
`docs/LINE-REPORT-JOURNAL-AI-MANUAL.md`）を参照して回答する。

店舗スタッフ向けの使い方ページは `public/mtalk-help.html`
（本番 `https://marugo-s.github.io/line_report/mtalk-help.html`）。
操作手順だけを書き、テーブル名・管理API・内部構造は載せていない。
ログイン画面とアカウントメニューの「使い方」から開ける。

### 天気

「今日／明日の天気」などには、店舗座標の気象データ（Open-Meteo）で直接答える。
生成AIは通さず、返信末尾に店舗のおおまかな地域名と情報元を付ける。

### Web検索

ルーム設定の「AIのWeb検索」がONのときだけ、明示的な調べ物や最新情報が必要な
疑問に Perplexity を使う。既定はOFF。検索1回ごとに料金が発生し、
`ai_usage_events` へ実費を記録して AI 使用料ページに出す。
店舗の実数値は検索対象外で、「ジャーナルに聞く」へ案内する。
Webを見て答えたときは出典URLを1行に保ち、本文中でも開けるようにする。

## 20. データモデル

### 参加時点からの履歴

新しくルームへ招待・参加したユーザーは`chat_group_members.joined_at`以降の
メッセージだけを閲覧できる（画面側の非表示ではなく、RLSで取得自体を拒否）。
同じ境界を検索・Realtime・リアクション・未読数・Web Pushバッジにも適用する。
初回表示は最新50件（`MESSAGE_PAGE_SIZE`）、上端まで遡ると50件ずつ追加読込する。
表示済み履歴は最大12ルーム分だけメモリキャッシュし（`ROOM_VIEW_CACHE_LIMIT`）、
ルームの行き来での再通信を減らす。メッセージ本文は共有端末対策として
永続キャッシュしない（署名URLだけ`sessionStorage`に短期保持）。

### テーブル一覧

| テーブル | 役割 |
| --- | --- |
| `chat_allowed_emails` | 旧許可リスト。セルフ登録の制限には現在使わない |
| `chat_users` | 表示名とアイコン。`id`は`auth.users(id)` |
| `chat_user_access` | M-talkだけの利用状態、1対1開始・ルーム作成・ユーザー一覧権限 |
| `chat_groups` | トークルーム。`is_direct`が真なら1対1 |
| `chat_group_members` | 参加関係とルーム別の閲覧・送信・招待・管理権限 |
| `chat_messages` | 発言。`kind`は`text`/`card`/`image`/`file`/`sticker`。本文を直すと`edited_at`と`edit_history`（取り消し線用） |
| `chat_read_states` | 既読位置。未読バッジと既読表示に使う |
| `chat_message_reactions` | リアクション。`(message_id, user_id, emoji)` |
| `chat_private_notes` | 個人メモ（送信されない、本人限定） |
| `chat_keep_items` | Keepメモ（ルーム横断、本人限定） |
| `chat_albums` / `chat_album_items` | アルバムとその収録画像 |
| `chat_stickers` | 感情イラストのID・表示名・パス・並び順・カテゴリ・有効状態 |
| `chat_scheduled_messages` | 予約送信。本人だけが見て取り消せる |
| `chat_push_subscriptions` | Web Pushの購読 |
| `chat_push_user_preferences` | 通知ON/OFFとプレビュー可否 |
| `chat_push_dispatches` | 同一メッセージの重複送信防止 |
| `chat_push_internal_config` | cron／pg_netから`chat-push`/`chat-knowledge`を叩くための内部シークレット |
| `chat_admin_audit_log` | M-talk管理画面から行った利用・権限変更の監査ログ |

### 発言の種別（`kind`と`payload`）

`content`にはどの種別でもプレーンテキスト版を入れる（トーク一覧のプレビューと
Web Pushの本文はこれを見るため、`payload`が読めなくても表示が壊れない）。

| kind | payload | 誰が作れるか |
| --- | --- | --- |
| `text` | なし | 全員 |
| `image` | `{v,kind,image:{path,w,h}}` | 全員。ただしトリガが作り直す |
| `file` | `{v,kind,file:{path,name,mime,size}}` | 全員。パスは送信先グループ配下限定 |
| `sticker` | `{v,kind,sticker:{id,label,path,display}}` | 全員。有効な`chat_stickers.id`だけをトリガが台帳から再構成 |
| `card` | `{v,kind,cards:[{header,sections,action(s)}]}` | `service_role`のみ |

`chat_set_message_author`トリガが`auth.uid()`の有無で振り分ける。ブラウザからの
insertは必ず`text`/`image`/`file`/`sticker`になり、`card`を詐称できない。

### 添付ファイルの検証

3層で検証する。ブラウザ（MIME＋拡張子＋サイズ）、Storageバケットの許可MIMEリストと
上限、DBトリガ（MIME再検証・保存先が送信先グループ配下か・ファイル名を
`[^A-Za-z0-9._() -]` → `_`へ正規化）。

## 21. Realtime購読

`chat-global`チャンネルで購読する。RLSがそのまま効くため、未参加グループの新着は
配信自体されない。

- `chat_messages` INSERT / UPDATE / DELETE
- `chat_groups` INSERT
- `chat_group_members` INSERT / UPDATE（本人のルーム権限変更） / DELETE
- `chat_user_access` UPDATE（本人の全体利用状態変更）
- `chat_message_reactions` すべて
- `chat_read_states` すべて
- `chat_private_notes` INSERT / DELETE（本人分のみ、他端末・他タブ同期用）

## 22. 設計上の割り切り・既知の制限

- **他人の発言は削除も編集もできない**。自分のテキストは「…」→「編集」で直せる。
  画像・ファイル・カード・大きく送ったスタンプは編集できない。
- 検索から途中へジャンプしているあいだに新着が来たら、間の発言を読み足して穴を埋める。
  見ていた位置は維持し、下端へは自動では飛ばない。「最新へ」で最下部へ移動できる。
- 一覧の未参加グループは招待リンクを貼って参加する。リンク無しの直接参加はしない。
- ルームの完全削除はクライアントの直接DELETEではなく`admin-api`経由（監査ログと
  権限再検証を一箇所に集約するため）。

## 23. 動作確認チェックリスト

1. 停止・論理削除されたユーザーの既存JWTでもM-talkを利用できない。
2. 未参加または閲覧不可のグループの本文が読めない。
3. 画像の署名URLが期限切れ後に作り直される。
4. 他グループのパスを指定した画像投稿が弾かれる。
5. 他ルームの発言を返信先に指定できない。
6. メンションに非参加者を混ぜても保存されない。
7. リアクションを他人の分として付けられない。
8. 通知ONのまま購読が消えた端末で再開バーが出て、タップ後に新しい購読が保存される。
9. Service Worker更新後も登録URLが`chat-sw.js`のままで、通知配信がHTTP 410にならない。
10. 正常な購読がある状態で画面をタップしてもendpointが増えない。
11. 通知テストが現在のendpoint1件だけへ送られ、他端末・他ユーザーへ送られない。
12. 個人メモ・Keepメモ・アルバムのいずれも、他の参加者・Bot・管理画面・Web Pushに
    表示・送信されない。
13. ゴミ箱のルームには送信・画像添付・予約配信・スタンプ送信のいずれもできない。
14. 完全削除はルーム作成者以外は実行できず、ルーム名の再入力が一致しないと止まる。
