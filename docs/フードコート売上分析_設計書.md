# 東京ドーム フードコート 売上分析 設計書

11店舗 × 天気 × イベント 統合分析フレームワーク
対象：日次・店舗別データ（売上・客数・客単価あり）。本書は分析考察（AI考察＋画面の自動考察）の正本フレームワーク。

> 元は `東京ドーム_フードコート_売上分析_設計書.docx`。実装（[foodcourt_compare.ts](../supabase/functions/_shared/foodcourt_compare.ts) のAI考察、[foodcourt.html](../foodcourt.html) の自動考察）はこの設計書に沿わせる。

## 1. 分析の目的
1. 売上予測：天気・イベントから日次／店舗別売上を見通し、仕入・人員配置に活かす。
2. 要因分析：何が売上を動かしているか（天気・イベント・曜日等）を定量的に特定する。
3. 店舗間比較：11店舗の強み弱み・客層差・食い合いを明らかにする。
4. メニュー・価格最適化：条件別に売れる商品・価格帯を把握し改善する。

## 2. 分析の土台：売上の分解（最重要）
出発点は **売上＝客数 × 客単価** という恒等式。売上が増減したら、それが「客数が増えたため」か「客単価が上がったため」かを**必ず切り分ける**（怠ると打ち手＝集客強化か単価向上かを誤る）。

- 客数 ＝ ドーム/施設の来館者数 × フードコート立寄率（捕捉率）
- 客単価 ＝ 1人あたり購入点数 × 平均商品単価

増減の寄与分解（近似）: ΔSales ≒ Δ客数 × 客単価 ＋ Δ客単価 × 客数 ＋ 交互作用。

## 3. 分析対象データ（手元）
- 粒度：日次 × 店舗別（全11店舗）
- 指標：売上 / 客数 / 客単価
- 外部データ（イベント・気象・カレンダー・施設催事）を「日付」キーで結合し説明変数にする。

## 4. 分析要素（説明変数）
- **A. ドームイベント**（最大の売上ドライバー）: 有無・種別（野球/ライブ/展示）。野球＝主催有無・対戦相手・デー/ナイター・動員数・勝敗・延長（人気カードで動員差、客層はファミリー〜中年男性）。ライブ＝アーティスト・動員・客層・開演/終演・連日（客層で飲食単価が変動、若年女性公演は単価傾向が異なる）。
- **B. 天気・気象**: 最高/最低/平均気温・体感・湿度（高温→冷製/飲料/アイス、低温→温麺/スープ）。降水量・降水有無・猛暑日/真夏日/冬日（雨は屋外客減、ドーム内イベント客は影響小）。
- **C. カレンダー**: 曜日・週末平日・祝日・連休・学校休暇（連休/長期休暇でファミリー比率上昇）。
- **D. ドームシティ全体**: カナデビアホール・後楽園ホール・プリズムホール・ラクーア等の同時催事（ドーム本体が無イベントでも独立した来館動機）。
- **E. 店舗・商品内**: メニュー構成・価格帯・提供速度・立地（動線）・行列・欠品・営業時間。
- **F. 店舗間相互作用**: カニバリ（食い合い）・アンカー効果・業態カテゴリ。
- **G. マクロ・その他**: インバウンド・近隣競合・価格改定・キャンペーン。

規模感（事実）: 野球時 約43,500人、コンサート等 最大約55,000人。年間稼働率 約87%（うち野球 約4割）。無イベント日は少なく、**イベント種別の違いが主変動要因**。

## 5. さらに加えるべき分析視点
- 売上の要因分解：増減を「客数要因」と「客単価要因」に必ず分ける。
- トレンド／季節分離：移動平均・前年同曜日比で基調と季節・曜日効果を切り離す。
- 交互作用：雨×イベント有無、猛暑×デザート店 など組み合わせ効果。
- ラグ・リード効果：前日のイベント、翌日が連休か、前売り完売の事前情報など時間差。
- イベント客層別の単価感度：野球（ファミリー〜中年男性）と女性中心ライブで単価傾向が異なる。
- フードコート捕捉率：推定来館者数に対する利用率（取りこぼしの可視化）。
- 価格弾力性・天気弾力性：価格や気温が1単位動くと売上がどれだけ動くか。
- 異常値検出：記録的動員日・台風など外れ値を切り分け、平常分析を歪めない。
- 時間帯×イベントのピーク設計（時間帯データ取得時）。

## 6. KPI・計算式
| 指標 | 計算式 | 用途 |
|---|---|---|
| 売上構成比 | 店舗売上 ÷ FC総売上 | 貢献度・ABC分析 |
| 客単価 | 売上 ÷ 客数 | 単価ドライバー |
| 平均購入点数(PI値) | 販売点数 ÷ 客数 | 点数増か単価増かの切り分け（点数要） |
| フードコート捕捉率 | FC総客数 ÷ 推定来館者数 | 集客取り込み度 |
| 店舗シェア | 店舗客数 ÷ FC総客数 | 客の取り合い |
| 前年同曜日比(YoY) | 当日 ÷ 前年同月同曜日 − 1 | 季節・曜日を揃えた成長率 |
| 移動平均(7/28日) | 直近N日の平均 | トレンド抽出 |
| 曜日指数 | 各曜日平均 ÷ 全日平均 | 曜日の強弱 |
| 月別季節指数 | 各月平均 ÷ 年平均 | 季節成分 |
| イベントリフト | イベント日平均 ÷ 無イベント日平均 − 1 | イベント押し上げ効果 |
| カード別/会場別リフト | 該当条件平均 ÷ 基準平均 − 1 | 条件ごとの効果差 |
| 雨日リフト | 雨日平均 ÷ 晴日平均 − 1 | 降水の影響度 |
| 気温弾力性 | 回帰係数(売上〜気温) | 気温1℃あたりの売上変化 |
| 価格弾力性 | %Δ数量 ÷ %Δ価格 | 値付け判断（点数要） |
| 店舗間相関 | 日次売上のピアソン相関 | 正＝連動/アンカー、負＝食い合い(カニバリ) |
| 異常値Zスコア | (当日 − 移動平均) ÷ 移動標準偏差 | \|Z\|>2.5 を外れ値候補 |

弾力性は厳密には他要因統制の回帰係数で求める（単純な比は目安）。捕捉率の推定来館者数はドーム動員＋各ホール催事の推定動員の合算。

## 7. 分析の進め方（STEP）
0. データ準備・品質チェック（日付キー結合、欠損/休業/重複/税込税抜、外れ値フラグ）
1. 記述統計・可視化（推移・分布・店舗構成比＝ABC）
2. 売上の要因分解（客数要因 vs 客単価要因）
3. トレンド・季節・曜日の分離（移動平均・曜日指数・月別季節指数・YoY）
4. 単変量の影響（イベント有無・天気区分・曜日の群間比較・相関）
5. 多変量モデル（重回帰で係数、GBDTで特徴量重要度・非線形/交互作用）
6. イベント・会場の深掘り（カード別/デー・ナイター別/会場別/客層別のリフト・捕捉率・客単価）
7. 天気感応度・弾力性（気温帯ビン別の業態別売上、雨日リフト、気温・価格弾力性）
8. 店舗間比較・カニバリ（売上相関で負＝カニバリ、正＝アンカー）
9. 予測モデルの構築・検証（時系列分割、MAPE、過学習/異常日）
10. 打ち手への落とし込み（仕入量・人員シフト・メニュー/価格）

## 8. 検証すべき仮説（例）
- 人気カード（巨人×阪神等）は他カードより総売上・客数が高い → カード別群間比較。
- ナイターはディナー帯売上を押し上げる → デー/ナイター別比較。
- 女性中心ライブはデザート/ドリンク/カフェの客単価を上げる → 会場×客層×業態。
- 格闘技（後楽園・カナデビア）はアルコール・軽食が伸びる → 会場別リフト。
- 真夏日は冷菓・ドリンクが伸び温麺が落ちる → 気温帯×業態。
- 雨天は屋内回遊増でFC捕捉率が上がる → 雨日/晴日で捕捉率比較。
- 麺類店同士は食い合う（負相関）/ 人気アンカー店の行列日は周辺店も底上げ。
- 天気＋イベント＋曜日で日次売上の大半を説明できる → 重回帰/GBDTの決定係数。

各仮説は「支持／不支持／条件付き」で判定し、効果量（リフト率・係数）を数値で添える。**相関と因果は区別**し、因果を主張する前に他要因を統制（回帰・層別）する。

## 9. 11店舗の業態分類（カニバリ分析用）
和食/丼・麺類（ラーメン/うどん）・洋食/鉄板・カレー/アジア・軽食/ファストフード・ベーカリー・スイーツ/デザート・カフェ/ドリンク・アイス/冷菓・居酒屋/アルコール 等に分類。同カテゴリ＝食い合い（カニバリ）、人気店＝アンカー効果（全体底上げ）の観点で関係を見る。実店舗プロファイルは [フードコート競合店プロファイル.md](フードコート競合店プロファイル.md) を正本とする。

## 10〜12. データ整備・手法・入手先
- 整備：売上テーブル（日次×店舗）を主表に、イベント/気象/カレンダー/施設催事を日付キーで結合、カテゴリ変数はダミー化、欠損/休業/外れ値にフラグ。
- 手法：記述統計・相関 → 要因分解 → 重回帰/GLM → 決定木/GBDT → 時系列（季節調整/SARIMA）。
- 入手先：気象庁（東京地点の日別 気温/降水/湿度）、東京ドーム公式イベントカレンダー、ドームシティ各会場の開催情報、内閣府の祝日データ・学校暦。

## 13. 統合 分析プロンプト（AI考察の指針）
売上＝客数×客単価を基本構造とし、増減をまず客数要因/客単価要因に分解。
1. 全体傾向：移動平均と前年同曜日比でトレンド・季節・曜日効果を分離。
2. 要因分析：イベント有無/種別・天気・曜日/祝日の影響を定量化（相関→重回帰/GBDTで重要度）。
3. イベント深掘り：野球の対戦カード別・デー/ナイター別、ライブの客層別にFC捕捉率（売上÷推定来館者数）と客単価を比較。
4. 天気感応度：気温帯別・降水有無別の売上と商品傾向、気温×売上の弾力性。
5. 店舗間比較：11店舗を業態分類し、強み弱み・客層差・カニバリ/アンカーを特定。
6. 交互作用：雨×イベント、猛暑×デザート店 などの組み合わせ効果。
7. 異常値：記録的動員・悪天候など外れ値を検出し要因を注記。

出力：各分析に結論（数値根拠つき1〜3行）／予測に効く要因の重要度ランキング／店舗別の打ち手（仕入・人員・メニュー/価格）／前提・データ限界・追加取得すべきデータ。推測ではなくデータに基づき、相関と因果を区別する。

## 14. 実装アーキテクチャ（AI考察の実装方式・2026-07-03〜）

「データに質問」(Q&A) と「分析サマリー（自動）」は、いずれも[foodcourt_compare.ts](../supabase/functions/_shared/foodcourt_compare.ts)の**専門AI2体並列＋統合AI**構成で実装している。単一のGroq呼び出しに11項目の分析フレームワーク（本書の§13等）を全部詰め込むと考察が浅く・毎回同じ言い回しになりやすいため、役割を分割した。

### 14.1 共通パイプライン

```
専門AI①(他店舗比較・過去データ分析)  ─┐
                                     ├→ 統合AI(1本の最終回答/サマリーにまとめる)
専門AI②(東京ドームイベント・天気分析) ─┘
```

- 2体の専門AIは`Promise.all`で並列実行（専門AI①＝Groq `openai/gpt-oss-120b`、失敗時は Gemini へフォールバック）。
- 相関・要因分解・異常値Zスコア・競合プロファイル等の**数値はすべてコード側で事前計算**し、専門AI・統合AIには「意味づけ」だけを担わせる（AIに数字を作らせない）。
- コスト・レイテンシは単一呼び出しの3倍程度（体感+数秒〜10秒）。

### 14.2 Q&A（`answerFoodCourtQuestion`）

- エンドポイント: `POST /foodcourt/ask`（admin-api）。呼ばれるたびにGroq課金・生成（自動出力キャッシュなし）。
- **画面表示中の対象日のグラウンディング**: フロント([foodcourt.html](../foodcourt.html))が現在表示中の単日レポートを`currentViewedReport`として追跡し、質問のたび`viewing_report_id`を送信。バックエンドは`fcSalesDate()`で実売上日に変換し、専門AI・統合AIすべてのプロンプト最優先位置に「画面表示中の対象日=◯◯」を明示する。これが無いと、AIは最大45日分の生データから話す日を自分で推測し、時間軸がずれた回答をすることがあった（2026-07-03 修正、詳細は[店舗運用修正記録.md](店舗運用修正記録.md)）。
- 会話履歴(最大8件)を渡し、指示語（「その店」「もっと詳しく」等）に対応。

### 14.3 分析サマリー（自動）（`generateFoodCourtDailySummary`）

- エンドポイント: `GET /foodcourt/daily-summary`。`foodcourt_daily_ai_summary`テーブルに`report_id`単位でキャッシュし、**1日1回だけ生成**（閲覧のたびに再生成・再課金しない）。フロントは瞬時にJSテンプレート版(`buildAnalysisText`)を表示→裏でAI版を取得できたら差し替え（失敗時は退行なしでテンプレートのまま）。
- 対象日固有の事実（FC内順位・シェア・自店史比較・客数/客単価要因分解・イベント/天気・直近推移）は`buildTargetDayFacts`が算出。統合AIの出力は画面が期待する固定7見出し(【総評】【売上】【客数】【客単価】【競合環境】【この日の評価（条件別）】【直近の勢い】)を厳守させる。
- **前回分析の自己検証**: 直近1営業日分のキャッシュ済みサマリーを「前回の分析」として渡し、そこで語った見立てが今回の実績でも裏付けられたか／変わったかを一言検証させ、同じ結論の繰り返しを避ける。

### 14.4 統計的パターン（`buildConditionPatternStats`）— 反復学習の位置づけ

日々の分析から「傾向」を蓄積させたいという要望に対し、当初はLLMが自由文で「蓄積知見メモ」を書き換える方式を試作したが、AIの主観判断に確度評価を委ねることになりMAPE(来客予測モデルの自己採点)のような客観性が無いため撤去した。

代わりに`buildConditionPatternStats`が、`reports`から**毎回**「曜日別」「東京ドームイベント種別別」「天気別」の平均・サンプル数n・変動係数CVを計算し直す（状態を持たない・[フードコート来客予測モデル.md](フードコート来客予測モデル.md)の`fit()`と同じ発想）。AIの役割は、対象日に同時に成立する複数条件（曜日×イベント×天気）がどう重なって効いたかを、確度（nの大小）を踏まえて**多角的に解釈すること**に限定し、確度判定そのものはコードに担わせている。データが増えるほど自動的に確度が上がる点は来客予測モデルと同じ設計思想。
