# フードコート 来客予測 学習システム システム構造

MARUGO S（東京ドーム内フードホール「FOOD STADIUM TOKYO」）の来客数・売上を予測する「自己再学習型」システムの全体構造。
データ収集 → 蓄積 → 特徴量化 → 学習 → 予測 → 出力 → 再学習 のループで、**データが貯まるほど精度が上がる**。
初版: 2026-06-24。2026-07-07更新: ポアソン回帰GLM＋モデル自動選択ループ・予想動員数の手入力を追加。
関連: [フードコート来客予測モデル.md](フードコート来客予測モデル.md)（モデル詳細）、[フードコートAIループシステム全体解説.md](フードコートAIループシステム全体解説.md)（2つのループの全体像）、[フードコート売上分析_設計書.md](フードコート売上分析_設計書.md)（分析フレームワーク）。

## 1. 全体構成（データフロー）

```
[LINEで画像送信]                [毎日 cron で自動取得]
 テナント一覧画像                 ┌─ tokyo-dome-events-cron (JST04:10) ─→ tokyo_dome_events(3会場)
   │                             └─ weather-daily-cron      (日次)      ─→ weather_daily
   ▼
 line-webhook
  └ maybeHandleFoodCourtReport
     └ Groq/Gemini で表をJSON抽出
        └ saveFoodCourtReport
           ▼
 foodcourt_tenant_reports ──(DBトリガー sync_foodcourt_daily_facts)──▶ foodcourt_daily_facts
   (アップロード原本)                                                  (日次×11テナント＝学習データ本体)
                                                                          │
                  tokyo_dome_events ┐                                     │
                  weather_daily     ┼──(view)──▶ foodcourt_daily_features ◀┘   ← 日付ごとに「実績＋イベント＋天気＋曜日」を1行に
                  (カレンダー)      ┘                    │
                                                         ▼
                           foodcourt-forecast-cron (JST05:00) ＝ 学習エンジン
                             ①-A fit()    乗算モデル: 全実績から係数を学習し直す
                             ①-B fitGLM() ポアソン回帰: 曜日+イベント+天気+log(1+動員数)+トレンド
                                          （リッジ強度λは候補{1,2,4,8,16}をバックテストで自動選択）
                             ② backtest   拡張窓で両モデルを out-of-sample MAPE で自己採点
                             ③ 選択       MAPEが小さい方を今晩の採用モデルに決定（モデル選択ループ）
                             ④ predict    採用モデルで当日〜+14日を予測
                                                         ▼
                                          forecast_predictions (予測＋区間＋実績＋model_version=採用モデル)
                                                         │
                        ┌────────────────────────────────┼───────────────────────────┐
                        ▼                                ▼                             ▼
            foodcourt.html「🔮来客予測」カード   admin-api /foodcourt/reports     AI考察(answerFoodCourtQuestion)
              (精度＝直近誤差%＋今後14日)          応答に forecast 同梱            予測＋自己採点を文脈に投入
```

「実績(actual)が後日入る → 翌朝の fit() に取り込まれて係数が更新される」が**学習ループ**。

## 2. レイヤ別の構造

### 2-1. データ収集層（Ingestion）
| 入力 | 経路 | 保存先 | タイミング |
|---|---|---|---|
| テナント一覧画像 | line-webhook → `maybeHandleFoodCourtReport`（Groq→Gemini で表をJSON抽出）→ `saveFoodCourtReport` | `foodcourt_tenant_reports` | LINE送信のたび |
| 東京ドーム＋カナデビア＋後楽園のイベント | `tokyo-dome-events-cron`（公式HTMLを確定パース。本体＝テキスト解析、各ホール＝`parseDomeCityHallCalendar`） | `tokyo_dome_events`（venue付き） | 毎日 JST 04:10 |
| 天気（過去＋予報） | `weather-daily-cron`（Open-Meteo） | `weather_daily` | 日次 |

- 売上日の確定: テナント一覧は「翌朝発行の前日比較表」。`report_date`＝受信日(JST)を保存時に自動設定し、**売上日＝report_date−1**。
- 冪等: reports は `line_message_id` 一意、events は `(event_date,venue,title)` 一意、weather は `(weather_date,location)` 一意。

### 2-2. 蓄積・正規化層（Storage）
- `foodcourt_tenant_reports`（原本JSON）→ **DBトリガー `sync_foodcourt_daily_facts`** が発火し、`foodcourt_daily_facts`（日次×11テナント、`business_date=report_date−1`）へ自動正規化。
- → アプリ改修なしで「学習データ」が常に最新。`is_base=true` が基準店 MARUGO S（予測の教師データ）。

### 2-3. 特徴量層（Features）
- view `foodcourt_daily_features`（保存せず都度合成）。1日1行で:
  - 曜日(iso_dow)・週末フラグ、イベント有無/種別(has_pro_baseball/has_live/has_event)・件数、予想動員(max_expected_attendance)、天気(weather_code/temp_max/min/precipitation/is_rainy)。
- **予想動員数は手入力**: 公開データが無いため、[foodcourt.html](../foodcourt.html) のイベント一覧「👥予想」欄から入力（admin-api `PUT /foodcourt/events/attendance` → `tokyo_dome_events.expected_attendance`）。入力が貯まるほどGLMの精度が上がる。
- 過去日＝学習入力、未来日＝予測入力（events/weather予報があるため未来も特徴量が揃う）。

### 2-4. 学習・予測層（Learning Engine）— 2モデル＋自動選択
- `foodcourt-forecast-cron`（毎日 JST05:00）。2つのモデルを毎晩バックテストで競わせ、良い方を採用する:
  - **A) 乗算モデル `fit()`/`predict()`** … `予測客数 = ベース客数 × 曜日係数 × イベント種別係数 × 天気係数`、各係数＝「その条件の平均 ÷ 全体平均」。少数サンプルは `shrink()`（K=4）で1へ収縮。AI解説用の係数は常にこちら（解釈しやすい倍率の形）。
  - **B) ポアソン回帰GLM `fitGLM()`/`predictGLMGuests()`** … `log(客数) = 切片+曜日+イベント種別+天気+log(1+予想動員数)+トレンド(経過日数)` をIRLSで最尤推定。リッジ正則化の強さλは候補{1,2,4,8,16}をバックテストして自動選択。動員数（連続値）とトレンド（開店後の伸び）を扱える。
  - **拡張窓バックテスト** … 各過去日を「それより前のデータだけ」で学習→予測し、A/B両方の out-of-sample MAPE を算出。**guestsのMAPEが小さい方をその晩の本番予測に採用**（＝モデル選択ループ）。売上＝予測客数 × 中央客単価。予測区間は採用モデルの誤差幅。
- model_version = `mult-factor-v1`（レガシー採用時）または `glm-poisson-v1(lambda=N)`（GLM採用時）。勝敗は `foodcourt_forecast_factors.model_selection` と `foodcourt_forecast_history` に記録。

### 2-5. 出力・活用層（Serving）
| 出力 | 実装 |
|---|---|
| 予測の保存 | `forecast_predictions`（target_date, metric=guests/sales, predicted/low/high, actual, model_version, features） |
| 画面表示 | [foodcourt.html](../foodcourt.html) 「🔮 来客予測（学習型）」カード（精度＝直近誤差%＋今後14日の予測客数・売上） |
| API | admin-api `/foodcourt/reports` 応答に `forecast` 同梱（`loadForecastForStore`・marugoSのみ） |
| AI考察 | [foodcourt_compare.ts](../supabase/functions/_shared/foodcourt_compare.ts) `answerFoodCourtQuestion` に予測＋自己採点を投入（`buildForecastContext`）。仕入・人員助言に利用、誤差大なら参考値と断る。 |

## 3. 学習ループ（なぜ貯まるほど賢くなるか）

```
①蓄積: 毎日アップロード/取得/手入力で facts・events(動員数)・weather が増える
   ▼
②学習: 毎晩、乗算モデルとGLMの両方が「全データ」で係数を計算し直す（固定値ではない）
   ▼
③選択: 両モデルをバックテストし、誤差(MAPE)が小さい方を今晩の採用モデルに決定
   ▼
④予測: 採用モデルで当日〜+14日を forecast_predictions に保存
   ▼
⑤観測: その日が来たら実績(actual)が facts に入る → ②へ戻る
```
- 係数はデータ由来で毎日更新 → 新実績が自動反映。
- `shrink`（乗算モデル）/ リッジλの自動選択（GLM）により、データが増えるほどパターンを強く信頼。
- ③の自動選択が「誤差実績が次の予測方法そのものを変える」**閉じたループ**。人間がモデルを切り替える判断をしなくてよい。
- バックテスト MAPE が下がっていく／GLMが勝ち始めるのが「賢くなった」証拠（[foodcourt-evolution.html](../foodcourt-evolution.html) で確認）。

## 6. セキュリティ・運用の鉄則
- 新規テーブルは **RLS有効・ポリシー無し（service_role専用）**。
- SECURITY DEFINER 関数（トリガー・cron invoke）は **anon/authenticated の EXECUTE を剥奪**（RLSバイパス防止）。
- 新規関数は `set search_path = public`。Edge Functions は main push で自動デプロイ、DDLは migration 経由（GitHub統合が自動適用）。
- 点検: 予測は `?dry_run=1` で学習結果(係数)・MAPE・予測を非破壊確認。

## 7. 現状
- 2026-06-24（初回）: 学習15日・MAPE 客数±36%／売上±45%。
- 2026-07-07（GLM＋モデル選択ループ導入時）: 学習40日・バックテスト36日。レガシー52.6% vs GLM59.7%で**レガシーを自動採用**（動員数が未入力のためGLMの強みが出ていない＝想定どおりの初期状態）。
- 学習の伸びしろは「**毎日テナント一覧をアップロードし続ける**」＋「**イベントの予想動員数を入力する**」の2つに直結。

## 8. 限界・次段階（精度を上げる順）
1. ~~動員数(expected_attendance)の取込~~ → **2026-07-07対応済み**（手入力UI＋GLMの`log(1+動員数)`項）。あとは入力の運用継続。
2. **会場×客層別**の係数（東京ドーム/カナデビア/後楽園、野球/ライブ/格闘技で来店動機が違う）。
3. **客単価のイベント別**化（女性中心ライブ＝デザート/ドリンクで単価変動 等）。
4. **GLMへの交互作用項**（曜日×イベント種別）→ その先にフェーズ2: 勾配ブースティング(GBDT)で非線形。
5. 季節性（月別指数）・前年同曜日比（1年蓄積後）。
