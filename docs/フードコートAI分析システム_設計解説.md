## 1. システム全体の設計思想

### 1-1. 解決した3つの問題

| 問題 | 原因 | 解決策 |
|---|---|---|
| 「毎回同じことしか言わない」 | 1つのAIが全てを担当 → 平均的な言い回しになる | 役割分担（専門AI×3→反証AI→統合AI） |
| 「数字を言い換えるだけで中身がない」 | AIが数字を生成するため、正確さより流暢さを優先 | **コードが全ての数値を事前計算**、AIには解釈だけさせる |
| 「予測モデルとAI解説が矛盾する」 | 数値予測モデルとAI解説が別々の統計を使っていた | 予測モデルの学習係数をDBに保存し、AI解説も同じ係数を参照（1本化） |

### 1-2. 基本原則

- **AIは数字を作らない**: 売上・客数・順位・比率はすべてコード（TypeScript）が計算し、AIにテキストで渡す
- **役割分担で深度を上げる**: 各専門AIが担当領域のみを深掘りし、統合AIが矛盾を解消する
- **反証ファースト**: 専門AIの主張を別AIが批判的にレビューしてから統合する（品質ゲート）
- **異なる知識・異なる思考回路を持つAIを意図的に組み合わせる**: 同じAIを複数役に使うと「癖」が共通し盲点も共通する。各役割に最適なプロバイダーを選ぶことで視点の多様性を確保する

## 2. 3専門AIの「知識の違い」が分析の核心

最も重要な設計判断は、**専門AI①②③をすべて異なるプロバイダー・モデルで構成している**ことである。

### なぜ同じAIを複数役に使ってはいけないか

同じモデルに「数値分析」と「運営改善」を別々に依頼しても、同じ学習データ・同じ思考の癖から生まれた回答が出てくる。専門性を偽装しているだけで、実態は1つのAIが2役を演じているに過ぎない。

### 3つの専門AIが持つ「異なる知識の種類」

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    3専門AIの知識領域の違い                               │
├─────────────────┬───────────────────┬──────────────────────────────────┤
│ 専門AI①         │ 専門AI②           │ 専門AI③                         │
│ Groq             │ Gemini            │ Grok (xAI)                       │
│ gpt-oss-120b     │ gemini-3.5-flash  │ grok-3-mini                      │
├─────────────────┼───────────────────┼──────────────────────────────────┤
│ 【強みの知識】   │ 【強みの知識】     │ 【強みの知識】                   │
│                  │                   │                                  │
│ 数値・統計的     │ 世界の出来事・      │ 現場で明日打てる打ち手の具体化    │
│ パターン分析     │ エンタメ・人物      │ （Chat Completions。X検索なし）  │
│                  │ に関する広範な      │                                  │
│ 「この数字は     │ 知識               │ ※最新のX話題は別経路の            │
│ 統計的に         │                   │  Xトレンドブリーフ（x_search）    │
│ 何を意味するか」 │ 「NiziUとは        │  が担当する                       │
│ を推論           │ どんな客層が       │                                  │
│                  │ 来るアーティスト   │                                  │
│ ← 数値分析・    │ か」を知っている   │ ← 運営改善（打ち手提案）に最適   │
│ 他店舗比較に最適 │                   │                                  │
```

### 具体的な分析例：同じ「野球の日」をどう読むか

**専門AI①（Groq）の視点 — データから読む:**
> 「プロ野球（ドーム本体）の日の学習係数は×1.89（n=6）で再現性あり。今日の実績は係数予測を7%下回っており、天気（雨）の係数×0.88が影響した可能性がある」

**専門AI②（Gemini）の視点 — イベント知識から読む:**
> 「巨人vs阪神戦は関西からの遠征ファンが多く、試合後の時間帯に小腹を満たしたい需要が特徴的。デーゲームのため13時〜15時のピーク後に夕方の谷間が生じる傾向がある」

**専門AI③（Grok）の視点 — 現在のトレンドから読む:**
> 「X上では最近の阪神ファンに『球場グルメを楽しむ』投稿が急増中。ビールよりも写真映えするサイドメニューへの関心が高い。試合終盤〜終演後30分が最大の商機で、スピード提供と見映えの両立が打ち手の軸になる」

→ **3つの視点が合わさって初めて「今日・この試合・この客層に何をすべきか」という深い分析が成立する。**

### 3-2. 並列・直列の実行順序

```
ラウンド1（並列・同時実行）: 専門AI①②③ → 約2〜4秒
      ↓
ラウンド2（直列）: 反証AI④ → 専門AI①②③の出力を受け取り批判的レビュー → 約1〜2秒
      ↓
ラウンド3（直列）: 統合AI⑤ → 全ての情報を受け取り最終出力 → 約3〜6秒
```

### 3-3. 品質評価ループ＝第6のエージェント（2026-07-07追加・2026-07-21 Q&A段階導入）

統合AI⑤の最終出力の後段に、**評価AI⑥**によるループを追加できる（AIループエンジニアリング）。

```
統合AI⑤の回答 → [評価AI⑥] 5軸採点（正確性/論理性/専門性/実用性/根拠・JSONのみ）
   → 合格（現在は総合70＋各項目65＝総合−5点の許容幅）なら返却
   → 不合格なら「改善点だけ」を統合AI⑤に渡して再生成 → 再評価
   → 上限（各surfaceとも最大2回）に達したら最高得点の回答を返す
```

- 再ループ時に専門AI①②③・反証AI④は**再実行しない**（メモを使い回し、統合AI⑤だけ再生成）＝コスト増を最小化
- 合否は評価AIの自己申告ではなくコード側が閾値判定。全ループは `foodcourt_ai_loop_runs` / `foodcourt_ai_loop_iterations` に保存
- **未設定時はOFF**。本番は `ask` のみ明示ON、`daily_summary` / `period_summary` / `weekly_report` は明示OFFで段階導入中
- 詳細な仕組み・有効化手順は [フードコートAIループシステム全体解説.md](フードコートAIループシステム全体解説.md)、設計・実装ログは [AI_LOOP_ENGINEERING_DESIGN.md](AI_LOOP_ENGINEERING_DESIGN.md) を参照

### 3-4. 現場日報データの Q&A 組み込み（2026-07-08追加）

#### 追加の背景

数値データだけでは「なぜ売上が動いたか」の因果を説明しきれない。現場スタッフが日報に記録した**施策・動員数・担当者評価・課題**をAIの分析材料に加えることで、施策効果の仮説検証が可能になる。

#### データフロー

```
[日報ページ] 施策・動員数を入力・保存
  ↓ (PUT /foodcourt/daily-logs)
  foodcourt_daily_logs テーブル

[Q&Aリクエスト]
  /foodcourt/ask ハンドラ
    ↓ 直近60日分を取得
  buildDailyLogsContext(dailyLogs)
    ↓ 日付ごとのテキストブロックに変換
  answerFoodCourtQuestion(... dailyLogs)
    ↓ opsUser プロンプト + contextBlock に注入
  AI 回答（施策と実績を照合して出力）
```

#### AI への注入内容

| 注入先 | 内容 |
|---|---|
| 運営改善専門AI (Grok) の `opsUser` | `# 現場日報・施策記録` ブロック（施策・評価・課題） |
| 統合AI の `contextBlock` | 同上（全エージェントが参照できるよう最終コンテキストにも含める） |
| 統合AIのシステム指示 **(12)** | 「施策を打った日/翌日の実績と照合せよ。担当者評価は主観なのでデータで裏取りし、整合・不整合を明示せよ」 |

#### Q&A の変化

| 以前 | 追加後 |
|---|---|
| 「7/5は客数が増えました」 | 「7/5は試食配布（14〜15時）を実施。担当者は+10組と評価しており、実績でも14〜16時の客数が前日比+18%と一致。ただしナイター客（42,000人規模）の影響と切り分けるには…」 |
| 「施策の効果は不明」 | 「7/12は声かけ強化を実施したが客数は前日比-3%。同日の動員数は30,000人でやや少なく、施策効果よりイベント規模の影響が大きい可能性」 |

詳細は [フードコート日報システム.md](フードコート日報システム.md) を参照。

## 4. 各AIエージェントの詳細

### 専門AI① ── 数値分析・他店舗比較専門（Groq）

| 項目 | 内容 |
|---|---|
| プロバイダー | Groq |
| モデル | `openai/gpt-oss-120b`（`FOODCOURT_GROQ_MODEL`環境変数で変更可。未設定時も同モデル） |
| フォールバック | Gemini（`buildFoodCourtProviderOrder('groq')`） |
| 最大出力 | 600〜700トークン |
| 出力用途 | 統合AIへの「分析メモ（下書き）」 |

**Groq / GPT-OSS を使う理由:**
- GPT-OSS 120B は数値・統計の推論と長い入力コンテキストに適する本番安定枠
- Groqの専用ハードウェア（LPU）による超高速推論（他の2専門AIと並列実行するため速度が重要）
- **「数字と数字の関係性から意味を引き出す」という分析的思考が強み**
- 失敗時は Gemini へ退避し、専門AI①だけが全滅しないようにする

**担当する分析タスク:**
1. 客単価・順位が業態（競合プロファイル）から見て妥当か想定外かを判定
2. 真の競合（同じ来店動機・価格帯で客を奪い合う相手）を特定
3. 売上増減が「客数要因」か「客単価要因」かを要因分解データで切り分ける
4. 店舗間相関（カニバリ/アンカー）を業態文脈で解釈
5. 異常値（Zスコア）の突出日/落込日を平常と切り離して注記
6. 予測モデルの自己採点（MAPE）を踏まえた参考所見

### 専門AI② ── イベント・天気需要ドライバー専門（Gemini）

| 項目 | 内容 |
|---|---|
| プロバイダー | Google |
| モデル | `gemini-3.5-flash`（`FOODCOURT_GEMINI_MODEL`環境変数で制御） |
| フォールバック | Groq `openai/gpt-oss-120b` |
| 最大出力 | 600〜700トークン |
| 出力用途 | 統合AIへの「分析メモ（下書き）」 |

**Geminiを使う理由:**
- Googleの膨大なウェブコーパスから学習しており、**アーティスト・スポーツチーム・興行イベントに関する世界知識が非常に豊富**
- 「NiziUライブ＝若年女性中心で物販後の軽い飲食需要」「阪神ファンは関西から遠征が多い」といった、イベント×来店客層の推論に強い
- 天気・季節・地理的文脈も組み合わせた複合的な分析が得意

**担当する分析タスク:**
1. イベント種別・規模・客層から、客数・売上への影響メカニズムを説明
2. 野球（対戦相手/デーナイター）、ライブ（アーティスト/客層）、小ホール（後楽園・カナデビア）の差異を考慮
3. 天気（雨・猛暑等）とイベント有無の交互作用
4. 今後の予定イベントと想定される影響・打ち手

### 専門AI③ ── 運営改善専門（Grok / xAI）

| 項目 | 内容 |
|---|---|
| プロバイダー | xAI（Elon Musk率いるAI企業） |
| モデル | `grok-3-mini`（`FOODCOURT_GROK_MODEL`環境変数で変更可） |
| APIキー変数 | `XAI_API_KEY` |
| フォールバック | Groq `openai/gpt-oss-120b` |
| 最大出力 | 600〜700トークン |
| 出力用途 | 統合AIへの「運営改善メモ（下書き）」 |

**Grokを使う理由と、その正確な範囲（重要）:**

> **注意（2026-08 修正）**: 以前ここには「Grok 3 mini は X のリアルタイム投稿データを学習しているので、現在進行形の流行を知っている」と書かれていたが、これは誤解を招く記述だった。専門AI③ は Chat Completions (`/v1/chat/completions`) 経由で呼ばれており、この経路は関数ツールしか受け付けず **`x_search` が使えない＝X を一切検索していない**。学習データにはカットオフがあるため、この経路だけでは「今週の話題」は原理的に取得できない。

現在は役割を2つに分離している:

| 役割 | 経路 | 実際にやっていること |
|---|---|---|
| 専門AI③（運営改善メモ） | Chat Completions + `grok-3-mini` | 学習済み知識＋渡されたデータで打ち手を書く（X検索なし） |
| Xトレンドブリーフ | **Responses API + `x_search`** + `grok-4.5` | 指定期間の X を実際に検索し、引用URL付きで返す |

X の最新トレンドは後者が担当し、その結果を統合AIの材料として渡す。検索が実行された証跡（`x_search_call` / X ドメインの引用URL）が取れない応答は破棄されるため、「検索したふり」の出力が混入しない。

| Xトレンドブリーフが取ってくるもの | 運営改善への活用 |
|---|---|
| 今話題のアーティストのファン層の反応 | 「このライブの客はどんな食を好むか」の推論 |
| スポーツチームのファンの当日の話題 | 「試合後の行動パターン・消費傾向」の予測 |
| 直近の食トレンド・SNS映えの傾向 | 「今どんな見せ方をすれば刺さるか」の提案 |
| 話題になっているキャンペーン・演出事例 | 現場で明日から使えるアイデアの引き出し |

いずれも**外部知見であり売上の根拠には使わない**。統合AIには出所を明示して書くよう指示している。

**MARUGO S固有データとの組み合わせが強い:**
コードから渡す「学習係数・予測・競合データ」がGrokをMAROUGO Sの現実に接地させる一方、Grokのトレンド知識が「その数字の背景にある客の心理・行動」を補完する。両者は競合しない。

**担当する分析タスク:**
1. 明日から現場で試せる打ち手のみを出力（数値分析・イベント分析の断定は行わない）
2. 仕込み量・人員配置・ピーク対応・声かけ・セット提案・商品の見せ方

**厳守ルール:**
- データにない販売点数・原価・スタッフ人数は作らない
- 打ち手には必ず「狙う客層/来店動機」「実施条件」「見るべきKPI」をセットで付ける

### 反証AI④ ── 品質管理・反証専門（Claude）

| 項目 | 内容 |
|---|---|
| 全 surface（Q&A・日次・期間・週次） | Claude `claude-haiku-4-5` → Gemini → Groq |
| モデル設定 | `FOODCOURT_CLAUDE_MODEL` / `CLAUDE_MODEL`（既定 `claude-haiku-4-5`） |
| APIキー変数 | `claude_haiku` / `CLAUDE_HAIKU` / `ANTHROPIC_API_KEY` |
| 最大出力 | 550〜650トークン（日次は timeout 15秒、他 surface は 25秒） |
| 出力用途 | 統合AIへの「反証メモ」 |

**Claude Haiku を全 surface で使う理由:**
- 言い過ぎ・因果断定・日付ずれの検出に、Anthropic API の Claude Haiku を統一する。
- 日次は定型の単日サマリーのため timeout を短めに、Q&A・期間・週次はコンテキストが厚いため timeout を長めにする。
- 評価AI⑥も Claude Haiku のため、反証と採点の基準が揃う。
- 反証メモは統合AIへの編集指示であり、最終回答そのものではない。

**担当する分析タスク:**
専門AI①②③のメモに含まれる以下の問題を検出する:
- 言い過ぎ（弱いデータからの過剰な断定）
- 根拠不足（データなしの主張）
- 相関と因果の混同（「Aの日は売上が高いから→Aが原因」）
- 対象日/期間の取り違え
- データにない数字の混入（捏造）

**出力形式:**
```
採用してよい主張: 〜〜（根拠が明確なもの）
弱めるべき主張: 〜〜（断定→仮説に変えるべきもの）
禁止すべき断定: 〜〜（データに根拠がないもの）
```

### 統合AI⑤ ── 最終回答生成（OpenAI）

| 項目 | 内容 |
|---|---|
| プロバイダー | OpenAI |
| モデル | `gpt-5.6-luna`（`FOODCOURT_OPENAI_MODEL`環境変数で制御） |

**GPT-5.6 Lunaを使う理由:**
- 複数の専門AIメモと反証メモを統合する推論・編集タスクに対応
- 反証AI④が禁止した断定を「仮説」「データ不足」へ言い換える編集判断を担う
- 公式単価が入力$1・出力$6/1Mトークンで、従来のo4-miniとほぼ同等コスト
- 品質ループの初回生成と改善再生成で同じモデルを使い、モデル切替による品質低下を防ぐ

**担当するタスク:**
1. 専門AI①②③のメモと反証AI④の指摘を受け取り、矛盾を解消
2. 反証メモで「禁止された断定」を使わず「仮説」「データ不足」と言い換える
3. 7見出し構造（日次・期間サマリー）またはQ&A回答として整形

## 6. 3つの分析モード

### 6-1. 日次サマリー（`generateFoodCourtDailySummary`）

特定の1日のレポートを対象とした自動生成サマリー。

**出力フォーマット（固定7見出し）:**
```
【総評】 対象日の総合評価（強い/弱い/平常）+ 根拠
【売上】 売上・FC平均比・順位 + 意味づけ
【客数】 客数・FC平均比・順位 + 意味づけ
【客単価】 客単価・FC平均比 + 業態文脈での意味づけ
【競合環境】 自店の業態・真の競合・強みの説明
【この日の評価（条件別）】 自店史比・曜日比・イベント/天気の影響・要因分解
【直近の勢い】 直近推移・前回分析の自己検証・次のKPIまたは打ち手
```

**前回分析の自己検証機能:**
前回（直近1営業日）の分析テキストを`priorSummary`として統合AIに渡し、
「前回の見立てが今回の実績でも裏付けられたか、変わったかを一言検証する」よう指示する。
→ 毎日同じ言い回しにならず、連続性のある分析になる。

---

### 6-2. 期間サマリー（`generateFoodCourtPeriodSummary`）

「期間で見る」モードで任意の開始日〜終了日を選んだときに生成。

- 期間内の曜日・イベント・天気の**構成比**を踏まえた分析
- キャッシュキー: `(store_key, start_date, end_date)`

---

### 6-3. Q&A（`answerFoodCourtQuestion`）

ユーザーの自然文の質問に回答するチャット形式。

**時間軸の正確性（重要）:**
画面に表示中のレポートの対象日を`viewingDate`として全エージェントのプロンプトに注入する。
この仕組みがないと、AIは「どの日の話か」をイベントの派手さだけで判断し、時間軸がずれた回答になる。

**会話継続:** 直前8メッセージの履歴を統合AIに渡し、「その店は？」「もっと詳しく」等の指示語が機能する。

## 7. 予測モデルとの「1本化」

### 7-1. 解決: `foodcourt_forecast_factors` テーブル

`foodcourt-forecast-cron` が毎晩学習した係数を保存し、AI解説も同じ係数を参照することで矛盾を排除。

```
foodcourt_forecast_factors
  tenant_name       'MARUGO S'
  model_version     'mult-factor-v1'
  mean_guests       全体平均客数
  wday_factors      {1:月曜係数, 2:火曜係数, ..., 7:日曜係数}
  event_factors     {soccer_pv:係数, pro:係数, live:係数, ...}
  weather_factors   {rainy:係数, dry:係数}
  mape_guests       バックテスト客数誤差率
  mape_sales        バックテスト売上誤差率
```

**確度ラベルの基準:**

| サンプル数 | ラベル |
|---|---|
| n ≥ 6 | 再現性あり |
| n ≥ 3 | 参考程度（やや少数） |
| n < 3 | サンプル僅少（参考不可） |

### 7-2. 統計拡張（stats-ext-v1）── AIに「数字をどこまで信じてよいか」を渡す

2026-07-05追加。`foodcourt-forecast-cron` が毎晩、係数と一緒に5種類の統計を計算し
`foodcourt_forecast_factors.advanced_stats`（jsonb）へ保存する。
AI解説（`buildForecastFactorsContext`）はこれを読み、解釈ガイド付きテキストとして全専門AIに渡す。

**干渉させない設計（重要）:**
- 予測モデル本体（`fit()`/`predict()`）には一切手を入れていない。**予測値は従来と完全に同一**
- 統計はすべて「AIが係数を解釈するための材料」であり、予測経路と解釈経路を分離している
- 計算は cron 1箇所に集約（1本化原則）。AI側は読むだけなので二重管理が発生しない

**5つの統計と、それぞれが解決する問題:**

| 統計 | 解決する問題 | AIができるようになること |
|---|---|---|
| ① 95%信頼区間（収縮前の生係数） | 「係数×1.89」が偶然か必然か分からない | CIが1をまたぐ係数を「偶然の可能性を否定できない」と自動判定 |
| ② 条件別の四分位数・range | 平均だけでは「ブレ」が見えない | 「野球の日でも最悪54人の日がある」という下振れリスクを言える |
| ③ 交互作用（実測 vs 独立仮定） | 乗算モデルは条件の独立を仮定している | 「土日×野球は掛け算どおり伸びない（頭打ち）」を指摘できる |
| ④ 残差バイアス（条件別の系統誤差） | モデルがどの条件で外しやすいか不明 | 「小ホールの日の予測は過大評価傾向→割り引いて解釈」と自己申告 |
| ⑤ 効果量（Cohen's d） | 倍率の見かけと実際の影響力が乖離する | 「どの要因が本当に効いているか」を単位に依存せず横比較 |

**初回実行（履歴38日）で早速得られた洞察の例:**
- 土日vs平日の効果量 d=2.69（極めて大）＝**曜日がイベントより支配的な要因**
- 土日×大型イベントの実測は独立仮定の80%＝**条件が重なっても掛け算どおりには伸びない**
- 「イベント無し」係数のCIは0.21〜2.68と極端に広い（n=4）＝**ベースラインがまだ不安定**
- モデルは小ホールの日を平均+55%過大評価＝**この条件の予測は割り引くべき**

このように、統計拡張は「AIがもっともらしく言い過ぎる」ことを数値の側から抑制し、
反証AI④のチェックとは独立した第2の品質ゲートとして機能する。

### 7-3. 学習の進化トラッキング（`foodcourt_forecast_history`）

2026-07-05追加。係数テーブル（`foodcourt_forecast_factors`）は最新1行を毎晩上書きするため、
そのままでは「先月より賢くなったか」を後から証明できない。そこで毎晩の学習結果を追記保存し、
専用画面 `foodcourt-evolution.html` とAI分析文脈の両方で使う。

**追加要素:**

| 追加要素 | ファイル/テーブル | 役割 |
|---|---|---|
| 学習履歴テーブル | `foodcourt_forecast_history` | 毎晩の履歴日数・バックテスト日数・MAPE・平均客数を1日1行で保存 |
| 学習cron追記処理 | `supabase/functions/foodcourt-forecast-cron/index.ts` | `forecast_predictions` と `foodcourt_forecast_factors` 保存後に、同日の学習結果を履歴へ upsert |
| 管理API | `GET /foodcourt/evolution-history` | 履歴テーブルを日付昇順で返す |
| 専用画面 | `foodcourt-evolution.html` | KPI、MAPE学習曲線、学習データ量バー、全履歴テーブルを表示 |
| ナビ導線 | `foodcourt.html` | 「AI学習 進化」ページへのリンクを追加 |
| AI分析への反映 | `foodcourt_compare.ts` | 履歴から7日以上離れた2点を比較し、改善/悪化の根拠をAI文脈へ渡す |

**データフロー:**

```text
毎日 05:00 foodcourt-forecast-cron
  ├─ foodcourt_daily_facts + foodcourt_daily_features を読む
  ├─ fit() で曜日・イベント・天気係数を再学習
  ├─ 拡張窓バックテストで MAPE を自己採点
  ├─ forecast_predictions に予測を保存
  ├─ foodcourt_forecast_factors に最新係数を上書き保存
  └─ foodcourt_forecast_history に当日の学習結果を追記/上書き
          ↓
GET /foodcourt/evolution-history
          ↓
foodcourt-evolution.html
  ├─ KPIカード
  ├─ MAPE学習曲線
  ├─ 学習データ量の推移
  └─ 全履歴テーブル
```

`foodcourt_forecast_factors` は最新状態だけを持つテーブルなので、過去との比較には使えない。
そのため「進化の軌跡」は `foodcourt_forecast_history` が正本になる。

```
foodcourt_forecast_history（1日1行・追記型）
  tenant_name     対象テナント（現状は MARUGO S）
  log_date        学習実行日
  history_days    その時点の学習データ日数
  backtest_days   バックテスト日数
  mape_guests     客数誤差率（DB上は 0.49 = 49%）
  mape_sales      売上誤差率（DB上は 0.49 = 49%）
  mean_guests     ベース客数
```

MAPEは「平均絶対誤差率」。低いほど予測が当たりやすい。
例: `0.30` は「平均30%程度ずれる」という意味。

**専用画面で見るもの:**

| 表示 | 意味 |
|---|---|
| KPIカード | 記録追跡日数、最新の学習データ日数、最新MAPE、平均客数、客数MAPEの傾き |
| MAPE学習曲線 | 客数MAPEと売上MAPEの折れ線。理想はデータ蓄積に伴って下がること |
| 学習データ量の推移 | `history_days` の増加。毎日取り込み続けるほど予測モデルが安定する |
| 全履歴テーブル | 全記録を新しい順に表示し、前回記録とのMAPE差分を「改善/悪化/横ばい」で表示 |

**AIへの自動フィードバック:**
`buildForecastFactorsContext` が履歴から7日以上離れた2点を比較し、進化の証拠を全専門AIに渡す:

```
[学習の進化(自動追跡)] 2026-07-05(履歴38日): 客数誤差±49% → 2026-08-01(履歴65日): ±31%
（18pt改善＝データ蓄積でモデルは着実に賢くなっている）
```

- **改善時**: AIが「モデルは賢くなっている」と根拠付きで言える
- **悪化時**: 「直近に予測しにくい日が続いた可能性。係数の断定は普段より控える」と自動で警告
- これにより「進化する構造」がブラックボックスではなく、**検証可能な事実**になる

**実装上の注意点:**

- 画面は `store_key=marugoS` でAPIを呼ぶが、履歴テーブルは `tenant_name='MARUGO S'` で保存する。`GET /foodcourt/evolution-history` 側で `marugoS / marugos / MARUGO S` 系を `MARUGO S` へ正規化する。
- DBのMAPEは比率形式（`0.49 = 49%`）。画面側で `abs(value) <= 1.5` の場合は `value * 100` として表示する。これをしないと `0.49%` と誤表示される。
- 現状は MARUGO S 専用。複数テナントを切り替えるUIはまだない。
- 「AIが勝手に学習している」のではなく、統計モデルが毎晩再計算され、その結果をAI分析に渡している。
- MAPEは万能ではない。イベントの特殊日やデータ数が少ない条件では、短期的に悪化する。
- `history_days` が増えても、似た条件のデータが増えない限り、特定イベントの予測精度は上がりにくい。

**画面確認:**

```text
https://marugo-s.github.io/line_report/foodcourt-evolution.html
```

接続には管理トークン、または有効な店舗ログインセッションが必要。

**質問による切り替え（2026-08-04 追加）**: Q&Aは1回$0.09かかるため、全質問で検索すると無駄が大きい。journal 側で実装・テスト済みの意図分類（`classifyJournalChatIntent`）を流用し、`data`（事実照会）と判定された質問では**検索そのものを行わない（課金ゼロ）**。`strategy` / `mixed` のときだけ走る。

| 質問例 | 判定 | X検索 |
|---|---|---|
| 直近で一番売れた日は？ | `data` | 走らない |
| 売上を伸ばすための提案を3つ | `mixed` | 走る |
| 今後の運営、世の中のトレンド… | `mixed` | 走る |

定期サマリー（日次/期間/週次）は質問が無いので、常に固定トピックで走る（キャッシュ共有で1日1検索）。

**検索対象の考え方（2026-08-04 変更）**: 当初は「東京ドーム／東京ドームシティの来場者の話題」に絞っていたが、**この範囲はX上の投稿数が足りず拾える話題が痩せる**。会場のイベント・客層は専門AI②が `tokyo_dome_events` から取得しており、Xで補う必要がない。Xにしか無いのは「いま何が食べられ、どう見せられ、どう語られているか」なので、地域を東京〜全国に広げ、**メニュー・商品の方向性に効く食トレンド**を主対象にしている（①スパイスカレー・カレー全般 ②ワインの飲まれ方 ③フードコート/商業施設内飲食の人気メニュー ④SNSでの見せ方・季節需要）。`max_tool_calls` の範囲で観点ごとに複数回検索する。

### フォールバック優先順位

```
統合AI⑤（openai preferred）: openai → gemini → groq
専門AI②（gemini preferred）: gemini → groq
反証AI④（claude preferred）: claude(claude-haiku-4-5) → gemini → groq
専門AI③（grok preferred）  : grok → gemini → groq
専門AI①（groq preferred）  : groq(openai/gpt-oss-120b) → gemini
評価AI⑥（claude preferred）: claude → gemini → groq（評価専用 deadline あり）
Xトレンドブリーフ③'        : grok(x_search) → フォールバック無し（取得できなければブロックごと省略）
```

Xトレンドブリーフだけはフォールバック先を持たない。他モデルは X を検索できないため、
代役を立てると「検索していないトレンド」が混入してしまう。取得失敗時は
プロンプトからブロックごと落とし、統合AIには「ブロックが無い場合はトレンドに言及しない」と指示している。

初回実測（検索1回）:

| 内訳 | 実測 | 割合 |
|---|---|---|
| 入力 31,728 tok × $2.00/1M | $0.0635 | **83%** |
| 出力 1,339 tok × $6.00/1M | $0.0080 | 10% |
| x_search 1回 × $0.005 | $0.0050 | 7% |
| **合計** | **$0.0765/回** | |

**費用の主成分はツール実行料ではなく入力トークン**。x_search が取得したX投稿の本文が丸ごとコンテキストに入るため、1検索あたり3万トークン規模で膨らむ。したがって効くレバーは検索回数（`GROK_X_SEARCH_MAX_TOOL_CALLS`）とキャッシュヒット率であり、いずれも「取り込む投稿量」を通じて入力トークンを左右する。

**実費の算出（ツール実行料込み）**: ブリーフのトークンは `ai_usage_events` に記録され、`model` が `grok-4.5 x_search*2` の形になっている（ツール回数の列が無いため model 名に残している）。次のSQLで実費が出る:

```sql
select
  count(*) as briefs,
  sum((regexp_match(model, 'x_search\*(\d+)'))[1]::int) as x_search_calls,
  round(sum(input_tokens) * 2.00 / 1e6 + sum(output_tokens) * 6.00 / 1e6, 4) as token_usd,
  round(sum((regexp_match(model, 'x_search\*(\d+)'))[1]::int) * 0.005, 4) as tool_usd,
  round(sum(input_tokens) * 2.00 / 1e6 + sum(output_tokens) * 6.00 / 1e6
        + sum((regexp_match(model, 'x_search\*(\d+)'))[1]::int) * 0.005, 4) as total_usd
from ai_usage_events
where provider = 'grok' and model like '%x_search%'
  and created_at >= date_trunc('month', now());
```

AI使用料ページ（`/usage/ai-cost`）はトークン費のみを表示する（`grok-4.5` 用の単価を別枠で持たせてあるので、`grok-3-mini` 単価で過小表示されることはない）。**ツール実行料はページに含まれない**ため、総額は上のSQLで確認する。

月額は $0.0765 × 検索回数。全サーフェスが同じ固定トピックを共有するため、キャッシュが効けば **1日1検索 = 月24〜30回 ≒ 月$1.8〜2.3**。キャッシュはisolate内メモリなので、コールドスタートが多いと回数は増える。高い場合は `FOODCOURT_X_SEARCH_CACHE_TTL_MS` を延ばす、`GROK_X_SEARCH_MAX_TOOL_CALLS` を減らす、`FOODCOURT_X_SEARCH_ENABLED=false` で停止、の順に効く。

**「検索したのに使われなかった率」の測定**: ブリーフが破棄された場合、model に `drop:<理由>` が付く（例 `grok-4.5 x_search*1 drop:missing_x_citations`）。課金は発生しているので、この比率が高いままなら設定を見直すか停止する。

```sql
select case when model like '%drop:%' then split_part(model, 'drop:', 2) else '(used)' end as outcome,
       count(*) as n,
       round(sum(input_tokens) * 2.00 / 1e6 + sum(output_tokens) * 6.00 / 1e6
             + sum((regexp_match(model, 'x_search\*(\d+)'))[1]::int) * 0.005, 4) as usd
from ai_usage_events
where provider = 'grok' and model like '%x_search%'
group by 1 order by n desc;
```

## 12. 分析の限界と注意事項

### AIへの制約（プロンプトで強制）

- **表の値の言い換え禁止**: 「売上は¥82,000、FC平均の61%、3位です」のような羅列は禁止
- **捏造禁止**: データにない指標（推定来館者数・販売点数・原価）は「データにありません」と明示
- **因果の誤用禁止**: 相関（Pearson r）は因果ではないことを明示

### データの制限

- **前年比なし**: MARUGO S は新規オープン（2026年〜）のため前年同月比は計算不可
- **学習初期の精度**: データが増えるほどMAPEが下がる。少量データ期は係数の信頼性が低い
- **イベント動員数**: 公式の動員数は非公開のため**手入力**（foodcourt.html のイベント一覧「👥予想」欄→GLMが `log(1+動員数)` として使用）。未入力のイベントは規模の効果を反映できない
