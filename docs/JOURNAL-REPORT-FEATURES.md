## 1. アプリの目的と範囲

Journal Report はマルゴグループ各店舗向けの **POS電子ジャーナル売上基盤** です。

1. レジが出す `.jnl` / `.lzh` を、再現可能な **確定売上の正本** にする  
2. その正本の上だけで AI 分析・チャットを行う（AI に足し算させない）  
3. 定休・施策・メニュー・現場メモ・予約事実を同じ店舗空間で突き合わせる  
4. 店舗データを `store_partition_key` で隔離し、管理者だけ横断できる  

**含まれないもの（別画面・別機能）:**

- LINE レシート OCR 全般・売上分析画面（`analytics.html` 等）の本体操作  
- フードコート日報アプリ（`foodcourt-report.html`）そのもの  
- 会話メッセージ検索（`message-search.html`）  

※ LINE Webhook は Journal の `#メモ` 連携と他業務（レシート等）が同居するが、本ドキュメントは Journal Report 側の機能に限定する。

## 4. ジャーナル取込とレポート

### 4.1 取込

1. 「変換」タブに `.lzh` / `.jnl`（または月フォルダ）を Drop／選択  
2. ブラウザ内で解凍・制御コード除去・文字コード変換・伝票集計  
3. ログイン済みなら **レポート作成〜クラウド保存まで自動**  
4. 必要に応じて店舗別の商品コード分類（フード／飲料／室料）を調整  

内部手順の要約: 解凍 → 制御コード除去 → デコード → レコード整理 → 売上集計／レポート化。

LINE Reportの `pos-journal.html` からLZHを登録した場合も、登録・修復後に
対象月の `pos_journal_files` 全件を読み直し、Journal Reportの保存済みレポートへ
**日別・月間の2件を自動作成／更新**する。既存保存レポートがLZH原本より広い月を
持つ場合はその月全体を維持し、原本がある営業日だけ原本へ差し替える。
単一日の追加で月間を1日へ縮めない。既存の単月レポートがあれば同じIDを更新し、
再アップロードで重複レポートを増やさない。支払変更で連続して残った同一控えは
日計総売上と元明細合計が不一致の場合だけ最新控えへ正規化する。両者が一致して
いる同時刻・同額・同商品や、組数と伝票行数が異なる割勘明細は正常な会計として
すべて保持する。`sourceMonths`が無い旧保存行もタイトル／期間から完全月の参照候補
に含めるが、ユーザー作成の合算レポートIDを自動日別／月間の更新先にはしない。

### 4.2 確定集計の正本

| 正本 | 用途 |
|------|------|
| 保存済みレポート（`saved_reports`） | AI・予測・一覧の主データ（カテゴリ分け済み月間を重視） |
| ジャーナル原本（`pos_journal_files` + Storage） | 商品初出・コース全期間・天候補完・再解析 |
| 伝票明細 `sales.items` | 商品点数・金額の詳細。無い場合のみ `topProducts` 要約にフォールバック |

ランチ／ディナー境界: **会計時刻 16:00 未満＝ランチ、以降＝ディナー**。

カテゴリ: ジャーナル上は主に **フード／飲料／室料**（チャージはフード内数として扱う設計あり）。「スパークリング」等はカテゴリではなく商品名側。

### 4.3 保存・原本・HTML

| 対象 | 保存先 |
|------|--------|
| レポート本体 | `saved_reports` |
| 詳細 HTML | Storage `pos-report-html` |
| `.lzh` 原本 | Storage `pos-journals`（メタは `pos_journal_files`） |

プレースホルダ行（不完全ジャーナル）への再アップロードでは、削除せず解析結果を **修復更新** できる経路がある（運用記録参照）。

LINE Reportの `pos-journal.html` は、同店舗・同月の `saved_reports` も
`admin-api` 内で共有参照する。LZH原本がある営業日は `pos_journal_files` を優先し、
原本が無い営業日だけ保存レポートで補完するため、同じ売上を二重計上しない。
共有レポートだけの月もKPI・日別・決済・商品・会計明細を表示するが、
「保管ファイル」一覧とダウンロード／削除は実在するLZH原本だけを対象にする。
画面の「PDFにまとめる」は、表示中の月の売上サマリーと商品ランキングを1つの印刷用PDFにする。アップロード・保管原本・会計明細の展開は含めない。

### 4.4 旧解析版・再作成

パーサ／カテゴリ／検証バージョンが古いレポートは stale 扱いとなり、再作成を促す。AI・印刷は再作成後を前提にする。

### 4.5 商品分類（大分類／細分類）

画面の分類は2層。大分類は **フード／飲料／室料／その他**。細分類（グラス赤、赤デキャンタ、カクテル、アルコール等）は親大分類へ集約する。チャージは独立カテゴリではなく、4カテゴリいずれかの内数。

- 手動上書きは店舗別 `productCategoryOverrides`。手動が自動より強い。
- 同じ大分類への確定も「分類済み」。未分類へ戻す操作は `自動分類`。
- 未分類へ戻すときチャージ判定 `isCharge` は上書きしない。
- 解析時の名前自動分類: 名称にハイボール → `アルコール`。名称にカクテル、またはジントニック等の有名カクテル名 → `カクテル`。カタカナ長音 `ー` は消さない。
- ブラウザ（`classifyProductAuto`）とサーバー POS（`classifyPosJournalReportItem`）の両方。保存済みレポートはジャーナル再読込後に新しい自動分類が乗る。

## 5. 店舗情報タブ

テーブル: `store_operation_profiles`（PK: `store_partition_key`）  
API: `GET/POST /pos-journals/store-ops`

店舗ごとに独立。AI分析・チャットのたびにクラウド→ローカル→初期値の順で読み、プロンプトへ注入する。

### 5.1 営業カレンダー前提

| 項目 | 内容 |
|------|------|
| 定休日 | 曜日チェック。定休の売上ゼロ／低下を弱点扱いにしない |
| ランチ／ディナー | あり／限定／なし |
| 溢日ルール | 定休曜日が月に多いとき、指定曜日の一部営業など |
| 特別営業ポリシー・メモ | 自由記述。特別営業の解釈に使う |

初期値リセットでも、後述の同期フラグ・カレンダー・ワインmlは維持する。

### 5.2 施策・イベントカレンダー

`profile.calendarEvents[]`: `{ id, title, kind, start, end, note }`

- 月次カレンダー UI で開始日〜終了日を登録  
- AI／プレビューは分析期間と重なる登録を優先表示  
- 長い本文・添付は **資料タブ** を使う  

### 5.3 過去売上への同期

`journalSalesSync`（既定 OFF）

- ON の店舗だけ、ジャーナルを正として過去売上系（手入力日次／月次など）へ同期する  
- 本番では店舗ごとに明示 ON（例: bistrocavacava）。他店へ勝手に広げない  

### 5.4 ワイン提供量の換算（ml）

`profile.wineMl`:

| 項目 | 既定 | 備考 |
|------|------|------|
| Glass Wine | 100 ml/点 | 店舗編集可 |
| デキャンタ | 375 ml/点 | 店舗編集可 |
| Bottle Wine | 750 ml/点 | **固定** |
| ペアリング | 300 ml/点 | 店舗編集可 |

対象SKU（名称または同等のコード／分類）:

- Glass Wine（コード末尾 `8102` など）  
- デキャンタ（名称にデキャンタ、または分類「赤／白／ロゼ／オレンジデキャンタ」）
- Bottle Wine（`2100`）  
- ペアリング／ペアリング5杯／SPペアリング（`2101` / `2102` / `0028` など）  

**銘柄名だけのボトルは含めない。**  
標準AI分析では `salesData.wineVolumeAnalysis` および店舗営業情報のワインml節を参照する。AIチャットで「どれくらいワインが出たか」等の曖昧質問では、**点数／総ml／両方** を確認してから回答する。

## 6. 資料タブと LINE `#メモ`（日報的な現場記録）

### 6.1 役割

施策・メニュー・価格改定・イベント・マニュアル・現場メモを登録し、AIが「その期間に店舗が何をしていたか」を踏まえて分析できるようにする。

| 原則 | 内容 |
|------|------|
| 数値の正本 | 保存済みレポート／ジャーナル確定集計のみ |
| 資料の役割 | 背景・要因の説明。金額の出典にしない |
| 引用の言い方 | 資料由来は「登録資料によると」、仮説は「※これは推測です」 |

### 6.2 閲覧・編集の場所

**閲覧・編集は Journal Report の「資料」タブ。**

- 登録済み一覧（種別・有効／無効・キーワードで絞り込み）  
- タイトル・期間・概要・本文・タグ・添付の確認／更新  
- 「現場日報」タグ等での絞り込み  
- 添付原本のダウンロード（署名URL）  
- 既定削除は論理削除（過去分析のため残す）。完全削除は purge 確認付き  

LINE 上だけでは一覧閲覧できない。蓄積先は常にこの資料一覧。

### 6.3 Web からの登録

| 項目 | 内容 |
|------|------|
| 種別 | 施策／メニュー／価格改定／イベント／マニュアル／その他 |
| タイトル・概要・本文 | 概要または本文が必要 |
| 期間 | 開始・終了。空欄＝常時有効（グランドメニュー等） |
| 添付 | 画像・PDF・テキスト等。画像は Gemini 解析→確認モーダル可 |
| RAG | 登録後にチャンク分割（実装は約1500字・overlap 200） |

### 6.4 LINE `#メモ` / `#日報` / `#note`

タグは同義。全角 `＃` も可。判定は `_shared/knowledge_memo_tag.ts` に集約。

| 経路 | やり方 | 結果 |
|------|--------|------|
| テキストメモ | `#メモ` に続けて本文を送信 | 店舗ナレッジへ自動分類・保存 |
| 添付メモ | 画像／PDF等を送り、**引用返信で `#メモ`** | Gemini 解析→資料登録 |
| 空の `#メモ` だけ | 本文なし・引用なし | 使い方ガイドを返信（登録しない） |
| 画像だけ送信 | `#メモ` なし | **登録しない**（画像メッセージに text が無いため） |

送信日時: LINE `event.timestamp` を `created_at` と `period_start`/`period_end`（JST送信日）へ保存する。
常時有効にはしない。分析では対象期間と重なるメモを必ず添付し、他月の LINE投稿は類似度だけで混ぜない。

自動分類の例:

- 天候・売れ筋・客足・本日の出来事・所感 → カテゴリ「その他」、タグに **現場日報** が付きうる  
- 新メニュー・ワイン・価格 → メニュー／価格改定  
- 近隣・競合・フェア → イベント／その他＋周辺情報  

`source_type` は `line_post` 相当。成功時は Bot が replyToken で返信（Reaction API は使わない）。

### 6.5 AIへの渡し方

毎ターン（分析・チャット）で次の **3系統** を突き合わせる。

1. ジャーナル確定集計（数値・予約vs飛び込み含む）  
2. 店舗営業情報（定休・カレンダー・ワインml等）  
3. 店舗資料／`#メモ`（期間重なり＋関連度。最大20資料のRAG／本文と、存在確認専用の全資料目次）

マルゴエス（`marugos`）だけ、4系統目として **東京ドーム／フードコート背景** を足す。`GET /foodcourt/journal-brief` が期間内イベント（最大36件）と直近コート内順位・シェア・タイプ判定だけを返す。`foodcourt.html` 全件や期間サマリーの再生成は呼ばない（時間切れ対策）。コート日報の売上は背景、店舗売上の正本はジャーナル。取得失敗は「イベントなし」にしない。

期間に合う資料は参照候補へ入る。全資料目次は存在確認専用で、期間内の施策・引用・因果の根拠には使わない。
正常な0件と、API取得失敗・未接続・部分取得・上限到達を区別し、未確認を「資料なし」に変換しない。

詳細: [JOURNAL-STORE-KNOWLEDGE.md](./JOURNAL-STORE-KNOWLEDGE.md)

## 7. AI分析（標準レポート）

レポートの「AI分析」または同等経路。

| 項目 | 内容 |
|------|------|
| Edge | `ai-analyze`（`action: analyze`） |
| 入力 | サーバー固定規約（OpenAI developer/system・Claude system）＋非信頼user証拠区画（`salesData`、クライアント文脈、店舗資料、外部知見） |
| 役割分担 | 画像／`#メモ`分類は Gemini。売上分析の合成は **OpenAI（Luna）→ Claude Haiku**。外部知見は Perplexity／Grok（任意）。**Qwen／Kimi は情報流出対策で構成外** |
| 出力 | Markdown の経営・売上多角分析＆ワイン営業戦略レポート |
| 履歴 | `ai_analysis_history` に自動保存 |

標準で重視する視点（要約）:

- 店舗立地（新宿三丁目を全店デフォルトにしない）  
- ランチ／ディナー分離の客単価・F/D 比率  
- ワイン・ドリンク構成、グラス／ボトル、**提供量(ml)換算**  
- 12月は確定商品明細・選定資料に季節コースの証拠がある場合だけ事実、無ければ仮説
- 定休を機会損失と誤診しない  
- 資料・カレンダーとの突合  

ビジュアルサマリー（ダッシュボード）は総売上・客単価・F/D・昼夜・曜日／時間帯・売れ筋などを表示する。

## 8. AIチャット

### 8.1 できること

保存済みレポートとジャーナル横断検索を根拠に、期間比較・月次推移・商品点数／売上・客単価・曜日／時間帯・コース・予約vs飛び込み・改善案などを質問できる。

回答下の「PDFにする」で印刷用表示を開き、質問＋回答を `ai_chat_pdf_history` へ保存する。

### 8.2 確認（clarifier）経路

曖昧な質問では、いきなり断定せず確認する。

| 種類 | 例 |
|------|-----|
| 期間 | 対象年月が不明・広すぎるとき |
| 意図 | 何を知りたいか曖昧なとき |
| ワイン表示単位 | 「どれくらいワインが出たか」等 → **点数／総ml／両方** |

選択肢ボタンで答えられる。総ml／両方のときは店舗の `wineMl` 換算で期間ごとの確定mlを注入してから回答する。

### 8.3 確定集計の追加レイヤ（Additive）

新機能は既存レイヤを消さず足す。代表:

| レイヤ | 内容 |
|--------|------|
| 昼夜別 F/D | ランチ／ディナーのフード・ドリンク |
| 異常月ドリルダウン | 高単価会計・コース寄与など |
| 商品初出・銘柄／コード | ジャーナル全件横断（ページ分割取得） |
| コースラインナップ | 単価帯主力と月次コース販売 |
| コホート比較 | 利用／非利用、昼夜、ボトル／グラス等 |
| 予約事実 | チャネル別・新規／リピート・予約vs飛び込み（推定） |
| 商品ランキング | ★大分類除外、コース合算オプション |

規約の詳細: [JOURNAL-AI-CHAT-RULES.md](./JOURNAL-AI-CHAT-RULES.md)

### 8.4 期間の読み方

「2026年1月から7月まで」は端点2か月ではなく **1〜7月の連続全月**。月次がある月は述べ、無い月だけ「今回の確定集計には表示されていません」とする。

## 15. セキュリティ（Journal 観点の要約）

## 16. 運用上の注意

| 注意 | 理由 |
|------|------|
| アプリ本体は `jnl2txt.html` の1本だけにする | `index.html` はクエリ・ハッシュを保って本体へ送る小さな転送スタブ。825KBの二重管理へ戻さない |
| `#メモ` は引用返信が必須（画像） | LINE 画像に text が無い |
| 資料の数字を売上正本にしない | 二重計上・幻覚の温床 |
| 定休を弱点扱いしない | 店舗情報を読まずに曜日分析しない |
| ワインmlは対象SKUのみ | 銘柄名だけのボトルは換算に入らない |
| Dropbox 作業コピーの `supabase/` を本番へ戻し書きしない | HANDOVER／運用事故防止 |
