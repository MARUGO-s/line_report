# MARUGO S フードコートAIシステム 内部構造・設計解説書

本書は、東京ドーム内フードホール「FOOD STADIUM TOKYO」の店舗 **MARUGO S（マルゴエス）** における、自己学習型売上・来客予測および複数AIオーケストレーション（エージェント協調）システムの内部構造・設計について詳細に解説する技術ドキュメントである。

---

## 1. AIオーケストレーション構成（マルチエージェント構造）

システムは単一の大型モデルに依存せず、**5つの専門・反証・統合AIエージェント**および、オプションの**評価AI**を組み合わせた**「5+1エージェント構造」**を採用し、段階的な推論ラウンドを実行する。

```
【ラウンド1: 並列実行（約2〜4秒）】
 ┌─────────────────────────────┐
 │ 専門AI① (数値分析)         │
 ├─────────────────────────────┤
 │ 専門AI② (需要ドライバー)   │
 ├─────────────────────────────┤
 │ 専門AI③ (運営改善・日報)   │
 └──────────────┬──────────────┘
                │ 各専門メモを出力
                ▼
【ラウンド2: 批判的検証（約1〜2秒）】
 ┌─────────────────────────────┐
 │ 反証AI④ (品質管理・監査)   │ ◀── 専門AI①②③の言い過ぎ・捏造を検出
 └──────────────┬──────────────┘
                │ 監査メモを付与
                ▼
【ラウンド3: 最終統合（約3〜6秒）】
 ┌─────────────────────────────┐
 │ 統合AI⑤ (推論・回答生成)   │ ◀── 専門①②③と反証④のメモをマージ
 └──────────────┬──────────────┘
                │ 最終回答を出力
                ▼
【ラウンド4: 評価ループ（オプション・Q&Aのみ段階導入）】
 ┌─────────────────────────────┐
 │ 評価AI⑥ (5軸採点ループ)    │ ── 不合格なら 統合AI⑤ を再実行（最大N回）
 └─────────────────────────────┘
```

各ラウンドにおけるエージェントの処理と実行順序は以下の通りである。

1. **ラウンド1（並列処理）**:
   * **専門AI①、専門AI②、専門AI③** が、システム側から投入された前処理済みの分析用コンテキストを同時に受け取り、それぞれの専門領域に基づいた「解釈メモ」を生成する。
2. **ラウンド2（直列処理）**:
   * **反証AI④** が起動し、ラウンド1で生成された専門AI①②③の解釈メモを比較・検証する。「データにない数値の捏造」「弱い相関からの過剰な因果断定」がないかをチェックし、監査メモを出力する。
3. **ラウンド3（直列処理）**:
   * **統合AI⑤** （推論モデル）が、専門AI①②③のメモと反証AI④の指摘メモを統合する。指摘された「言い過ぎ」を穏やかな「仮説」や「データ不足」に表現を緩和させながら、7部構成のレポート形式（またはQ&A回答）へと最終出力する。
4. **ラウンド4（品質評価ループ - オプション）**:
   * ゲートウェイ環境変数（`FOODCOURT_LOOP_ENABLED=true`）が有効な場合、**評価AI⑥** が統合AI⑤の出力を5軸で自動評価する。基準点未満の場合は改善指示を出して統合AI⑤へ差し戻し（再生成）を行う。

各エージェントにはそれぞれのモデル特性に合わせた最適な役割が割り振られており、月間のAPIコストを最適化しつつ最高精度の出力を得るよう調整されている。

| エージェント | 役割 | 採用モデル (プロバイダー) | 得意分野・特性 |
| :--- | :--- | :--- | :--- |

| **専門AI②** | 需要要因・イベント知識 | **Gemini 3.5 Flash**<br>(Google) | **世界知識・イベント情報の解釈**。東京ドームで開催される野球（対戦相手、デー/ナイター）、ライブ（アーティスト情報、主客層）、および天候との交互作用が客数に与えるメカニズムを解説する。 |
| **専門AI③** | 現場運営改善・日報照合 | **Grok 3 mini**<br>(xAI) | **リアルタイムトレンドと現場施策の紐付け**。X（旧Twitter）のリアルタイム情報を学習している強みを活かし、現場日報（`foodcourt_daily_logs`）の施策と売上実績の突き合わせ、明日現場で打てる具体的な対策を考える。 |

| **評価AI⑥**<br>(ループ評価) | 回答品質の定量測定 | **Claude**（既定） | **多角的なメタ評価**。最終回答がビジネス用途として十分な品質（正確性・実用性など）を満たしているかをJSON形式で厳格に採点する。 |

## 3. ループエンジニアリングの仕組み

システムには、統計学的なアプローチとAI自身のメタ評価アプローチのそれぞれを利用した**2つの自律制御ループ**が組み込まれている。

### ループ①：来客予測のモデル選択ループ（統計型ループ）
毎晩 **JST 05:00** に cron ジョブ（`foodcourt-forecast-cron`）が自動実行され、蓄積されたデータに基づき予測モデルの自己学習とバックテストを回す。

```
【実績データ】
    │
    ├─ A) 乗算モデル (mult-factor-v1)
    │     ベース客数 × 曜日係数 × イベント種別係数 × 天気係数
    │
    └─ B) ポアソン回帰GLM (glm-poisson-v1)
          log(客数) = 切片 + 曜日 + イベント種別 + 天気 + log(1+予想動員数) + トレンド
          ※ 正則化パラメータ λ を候補{1, 2, 4, 8, 16}からバックテストで最適化
                │
                ├─ 過去の全日程に対して「拡張窓バックテスト」を実施
                ├─ それぞれの MAPE（平均絶対誤差率）を計算して比較
                ▼
【最良モデルの自動決定・予測の生成】
```

1. **乗算モデル** と **GLMモデル** の両方に同じ実績データ（`foodcourt_daily_facts`）を学習させる。
2. 過去の履歴に対し、未来データを使わない「拡張窓バックテスト」をそれぞれ回し、当日予測値に対する **MAPE（平均絶対誤差率）** を算出する。
3. **MAPEがより小さい（精度の高い）モデル** を「本晩の採用モデル」として自動採択し、当日〜14日先までの来客数・売上予測（`forecast_predictions`）を生成する。
4. 採択されたモデル情報や誤差率は `foodcourt_forecast_factors.model_selection` に自己学習の記録として保存される。

### ループ②：AI回答品質評価ループ（ジェネレーティブ・ループ）
統合AI⑤が生成した最終回答の品質を維持するため、評価AI⑥によるフィードバック評価ループを実装している。

```
[初回回答] ──▶ [評価AI⑥による5軸採点]
                    │
                    ├─ (全軸80点以上 かつ 総合90点以上) ──▶ 合格・そのままユーザーへ返却
                    │
                    └─ (不合格) ──▶ 改善点テキストのみを統合AI⑤に渡し、回答を再生成（最大N回）
```

* **5つの評価軸**:
  1. **正確性**: データとの不整合がないか。
  2. **論理性**: 主張とデータ・解説が論理的につながっているか。
  3. **専門性**: フードコートや飲食ビジネスの文脈を理解しているか。
  4. **実用性**: 提案された打ち手が現場で実施可能か。
  5. **根拠性**: すべての評価が「数字」や「日報の記述」に基づいているか。
* **差し戻しの最適化**: 再生成時、初回回答の全文やプロンプトをそのまま引き継ぐとトークン消費と混乱が増すため、「不合格判定の具体的な改善ポイント」のみを抽出して統合AI⑤に送信する。
* **ループ上限の自動制御 (Surface-aware Limit)**:
  APIコストとレスポンス速度のバランスを考慮し、ユーザーの利用シーン（Surface）に合わせて上限ループ回数 $N$ を動的に制御している。
  * **Q&A機能 (ask)**: $N=3$ （キャッシュが使えないリアルタイム質問のため、最も厳格にループ）。
  * **日次サマリー (daily_summary)**: $N=2$ （初回閲覧時のみ生成され、以降はキャッシュされるため）。
  * **期間サマリー (period_summary)**: $N=1$ （最もインプットデータ量が多くAPIコストが高いため、1回で打ち切る）。

## 4. 自己学習アルゴリズムと最新のモデル選択基盤

本システムは、静的な予測係数を持ち続けず、日々の実績増加に伴ってモデル自体が毎日自動で「進化」する学習基盤を備えている。

```
 ┌── 1. 蓄積: 日報、イベント動員、実績売上の登録 ──┐
 │                                                │
 └── 5. 観測: 翌朝に前日の実数値をfactsに自動JOIN ─┴─▶ 2. 学習: 毎晩05:00に全係数を自動再計算
                                                            │
 ┌── 4. 予測: 決定されたモデルで翌日〜14日先を予測 ◀─────── 3. 選択: バックテストでMAPE最小モデルを決定
```

### 4.1. モデル構造と正則化アルゴリズム

#### A) 乗算モデル（Legacy Multiplicative Model）
ベースとなる客数に各需要要因（カテゴリ）の倍率を掛け合わせるモデル。
* **サンプル収縮処理 (Shrinkage)**:
  十分なサンプル数（実績日数）が集まっていない要因については、推定倍率が過剰にブレるのを防ぐため、以下の数式を用いて基準値 `1.0` に自動的に引き戻す。
  $$W_{shrink} = \frac{n \cdot W_{raw} + K \cdot 1.0}{n + K}$$
  ここで、$n$ は該当するイベント・天気の出現回数、$K$ は収縮強度定数（システム既定値: $K=4$）である。サンプル数が極少のときは影響度が小さくなり、データが蓄積するにつれ実績倍率 $W_{raw}$ に収束する。

#### B) ポアソン回帰GLMモデル（Generalized Linear Model）
客数などのカウントデータに適したポアソン分布を前提とし、経過日数による長期トレンドやイベント動員数を連続値として組み込める高度な統計モデル。

$$\log(\text{予測客数}) = \beta_0 + \sum \beta_{dow} \cdot D_{dow} + \sum \beta_{event} \cdot D_{event} + \beta_{rain} \cdot D_{rain} + \beta_{attendance} \cdot \log(1 + X_{attendance}) + \beta_{trend} \cdot T_{trend}$$

* **L2正則化（リッジペナルティ）と $\lambda$ の自動チューニング**:
  多重共線性や過学習を防ぐため、モデルは目的関数にリッジペナルティ（係数の二乗和）を加算して最適化する。
  正則化強度 $\lambda$ は固定せず、**候補値群 $\{1, 2, 4, 8, 16\}$** からバックテストでMAPEが最も小さくなった $\lambda$ を自動選択する基盤が稼働している（データ数が少ない初期フェーズでは大きな $\lambda$ が選ばれ、データが潤沢になるにつれ正則化が緩められる）。

## 5. 統計学的な数値の計算ロジック

「AIは文章と解釈を作り、数字はTypeScript（プログラム）が作る」という原則を徹底するため、以下の数値指標はすべてシステム内部のコードによって厳密に事前計算され、コンテキストとしてAIに渡される。

### 5.1. 主要指標の計算式

* **平均絶対誤差率 (MAPE: Mean Absolute Percentage Error)**
  モデル予測精度の定量評価に使用される。
  $$\text{MAPE} = \frac{1}{N} \sum_{t=1}^{N} \left| \frac{\text{実績}_t - \text{予測}_t}{\text{実績}_t} \right| \times 100\%$$
* **異常値のZスコア判定**
  特異な売上変動をイベントや天気のせいか見極めるため、過去の移動平均からの乖離を測定する。
  $$Z = \frac{X_{当日} - \mu_{移動平均}}{\sigma_{移動標準偏差}}$$
  $|Z| \ge 2.0$ の場合、システムは「異常突出日/異常落込日」として自動検出し、解釈の優先度を上げる。
* **店舗間相関係数**
  フードコート内の他の10店舗との共生関係（相乗効果）または競争関係（競合食い合い）を可視化するため、売上の日次時系列データを用いてピアソン積率相関係数 $r$ を計算する。
  $$r = \frac{\sum (X_i - \bar{X})(Y_i - \bar{Y})}{\sqrt{\sum (X_i - \bar{X})^2 \sum (Y_i - \bar{Y})^2}}$$
  * $r > 0.4$ (正の相関): 呼び込み効果の高い「アンカー店舗」とみなす。
  * $r < -0.2$ (負の相関): 客を取り合う「カニバリゼーション」とみなす。

### 5.2. 最新の統計拡張（`stats-ext-v1`）

予測精度をさらに高めるため、以下の高度な統計解析が実行される。

1. **生係数の95%信頼区間（CI: Confidence Interval）**:
   推定されたイベント・天気係数が十分な信頼性を持つかを判定。CIが $1.0$（変化なし）をまたぐ場合、AIには「効果の方向性が統計的に確定していない（偶然のブレの可能性がある）」と解釈するよう指示される。
2. **確度ラベルによるデータ量可視化**:
   AIが僅かなデータから誤った教訓を学ばないよう、要因ごとのサンプル数 $n$ に応じて確度を評価する。
   * $n \ge 6$: **再現性あり**（信頼性の高い傾向）
   * $3 \le n < 6$: **参考程度**（サンプル少数）
   * $n < 3$: **参考不可**（サンプル僅少・解釈禁止）
3. **交互作用（実測 vs 独立仮定の乖離）**:
   「土日」かつ「大型イベント」の日のように、個別の掛け算以上の頭打ち（客席のキャパシティ上限など）が発生していないかを測定し、予測上限の補正に用いる。
4. **残差バイアス評価（系統誤差）**:
   モデルが特定の条件下（例: 雨の日、特定のイベントジャンル）で一貫して過大/過小予測する偏りを検出し、AIの文脈解説で「この要因は割り引いて見るべき」と補正を促す。
5. **効果量（Cohen's d）による寄与度分析**:
   単純な売上増加額だけでなく、曜日の効果やイベント効果がどれほど強力でノイズに強いかを Cohen's d で評価し、最も優先すべき対策要因を絞り込む。
   $$d = \frac{\mu_{イベント日} - \mu_{通常日}}{s_{\text{プールされた標準偏差}}}$$

## 6. 日報システム（`foodcourt_daily_logs`）の統合と活用

現場の「定性的な文脈（なぜ売上が変わったか）」とデータベースの「定量的な実績」を統合するため、2026年7月に日報システムが新設された。

```
 ┌───────────────────────────────────────────────┐
 │  日報ページ (foodcourt-report.html)            │
 │  ・現場担当者が施策カテゴリ・動員・コメントを入力│
 └──────────────────────┬────────────────────────┘
                        │ PUT /foodcourt/daily-logs
                        ▼
 ┌───────────────────────────────────────────────┐
 │  データベース: foodcourt_daily_logs テーブル    │
 └──────────────────────┬────────────────────────┘
                        │ 過去60日分を自動抽出
                        ▼
 ┌───────────────────────────────────────────────┐
 │  AI問合せ (ask) / 定期分析への文脈注入           │
 │  ・現場日報テキストをコンテキストに変換            │
 │  ・Grok 3 mini / 統合モデルのプロンプトに注入     │
 └──────────────────────┬────────────────────────┘
                        ▼
【AIによる裏取り検証・最終回答】
「担当者は販促チラシで客数大幅増と日報に記録しましたが、
　実際の店舗内売上シェアは通常通りであり、この客数増は
　ドーム全体の動員増(4.2万人)による外部要因の可能性が高いです」
```

### 6.1. 日報データの主要フィールド

* **施策リスト (`actions` jsonb)**:
  実施した取り組みをカテゴリコード（`cat`）とともに記録する。
  * `promotion`: 🎯 販促・集客（試食、声かけ）
  * `menu`: 📋 メニュー提案（セットメニュー、陳列変更）
  * `service`: 👥 接客・サービス（スピードアップ、列誘導）
  * `environment`: 🏪 環境・設備（POP設置、レイアウト変更）
  * `staff`: 👤 スタッフ（配置、シフト調整）
  * `other`: 📝 その他
* **実績・課題・申し送り**:
  客数・売上への主観的影響評価（`guest_impact`/`sales_impact`）や、現場の課題（`issues`）、翌日への申し送り（`next_actions`）を記録。
* **動員数 (`daily_attendance`)**:
  イベントの実際の動員人数を記録し、自動的に売上分析ページのイベント一覧へ「📋 42,000人」といった青色バッジとして連携・描画される。

### 6.2. AIと日報の照合ロジック（裏取りルール）

統合AIには、日報テキストを処理する際に以下の**厳格な突き合わせルール**が課されている。

1. **主観と客観の分離**:
   日報に「声かけを強化して客数が増えた」と書かれていても、それをそのまま真実としてレポートしない。同日の実績データ（客数前日比、他店シェア推移）と照合し、データ上の裏取りを行う。
2. **整合・不整合の明記**:
   * **整合**: データでも客数が上昇している場合、「担当者の評価通り、声かけ施策が機能した可能性が高い」と支持する。
   * **不整合**: 実績データが横ばいまたは減少している場合、「担当者は効果ありと報告したが、店舗全体の客数は前週比で下落しており、施策の効果は限定的だった可能性がある」と論理的に指摘する。

## 7. AI蒸留（AI Distillation）と進化の知識転移

システムを持続的に進化させ、推論精度を高めつつAPIコストを長期的に削減するため、AI蒸留と知識転移の設計基盤が備わっている。

### 7.1. 知識転移の仕組み

* **モデル推定係数の転移**:
  ループ①で毎晩再学習された乗算/GLM係数は、翌朝のAI分析にシームレスに転移される。AIプロンプトには最新の統計係数が動的に埋め込まれるため、分析解説と実際の予測ロジックが完全にシンクロし、「予測計算とAIの言い訳が食い違う」という問題を防ぐ。
* **進化の自動観測**:
  毎晩のバックテストデータに基づき、過去7日間でモデル精度がどれほど改善したか（データの蓄積によるMAPEの低下傾向など）を追跡し、AIに「予測モデルが自己進化している証拠」としてプロンプトにインプットする。

### 7.2. AI蒸留（AI Distillation）データ出力

より小型で高速・安価な専用モデルを将来ファインチューニングするため、品質合格または人が承認した回答から「教師データ候補」を自動構成し、進化トラッキング画面からJSONLで書き出せる。人が「改善が必要」とした回答は除外される。

```json
{
  "dataset_version": "foodcourt-distillation-v1",
  "input": {"task": "質問または定型分析", "source_ref": {}},
  "initial_response": "統合AI⑤の初回回答",
  "initial_evaluation": {"improvement_points": [], "risk_flags": []},
  "preferred_response": "品質合格または人が承認した最終回答",
  "trajectory": [{"loop_index": 1, "score": 62}]
}
```

この「初期回答 → 評価 → 改善後回答」の記録はモデル学習へ投入できる形式だが、現在はデータセットの収集・書き出しまでであり、基盤モデル自体の自動学習は行わない。承認済み回答はRAGとして次回分析へ再利用するが、現在の検索は日本語bigramによる字句類似検索であり、embeddingを使うセマンティック検索ではない。

進化トラッキング画面では、承認済み件数・人の承認件数・日次分析教材数を監視する。データ量の最低条件を満たしても本番モデルの自動昇格はせず、固定評価セットによる比較と人の承認を必須とする。

## 8. 野球（巨人戦）詳細データ同期と勝敗・連勝連敗分析（野球情報専門クローラー）

2026年7月、野球試合の結果やファン心理の盛り上がりがフードコートの売上に与える影響をより精密に分析するため、野球情報専門クローラーおよび分析ロジックが追加された。

### 8.1. データ同期アーキテクチャ

毎日朝の **JST 04:10** に実行される cron ジョブ（`tokyo-dome-events-cron`）にて、以下の並行処理が自動実行される。

1. **試合スケジュール・結果のスクレイピング**:
   * 対象URL: `https://baseball-freak.com/game/giants.html`
   * 抽出データ: 試合日、スコア（得点、失点）、対戦相手、球場、開始時間
2. **観客動員数のスクレイピング**:
   * 対象URL: `https://baseball-freak.com/audience/giants.html`
   * 抽出データ: 試合日、観客動員数、勝敗（○/●/△）、試合時間
3. **データの突合（マージ）**:
   * クローラー内部で2つのデータソースを「試合日（日付）」キーで結合し、東京ドーム開催だけでなく、全会場（地方球場など）の試合詳細データを一体化する。
4. **ダブル書き込み（UPSERT）**:
   * 取得されたデータは、主キー（`game_date`）を用いて以下の2つのテーブルに同時に `ON CONFLICT DO UPDATE`（上書き更新）される。
     * **`giants_game_results`** (新規テーブル): 地方球場を含む全巨人戦の詳細履歴を格納。
     * **`tokyo_dome_events`**: 東京ドーム開催分のみ、カレンダー描画・手入力用の動員数や試合時間カラムを更新。

### 8.2. 連勝・連敗数（モメンタム）の時系列追跡

ファン心理の熱量（モメンタム）を測るため、APIサーバー（`admin-api`）は以下のロジックで試合開始直前の連勝・連敗数（`streak_before`）を算出する。

* `giants_game_results` から全試合を日付順（昇順）にソートして走査。
* 前日までの勝敗をもとに連勝（プラス）または連敗（マイナス）のカウント値を累積し、当日試合開始前のステータスを決定。引き分け（△）は連勝/連敗をリセット（`0`）する。
* **地方球場での試合結果も累積カウントに寄与する**ため、地方連戦での勝ち越しによるファンの熱量の高まりが、その後の東京ドームホーム戦へ与える影響（祝勝会需要など）を正確に評価可能。

### 8.3. AI向け数値分析コンテキスト

APIからマージされたデータは、`foodcourt_compare.ts` に渡され、以下のグループ別実績が自動集計されてAIに引き渡される。

* **勝敗別平均**: 勝ち試合 vs 負け試合 の売上・客数差（祝勝会によるアルコール/客単価アップ要因の検証）。
* **時間帯別平均**: デーゲーム vs ナイター の売上・客数差（来客時間帯シフトの予測）。
* **試合時間別平均**: スピード決着（3時間以下） vs 長期戦（3時間超） の売上・客数差（試合終了後の流入時刻のズレ）。
* **接戦度・点差別平均**: 接戦（1点差以内） vs 大点差（5点差以上） の売上・客数差（大点差時は7回裏以降の早期退場による早期流入が発生しやすい仮説の検証）。
* **連勝・連敗状況別平均**: 2連勝以上 vs 2連敗以上 vs 連勝連敗なし の売上・客数差（チームの勢いによる集客・消費力リフトの定量評価）。
