## 1. 設計思想（何を解決しているか）

### 1-1. 解決した3つの問題

| 問題 | 原因 | 解決策 |
|------|------|--------|
| 「毎回同じことしか言わない」 | 1つのAIが全部を担当し、平均的な言い回しになる | **役割分担**（専門AI×3 → 反証 → 統合） |
| 「数字を言い換えるだけで中身がない」 | AIが数字を自分で作り、正確さより流暢さを優先する | **コードが全数値を事前計算**し、AIには解釈だけさせる |
| 「予測モデルとAI解説が矛盾する」 | 数値予測と文章生成が別統計を使う | 予測係数をDBに保存し、**解説も同じ係数を参照（1本化）** |

### 1-2. 不変の原則

1. **AIは数字を作らない**  
   売上・客数・順位・シェア・相関・Zスコア・係数・MAPEはすべて TypeScript が計算し、テキストとしてプロンプトに注入する。
2. **同じモデルを複数役に使わない**  
   同じ学習データ・同じ癖のモデルを「分析」「天気」「改善」に分けると、専門性を偽装しただけの1人芝居になる。**異なるプロバイダー＝異なる知識源**を意図的に組み合わせる。
3. **反証ファースト**  
   専門AIの主張を別系統のAIが批判的にレビューしてから統合する。
4. **自己申告を信用しない**  
   予測の優劣は MAPE（バックテスト）、文章の合否はコード側の閾値判定。AIの「自信」は採用基準にしない。
5. **現場の主観は主観として扱う**  
   日報の施策評価は「仮説」として数値実績と照合し、整合・不整合を明示する。

```
└───────────────────────────────┬──────────────────────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────────────────┐
│                    数値学習層（ループ①）                                   │
│  foodcourt_daily_facts / foodcourt_daily_features                        │
│  foodcourt-forecast-cron (JST 05:00)                                     │
│    乗算モデル vs ポアソンGLM → 拡張窓MAPEで自動採用                         │
│  → forecast_predictions / foodcourt_forecast_factors / history           │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ 係数・MAPE・統計拡張をテキスト化
┌───────────────────────────────▼──────────────────────────────────────────┐
│                    文章生成層（5+1エージェント）                            │
│  統計コンテキスト + 生データ + 日報 + 予測                                  │

└──────────────────────────────────────────────────────────────────────────┘
```

## 3. AIオーケストレーション（誰が何をどの順で動くか）

### 3-1. パイプライン全体

```
[コード事前計算コンテキスト]
  対象日事実 / 要因分解 / 相関 / 異常値 / イベント・天気相関
  学習係数 / 統計拡張 / 予測+MAPE / 競合プロファイル / 日報
         │
         ├──────────────┬──────────────┐
         ▼              ▼              ▼
   専門AI①          専門AI②        専門AI③
   数値・他店比較     イベント・天気    運営改善
   Groq             Gemini          Grok (xAI)
   (並列・同時)       (並列)          (並列)
         │              │              │
         └──────┬───────┘              │
                ▼                      │
          反証AI④                      │
          Kimi K3（失敗時Claude Haiku）  │
                │                      │
                └──────────┬───────────┘
                           ▼
                     統合AI⑤
                     OpenAI GPT-5.6 Luna
                     （矛盾解消・最終文章）
                           │
              ┌────────────┴────────────┐
              │ ループ②が有効な場合のみ  │
              ▼                         │
        評価AI⑥（採点JSONのみ）          │
          合格 → 返却                    │
          不合格 → 改善点だけを⑤に戻す    │
          （①〜④は再実行しない）         │
```

### 3-2. 実行タイミングとレイテンシの目安

| ラウンド | 内容 | 性質 | 目安時間 |
|---------|------|------|----------|
| 0 | コードが統計・コンテキストを組み立て | 同期・課金なし | 数十ms〜数百ms |
| 1 | 専門AI①②③ | **並列** `Promise.all` | 約2〜4秒 |
| 2 | 反証AI④ | 直列（①②③の出力待ち） | 約4〜25秒（Kimi K3、失敗時Haiku） |
| 3 | 統合AI⑤ | 直列 | 約3〜6秒 |
| 4+ | 評価AI⑥＋統合再生成（任意） | ループ上限まで | 1回あたり+数秒 |

再ループ時に専門AIと反証を回し直さないのは、**コスト増を「統合＋評価」に限定する**ための設計である。

### 3-3. 3つの表面（surface）で同じ骨格を共有

| surface | 関数 | 用途 | キャッシュ |
|---------|------|------|------------|
| `ask` | `answerFoodCourtQuestion` | 自由質問（Q&A） | なし |
| `daily_summary` | `generateFoodCourtDailySummary` | 1日の自動サマリー | `foodcourt_daily_ai_summary` |
| `period_summary` | `generateFoodCourtPeriodSummary` | 期間サマリー | `foodcourt_period_ai_summary` |

いずれも「専門×3 → 反証 → 統合」の骨格は共通。品質評価ループは環境変数で surface ごとに ON/OFF できる。

### 3-4. なぜ「オーケストレーション」が必要か

単一モデルに設計書の全分析観点を一度に投げると:

- 回答が浅く、言い回しが毎回似る
- イベント知識と統計解釈と打ち手が混線する
- 言い過ぎ・数字捏造の抑制が弱い

役割を分け、**異なる知識源のメモを統合AIに編集させる**ことで、深度と安全性を両立している。

## 4. 各AIエージェントの役割と強み

### 4-1. 専門AI① — 数値分析・他店舗比較（Groq / Llama）

| 項目 | 内容 |
|------|------|
| プロバイダー | Groq |
| モデル（既定） | `qwen/qwen3.6-27b`（Alibaba Cloud Qwen 3.6 27B。`FOODCOURT_GROQ_MODEL` で変更可。旧Llama指定は自動的に置換） |
| フォールバック | `openai/gpt-oss-120b` |
| 最大出力 | 約600〜700トークン |
| 出力 | 統合AI向けの**分析メモ（下書き）** |

**強み（なぜこの役か）**

- 数値・統計パターンの推論に強いオープンウェイト系モデル
- Groq LPU による**超高速推論** → 3専門AI並列のボトルネックになりにくい
- 「この数字の関係は統計的に何を意味するか」を読む役に最適

**担当タスク（例）**

1. 客単価・順位が業態プロファイルから妥当か／想定外か
2. 真の競合（来店動機・価格帯が近い相手）の特定
3. 売上増減が**客数要因か客単価要因か**（コードが計算した要因分解を解釈）
4. 店舗間相関（カニバリ／アンカー候補）の業態文脈での意味づけ
5. 異常値（Zスコア）日の平常からの切り分け
6. 予測モデルの MAPE・信頼度を踏まえた「参考値」としての扱い

---

### 4-2. 専門AI② — イベント・天気需要ドライバー（Gemini）

| 項目 | 内容 |
|------|------|
| プロバイダー | Google |
| モデル（既定） | `gemini-3.5-flash` 系（`FOODCOURT_GEMINI_MODEL`） |
| フォールバック | Groq `qwen/qwen3.6-27b` |
| 最大出力 | 約600〜700トークン |

**強み**

- ウェブ規模の学習コーパスに基づく**エンタメ・スポーツ・興行の世界知識**
- 「NiziUライブ＝若年女性中心」「巨人×阪神＝遠征ファン」など、**イベント×客層**の推論
- 天気・季節・地理文脈との複合解釈

**担当タスク（例）**

1. イベント種別・規模・客層から客数・売上への影響メカニズムを説明
2. 野球（対戦・デー／ナイター）、ライブ、小ホール（後楽園・カナデビア）の差
3. 天気とイベントの**交互作用**（雨でもドーム内イベント客は影響が違う等）
4. 今後の予定イベントと想定影響・打ち手の方向性

### 4-3. 専門AI③ — 運営改善（Grok / xAI）

| 項目 | 内容 |
|------|------|
| プロバイダー | xAI |
| モデル（既定） | `grok-3-mini`（`FOODCOURT_GROK_MODEL`） |
| APIキー | `XAI_API_KEY` 等 |
| フォールバック | Groq `qwen/qwen3.6-27b` |
| 最大出力 | 約600〜700トークン |

**強み（他AIと根本的に違う点）**

Grok は **X（旧 Twitter）上のリアルタイムに近い世論・トレンド**を知識に取り込みやすい設計思想を持つ。東京ドームのフードコートでは:

| Grokが扱いやすい知識 | 現場への落とし込み |
|----------------------|--------------------|
| 話題のアーティストのファン層 | 当日の見せ方・セット提案 |
| 球団ファンの行動・消費傾向 | 試合後ピークの仕込み・提供速度 |
| 食・写真映えのトレンド | 陳列・訴求の具体案 |
| 他店・他業界の演出事例 | 明日から試せるアイデア |

**MARUGO S 固有データとの組み合わせ**

- コードが渡す係数・予測・競合データ → **現実の接地**
- Grok のトレンド知識 → **客心理・流行の補完**  
両者は競合せず、相互補完する。

**厳守ルール（プロンプトで強制）**

- データにない販売点数・原価・スタッフ人数を作らない
- 打ち手には「狙う客層」「実施条件」「見るべきKPI」をセットで付ける
- 数値分析・イベント分析の断定は行わない（①②の領域を侵さない）

**日報との接点**

- `# 現場日報・施策記録` は主に運営改善AIの `opsUser` に注入される  
  → 「昨日やった施策」と「明日やる打ち手」を同じ視点で接続する。

### 4-4. 反証AI④ — 品質管理・反証（Kimi K3 → Claude Haiku）

| 項目 | 内容 |
|------|------|
| 優先プロバイダー | Moonshot |
| 優先モデル | `kimi-k3`（`FOODCOURT_MOONSHOT_MODEL`） |
| API設定 | `temperature=1` / `reasoning_effort=low` / `max_tokens=本文上限+1000` |
| フォールバック | Anthropic `claude-haiku-4-5`（`FOODCOURT_CLAUDE_MODEL`） |
| 最大出力 | 約550〜650トークン |
| 出力 | **反証メモ**（統合AIへの編集指示） |

**強み**

- 安全性・正直さを重視した学習方針 → **「言い過ぎ検出」「根拠なし主張の指摘」**に向く
- ①②③とはアーキテクチャ・学習方針が異なるため、**共通の盲点を独立視点で突く**

**検出対象**

- 弱いデータからの過剰断定
- データなしの主張
- **相関と因果の混同**
- 対象日／期間の取り違え
- データにない数字の混入（捏造）

**出力形式（概念）**

```
採用してよい主張: …
弱めるべき主張: …（断定→仮説）
禁止すべき断定: …
```

## 5. 統計学的計算をコード側で行いAIに渡す仕組み

### 5-1. 原則の再掲

**AIは電卓ではない。**  
ピアソン相関も Z スコアも係数も、すべて `foodcourt_compare.ts`（および予測 cron）が計算し、**解釈ガイド付きテキスト**としてプロンプトに載せる。

### 5-2. Q&A / サマリー直前に組み立てるコンテキスト

`answerFoodCourtQuestion` 付近で典型的に組み立てるもの:

| 関数・ブロック | 計算内容 | AIへの意味 |
|----------------|----------|------------|
| 生データ `blocks` | 直近最大45日×11テナントの売上・客数・客単価 | 事実の一次情報 |
| `buildBaseInsights` | 基準店の要約傾向 | 全体感 |
| `buildEventCorrelation` | イベント有無・種別と客数の関係 | イベント効果の定量 |
| `buildWeatherCorrelation` | 雨／気温帯と客数 | 天気感応度 |
| `buildCompetitorContext` | 競合11店の業態プロファイル | 業態文脈 |
| `buildContributionDecomposition` | **売上＝客数×客単価の要因分解** | 増減の主因切り分け |
| `buildStoreCorrelation` | **ピアソン相関 r**（基準店 vs 他店） | カニバリ／アンカー候補 |
| `buildAnomalyDays` | **Zスコア \|Z\|≥2** の突出／落込日 | 外れ値の切り分け |
| `buildForecastContext` | 予測値＋過去精度 | 見通しと信頼度 |
| `buildForecastFactorsContext` | 学習係数＋MAPE＋**統計拡張** | 1本化された根拠 |
| `buildDailyLogsContext` | 日報（施策・動員・主観評価） | 因果仮説の現場材料 |
| `viewingBlock` | 画面表示中の対象日 | 時間軸の固定 |

### 5-3. 売上の要因分解（設計書の最重要恒等式）

出発点:

\[
\text{売上} = \text{客数} \times \text{客単価}
\]

増減の近似分解（前半平均 → 後半平均）:

\[
\Delta S \approx \underbrace{(G_l - G_f)\,K_f}_{\text{客数要因}}
+ \underbrace{(K_l - K_f)\,G_f}_{\text{客単価要因}}
+ \underbrace{(G_l - G_f)(K_l - K_f)}_{\text{交互}}
\]

コードは主因ラベル（客数要因／客単価要因）まで付与してAIに渡す。  
打ち手を「集客強化か単価向上か」で誤らないための**定量ゲート**である。

### 5-4. 店舗間ピアソン相関

- 日次売上の系列で基準店と各店の相関係数 \(r\) を計算（最低サンプル数のガードあり）
- \(r \le -0.3\) をカニバリ候補、\(r \ge 0.5\) を連動／アンカー候補として列挙
- プロンプトに **「相関は因果ではない（曜日・イベントの共通要因で連動しうる）」** と明記

### 5-5. 異常値 Z スコア

\[
Z = \frac{\text{当日売上} - \text{平均}}{\text{標準偏差}},\quad |Z| \ge 2
\]

を検出し、同日のイベント・雨・気温を添えて「平常分析から切り分ける日」として渡す。

### 5-6. 学習係数と確度ラベル

`foodcourt_forecast_factors` から読む係数（曜日／イベント種別／天気）について:

| サンプル数 n | ラベル |
|--------------|--------|
| n ≥ 6 | 再現性あり |
| n ≥ 3 | 参考程度（やや少数） |
| n < 3 | サンプル僅少（参考不可） |

MAPE とバックテスト日数から **モデル信頼度（低／中／中〜高）** も文章化し、断定の強さを制御する。

### 5-7. 統計拡張（stats-ext-v1）— 「どこまで信じてよいか」

予測モデル本体の `fit()` / `predict()` には手を入れず、**解釈専用**の5統計を毎晩計算して `advanced_stats` に保存する。

| # | 統計 | 解決する問題 | AIができること |
|---|------|--------------|----------------|
| ① | 95%信頼区間（収縮前の生係数） | 係数×1.89が偶然か | CIが1をまたぐ係数を「偶然の可能性」と扱う |
| ② | 条件別四分位数・range | 平均だけではブレが見えない | 下振れリスク（最悪ケース）を述べる |
| ③ | 交互作用（実測 vs 独立仮定） | 乗算は独立を仮定 | 「土日×野球は掛け算どおり伸びない」等 |
| ④ | 残差バイアス（条件別） | どこで系統的に外すか | 過大評価条件を割り引いて解釈 |
| ⑤ | 効果量 Cohen's d | 見かけの倍率と影響力の乖離 | 要因の横比較（曜日 vs イベント等） |

**干渉させない設計:** 予測経路と解釈経路を分離。計算は cron 1箇所、AIは読むだけ。

### 5-8. 画面表示日のグラウンディング

フロントが `viewing_report_id` を送り、バックエンドが売上日に変換して全エージェントの**最優先ブロック**に注入する。

これがないと、AIは数十日分の生データから「派手なイベントの日」を勝手に対象にし、**時間軸がずれた回答**をする。統計が正しくても、対象日がずれれば分析は無意味になる。

## 6. 来客予測の学習システム（数値の自己改善ループ）

「学習」は LLM の fine-tuning ではなく、**毎日の実績から統計モデルの係数を再推定し、誤差で次の採用モデルを決める**ことである。

### 6-1. データフロー

```
テナント一覧画像（LINE）
  → foodcourt_tenant_reports
  → DBトリガー → foodcourt_daily_facts（日次×11テナント）
  → view foodcourt_daily_features（曜日・イベント・天気・動員）

毎晩 JST 05:00 foodcourt-forecast-cron
  ① 乗算モデル fit
  ② ポアソンGLM fit（λ ∈ {1,2,4,8,16} をバックテスト選択）
  ③ 拡張窓バックテストで MAPE 比較 → 勝者を採用
  ④ 当日〜+14日を forecast_predictions に保存
  ⑤ 係数・MAPE・model_selection を factors / history に記録
```

実績が翌日以降に入ると翌朝の fit に取り込まれ、**係数が更新される＝学習ループが閉じる**。

### 6-2. モデル A — レガシー乗算（mult-factor-v1）

\[
\text{予測客数} = \text{ベース} \times \text{曜日係数} \times \text{イベント係数} \times \text{天気係数}
\]

- 係数 = 条件別平均 ÷ 全体平均  
- **shrink（K=4）**: 少サンプル係数を 1（影響なし）へ収縮  
- **AI解説用係数は常にこちら**（「土曜=×1.2」のように解釈しやすい）

### 6-3. モデル B — ポアソン回帰 GLM（glm-poisson-v1）

\[
\log(\text{客数}) = \text{切片} + \text{曜日} + \text{イベント} + \text{天気}
+ \log(1+\text{予想動員数}) + \text{トレンド}
\]

- IRLS＋リッジ正則化  
- 動員数（連続値）と開店後トレンドを扱える  
- データと動員入力が貯まるほど有利になる想定  

### 6-4. モデル選択ループ（ループ①）

1. 各過去日について「それより前のデータだけ」で学習→予測（拡張窓・out-of-sample）
2. guests の **MAPE** が小さい方をその晩の本番に採用
3. 勝敗・λ・両 MAPE を `foodcourt_forecast_factors.model_selection` と `foodcourt_forecast_history` に記録
4. 画面 `foodcourt-evolution.html` で MAPE 推移と model_version を可視化

**人間がモデルを切り替える必要はない。** 誤差実績が次の予測方法そのものを変える。

### 6-5. 予測とAI解説の1本化

| 用途 | 参照元 |
|------|--------|
| 本番の数値予測 | その晩の採用モデル（乗算 or GLM） |
| AI が語る係数の根拠 | **常に乗算モデルの倍率**（語り口の安定） |
| 信頼度 | 両モデル共通の MAPE・履歴日数・進化トラッキング |

これにより「予測はGLM、解説は別の勘」という**二重真理**を防ぐ。

## 7. Q&A / サマリーの品質評価ループ（AIループエンジニアリング）

### 7-1. ループ②とは何か

既存5エージェントが作った**統合回答**を、第6の評価AIが5軸採点し、不合格なら**改善点だけ**を統合AIに渡して再生成する。

```
統合回答（1回目）
  → 評価AI⑥（JSONのみ: 5軸スコア + 改善点 + リスクフラグ）
  → コードが合否判定:
       総合 ≥ 90 かつ 各項目 ≥ 80
  → YES: 返却
  → NO: 改善点のみを統合AI⑤に追加 → 再生成 → 再評価
  → 上限到達: 最高得点の回答を返す
```

**反証AI④との違い**

| | 反証AI④ | 評価AI⑥ |
|--|---------|---------|
| タイミング | 統合の**前** | 統合の**後** |
| 入力 | 専門メモ | 最終回答＋コンテキスト |
| 出力 | 編集メモ | 採点JSON |
| 再生成 | しない | 不合格時に統合を再実行 |

### 7-2. 5軸評価

1. **正確性** — データにない数字を作っていないか、日付の混同はないか  
2. **論理性** — 因果と相関の取り違え、要因分解の一貫性  
3. **専門性** — フードコート／ドーム業態の文脈  
4. **実用性** — 打ち手が具体的か、KPIまで落ちているか  
5. **根拠** — イベント／天気／曜日／係数が実データと対応しているか  

サブ観点（評価プロンプトに内包）:

- データに無い数値の捏造
- 売上日とレポート発行日の混同
- 相関と因果の断定
- 客数要因と客単価要因の取り違え
- 抽象的な打ち手だけで終わること

### 7-3. コスト設計（再生成戦略）

| surface | ループ上限（既定） | 理由 |
|---------|-------------------|------|
| Q&A `ask` | 3 | 自由質問で品質効果が最大。キャッシュなし |
| 日次 `daily_summary` | 2 | 初回生成時のみ（以降キャッシュ） |
| 期間 `period_summary` | 1 | コスト高のため最小 |

**標準再生成:** 専門①②③・反証④のメモは再利用し、**統合⑤だけ**改善点付きで再実行。  
1ループ追加の増分 ≈ 統合1回＋評価1回。

### 7-4. 改善点フィードバックの作法

`buildLoopFeedback` は:

- **前回回答全文を渡さない**
- 改善点・リスクフラグだけを渡す
- 「不足部分だけ改善し、形式は維持」と指示

→ 全文を渡すとモデルが丸ごと書き換え、安定した7見出しやKPI構造が崩れるのを防ぐ。

### 7-5. 記録テーブル（将来の蒸留素材）

| テーブル | 内容 |
|----------|------|
| `foodcourt_ai_loop_runs` | 1質問／1生成の最終結果（採用ループ、最終スコア、返却理由） |
| `foodcourt_ai_loop_iterations` | 各ループの生成物・5軸・改善点・使用量 |

`returned_reason`:

- `passed` — 合格
- `max_loop_best` — 上限到達で最高点採用
- `evaluation_failed` — 評価失敗（その回の生成を採用）
- `generation_failed` — 生成失敗

### 7-6. 有効化（2026-07-21: Q&Aのみ段階導入）

```
FOODCOURT_LOOP_ENABLED=true
FOODCOURT_LOOP_APPLY_TO_ASK=true      # まずQ&Aのみ推奨
FOODCOURT_LOOP_APPLY_TO_DAILY=false
FOODCOURT_LOOP_APPLY_TO_PERIOD=false
FOODCOURT_LOOP_APPLY_TO_WEEKLY=false
FOODCOURT_LOOP_MAX_ASK=2
FOODCOURT_LOOP_PASS_TOTAL=70
FOODCOURT_LOOP_PASS_EACH=65
```

全体フラグとsurface別フラグの両方がtrueの場合だけ有効。未設定時はOFFとなる。現行の通常版・loop版は同一キャッシュバージョンのため、日次をOFFにしても不要な再生成は発生しない。

### 7-7. 使用量

評価・再生成を含む全呼び出しは `ai_usage_events` に記録され、AI使用料ページで可視化できる。

## 8. AIの蒸留・RAG・フィードバック学習（現状と設計）

### 8-1. 用語の整理（本システムでの意味）

| 用語 | 本システムでの意味 | 現状 |
|------|--------------------|------|
| **数値学習** | 乗算／GLM の係数再推定・MAPEによるモデル選択 | **本番稼働** |
| **品質ループ** | 評価AIによる再生成 | **Q&Aのみ本番稼働** |
| **蒸留（distillation）** | 高品質な「入力→下書き→評価→最終」ペアを教材化し、より安価／高速なモデルやプロンプト改善に使う | **設計済み・未実装の本格運用** |
| **RAG** | 過去の合格回答を類似質問で検索し、新規回答の材料にする | **設計済み** |
| **ユーザーFB学習** | 「役に立った／違う」でランキング | **設計済み** |

### 8-2. すでに「学習」しているもの（実装済み）

1. **来客予測の係数・λ・採用モデル** — 毎晩、実績で更新  
2. **統計拡張 advanced_stats** — 係数の信頼性メタ情報  
3. **進化トラッキング** — `foodcourt_forecast_history` の MAPE 時系列をAIに「賢くなっているか」として渡す  
4. **日次サマリーの自己検証** — 前回サマリーを `priorSummary` として渡し、見立ての連続性を検証  
5. **ループログ** — 有効化時、全反復を DB に保存（蒸留・RAG の原料）

### 8-3. 蒸留データとして使える形（設計）

品質ループが回ると、次のペアが自然に溜まる:

```json
{
  "input": "ユーザー質問 + 実データコンテキスト（統計・日報・係数）",
  "draft_answer": "初回の統合回答",
  "evaluation": {
    "scores": { "accuracy": 90, "logic": 85, "expertise": 82, "practicality": 78, "evidence": 86 },
    "improvement_points": ["打ち手にKPIが不足", "イベント根拠が弱い"]
  },
  "final_answer": "合格または最高点の回答"
}
```

**想定される使い道**

- 不合格→合格の差分から、プロンプトの弱点を定量改善  
- 高得点回答だけを教師として、統合モデルの few-shot 例に使う  
- 将来、小型モデルへの **knowledge distillation** 用コーパス  
- 成功例／失敗例の RAG インデックス

### 8-4. RAG（設計）

- `foodcourt_ai_loop_iterations` から `passed=true` かつ高スコアを抽出  
- embedding 列または `foodcourt_ai_answer_embeddings` を追加  
- 類似質問に対し「過去に通った言い方・打ち手」をコンテキスト注入  

### 8-5. ユーザーフィードバック（設計）

```sql
-- 概念: foodcourt_ai_answer_feedback
-- run_id, rating(1-5), comment, created_at
```

評価AIスコア × ユーザー評価 × 再利用回数で **回答ランキング** が可能になる。

### 8-6. 数値モデル側の次段階（蒸留とは別系統）

- 曜日×イベントの交互作用項  
- 客単価のイベント別化  
- GBDT 等の非線形モデル  
- 会場×客層別係数  

これらは LLM 蒸留ではなく、**予測エンジンの統計学習の進化**である。

## 9. 日報システムのデータの重要性

> ユーザー表記の「日葡」は **日報** を指すものとして記載する。

### 9-1. なぜ日報が「ただのメモ」ではないか

数値パイプライン（売上・客数・イベント・天気）は **何が起きたか** を語る。  
しかし次は語れない:

| 数値だけでは分からないこと | 日報が埋める情報 |
|----------------------------|------------------|
| なぜその日だけ客数が増えたか | 試食・声かけ・陳列変更などの**施策** |
| 客数増でも売上横ばいの理由 | 客層変化・回転の**現場感覚** |
| 予測が動員規模を誤る理由 | **動員数の直接入力**（公開データに無い） |
| 次の同イベントで何を変えるか | 課題・申し送りの蓄積 |

日報は AI と予測モデルの両方に効く **「因果の仮説データ」と「規模の教師データ」** である。

### 9-2. データモデル（要点）

テーブル `foodcourt_daily_logs`（店舗×日付で一意・Upsert）:

| フィールド | 意味 | 下流への効き方 |
|------------|------|----------------|
| `actions` | 施策（カテゴリ＋本文） | Q&A・運営改善AIの「何をしたか」 |
| `guest_impact` / `sales_impact` | 担当者の主観評価 | 実績と照合し整合／不整合を判定 |
| `daily_attendance` | 動員数（人） | 分析画面バッジ＋予測の規模特徴量の燃料 |
| `weather_note` / `event_note` | 体感・特記 | 公式天気・イベントの補完 |
| `issues` / `next_actions` | 課題・申し送り | 翌日の打ち手提案の連続性 |
| `handler` | 担当者 | 責任の文脈 |

施策カテゴリ: 販促／メニュー／接客／環境／スタッフ／その他。

### 9-3. Q&A への組み込み（文章側）

```
PUT /foodcourt/daily-logs  →  foodcourt_daily_logs
POST /foodcourt/ask
  → 直近60日分の日報を取得
  → buildDailyLogsContext()
  → 運営改善AI (opsUser) と 統合コンテキスト に注入
  → 統合AI指示: 施策日・翌日の実績と照合し、
                 担当者評価は主観なのでデータで裏取り、
                 整合・不整合を明示せよ
```

**変化の例**

| 以前 | 日報あり |
|------|----------|
| 「7/5は客数が増えた」 | 「7/5は14–15時に試食。担当は+10組と評価。実績の14–16時も前日比+18%で方向一致。ただしナイター動員4.2万人との切り分けが必要」 |
| 「施策効果は不明」 | 「声かけ強化日は客数-3%。同日動員3万人でやや少なく、施策より規模要因の可能性」 |

### 9-4. 予測・分析画面への組み込み（数値側）

- 日報の `daily_attendance` は `loadBaseDailyForReports` で売上日次にマージされ、分析画面のイベント行に動員バッジとして出る  
- イベント一覧の「👥予想」は `tokyo_dome_events.expected_attendance` に入り、GLM の \(\log(1+\text{動員})\) の燃料になる  
- **動員入力が貯まるほど GLM がレガシーに勝ちやすくなる**＝予測が賢くなる直接レバー

### 9-5. 設計上の扱い（誤用を防ぐ）

1. **担当者記述は主観** — AIは断定の根拠にせず、数値と照合する  
2. **動員数は可能な限り単一の真実** — 予測・画面・日報で矛盾しないよう同じ系統に寄せる  
3. **日報が無い日も数値分析は動く** — 日報は任意の強化層。欠落で既存分析を壊さない  

### 9-6. 日報データの戦略的価値（まとめ）

| レイヤ | 日報が効く理由 |
|--------|----------------|
| ループ①（予測） | 動員数・現場規模感が特徴量の質を上げる |
| ループ②（文章品質） | 「施策→結果」の検証可能なストーリーが実用性・根拠スコアを押し上げる |
| 専門AI③（運営改善） | 昨日の施策と明日の打ち手が接続し、抽象アドバイスが減る |
| 統合AI | 主観と客観のズレを明示でき、信頼できる経営言語になる |
| 将来の蒸留 | 「施策あり日の高得点回答」は最も価値の高い教師データになる |

**結論:** 日報は「現場の日記」ではなく、**AI売上分析の因果層と予測層を結ぶ一次データ資産**である。毎日の記入と動員入力は、モデル改善とQ&A品質の両方に直結する。

## 11. データの流れ（収集→学習→解説→現場）

```
[毎日]
  テナント一覧を LINE 送信  →  11店実績が増える
  イベント cron / 天気 cron  →  特徴量が揃う
  日報・動員入力             →  因果と規模が揃う

[毎晩 05:00]
  係数再学習 + モデル選択 + 14日予測 + 統計拡張

[人が分析画面を開く / 質問する]
  コードが統計コンテキストを構築
  専門AI×3 → 反証 → 統合（→ 任意で評価ループ）
  現場は「仕入・人員・見せ方・KPI」まで落ちた文章を受け取る
```

**貯まるほど賢くなるもの**

- 予測 MAPE（進化ページで確認）
- 係数の信頼区間の狭さ
- 日報と実績の照合パターン
- （将来）合格回答コーパス
