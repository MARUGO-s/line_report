# 統一売上・出所・差異通知

2026-09-11。日別の同じ売上を二重計上せず、表示と定型報告の集計を共通化する仕様。

## 利用者向け

| 優先 | 入力 | 採用ルール |
|---|---|---|
| 1 | 売上分析での明示的な日別修正 | 修正した項目だけ優先。空欄で解除 |
| 2 | 同期済みジャーナル確定日計 | 手修正のない項目に採用 |
| 3 | レシート解析後の保存値 | ジャーナル・手修正のない項目に採用 |

税込売上・税額・客数・組数を店舗と営業日で照合する。同じ日に両方があっても足さない。明示した0は実績であり、未登録とは区別する。月次登録値は、その店舗・月に日別実績が1日もない場合だけ月合計として使う。日別値を推測して作らない。前年比の月次途中期間按分は従来どおり参考推計として扱う。

管理画面の「統一売上」欄で採用順を確認できる。ジャーナルとレシートが両方ある日は項目ごとに比較し、1円・1人・1組の差から通知する。差は「ジャーナル−レシート」。日ごとのプラスとマイナスが月合計で相殺されても、差異日を消さない。元データが欠けた項目は一致と断定しない。

日別修正はジャーナル再同期後も保持する。解除すると保存済みジャーナル、なければレシートに戻る。税込売上だけ直した場合、税率から税を推測せず元の税額を保持し「税額要確認」を表示する。売上分析の警告内の「税額を確認・修正」で確定税額を入力できる。税額不明時の税抜は未確定。税込より大きい税額になる手修正は拒否するため、必要なら税額を先に修正する。

レシート相当のExcel/CSV再取込でも、日別修正・ジャーナルは保持する。取込値との差は優先順位どおり表示し、必要なら日別修正を明示解除する。確認付きの「月全体削除」「月合計への置換」は別操作で、削除対象を確認して実行する。

## 対象と原本の区別

- 売上分析のKPI・日別・月別・曜日/天候集計、日々のLINE/M-talkレシート返信、定型中間/月末報告、DBからシートへの出力を共通日別集計へ接続。
- 電子ジャーナルとJournal Reportには現在の統一売上・差異を別枠表示。会計明細、商品内訳、保存時点のレポートは原本として残す。印刷/HTML出力には確認時点の統一欄も含める。
- フードコートの基準店舗日別実績と数値予測用ビューにも同じ採用値を反映。テナント日報画像自体は書き換えない。
- 配信済みLINE、保存済みAI文章、以前に出力したPDF/HTMLは自動で書き換えない。シートへの反映は従来の店舗別同期設定・実行時点に従う。
- 新規のJournal分析・チャット・POS AIも同じ採用値を使用。利用者は2026-09-11に公開GitHubへのコード/仕様書反映・本番配備と、既存OpenAI/Anthropic/Groqへの日別売上・税額・客数・組数の連携を明示承認した。提供元・モデルは変更しない。
- AIへの統一値は認証・店舗スコープ・レート制限確認後にサーバーで取得する。ブラウザから受け取るのは対象期間で、ブラウザの総額や「統一値」を信用しない。複数比較期間は別区間のまま保持し、中間の月を補わない。
- AIの商品・決済・時間帯・昼夜の内訳は原本参考値。修正総額へ按分しない。税額不明はnull、データなしはno_records、期間不明はperiod_not_providedとして0と区別。DB取得失敗時は503でAI呼出し前に停止する。未同期の原本を現在の統一値と称さない。

## 構造・整合性

```text
レシート原本 ───────────┐
ジャーナル → journal_values ├→ 共通日別採用 → 画面 / 定型報告 / シート / 新規AI
日別修正   → manual_values ┘             └→ 出所・差額・税額注意
```

正本関数は `_shared/sales_reconciliation.ts`。日時は登録日時でなく営業日。1,000行単位でページ取得し、DB取得失敗時はエラーを返す（レシートだけ/0円を正常結果として出さない）。

AI接続は `_shared/sales_reconciliation_ai.ts`。区分内の連続月だけ結合し、重複範囲は拒否。上限24区分/24非連続範囲/延べ3,660日、従来の入力100,000字制限を前後で検査する。`ai-analyze`は`unified_sales`を正本、`original_reference`を参考とする固定規約を適用。POS AIの新規保存履歴KPIも同じfactsを使う。予約のみ・商品検索のみの質問は不要な売上期間を追加送信しない。

`line_sales_manual_day` は互換用の採用値列と、独立した `journal_values` / `manual_values` を持つ。migration `20260911100000` は既存金額・更新日時を変えず、出所メタデータを補う。過去に上書きされ既に失われた値の復元は行わない。

追補migration `20260911110000` は予測用ビューのSQL集計も共通採用に揃える。税/税抜の一部欠損をSQLのSUMで無視して確定値にせずnullにする。元の保存値は変更しない。

書込みは service-role 限定 `write_daily_sales_source` RPC。店舗ごとのトランザクションロックと項目別パッチで、再同期とセル編集の取りこぼしを防ぐ。バッチ内不正値は全体をロールバック。同じ原本の再同期では `updated_at` も変えない。ストア一覧から正式キーを解決し、未登録店舗を拒否する。

`GET /pos-journals/sales-summary?store_key=…&from=YYYY-MM-DD&to=YYYY-MM-DD` は既存の管理認証・店舗スコープを適用。公開Pagesは業務テーブルを直接読まない。範囲上限3,660日。保存済み原本と現在の統一値は別フィールド。

## 検証と運用

- `npm run test:unified-sales`: 実PostgreSQL互換PGliteでmigration/RPC/権限/原子性、Denoでソース選択・画面/返信/定型報告/シートの一致・ページング、DOMの差異/XSS/税修正を検証。
- `npm run test:ci`、既存Journal/予約/レシート/フードコート等の回帰テストを実行する。
- `./scripts/local-line-report-pages.sh` でPC/スマホ幅を確認。UI検証は合成データのみ。
- mainデプロイはDB migration成功後にEdge Functionsを更新。既存の生データ、店舗の同期ON/OFFは変更しない。新規の通知cronや過去差異の一斉配信は追加しない。
- 差異が出たら日付と原本を照合し、必要な項目だけ修正。原本を消して一致させない。
- ロールバック時も新しいJSON列を削除しない。旧コードへの単純復帰は手修正保護を失うため、RPC/採用ルールを残した前方修正を優先する。旧バックフィルSQLは今回のRPCを使わない過去復旧用であり、再使用しない。
