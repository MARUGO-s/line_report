# フードコート日報システム 設計解説

MARUGO S（東京ドーム内フードホール「FOOD STADIUM TOKYO」）の現場スタッフが、毎日の施策・出来事を記録し、売上分析の精度向上に活かすための**日報システム**の設計と動作を解説する。

バージョン: `daily-report-v1`（2026-07-08 新設）  
関連ページ: [`foodcourt-report.html`](../foodcourt-report.html)  
関連 API: `supabase/functions/admin-api/index.ts` — `/foodcourt/daily-logs` (GET/PUT/DELETE)  
関連ドキュメント: [フードコートAI分析システム_設計解説.md](フードコートAI分析システム_設計解説.md)

---

## 1. 目的と設計思想

### 1-1. なぜ日報が必要か

フードコート AI 分析システムは「数値データだけ」を根拠にする。しかし現場には数値に現れない情報が存在する。

| 数値データが語れないこと | 日報が補う情報 |
|---|---|
| なぜその日だけ客数が増えたか | 試食配布・声かけ強化など **施策の記録** |
| 客数が増えたのに売上が伸びなかった理由 | 客層変化・回転率の感覚的評価（担当者視点） |
| 予測モデルが動員数を正確に扱えないケース | **動員数の直接入力** で予測モデルに反映 |
| 次の同イベント時に何を変えるべきか | 課題・申し送りの蓄積 |

### 1-2. 設計原則

- **担当者の記述は主観として扱う**: AI は日報記述と数値実績を必ず照合し、整合・不整合を明示する
- **動員数は単一の真実として扱う**: 日報で入力した動員数はそのまま分析ページの動員数バッジに反映し、予測モデルの来客計算に使える形で蓄積する
- **日報が無い日もデータは残る**: 日報の有無と売上データは独立。日報を書かなくても既存の数値分析は影響を受けない

## 2. データモデル

### 2-1. テーブル: `foodcourt_daily_logs`

```sql
CREATE TABLE foodcourt_daily_logs (
  id                  bigserial PRIMARY KEY,
  store_partition_key text NOT NULL,
  log_date            date NOT NULL,
  handler             text,             -- 担当者名
  actions             jsonb NOT NULL DEFAULT '[]',
  guest_impact        text,             -- 客数への影響（担当者評価）
  sales_impact        text,             -- 売上への影響（担当者評価）
  weather_note        text,             -- 天気・気候メモ
  event_note          text,             -- イベント・特記事項
  daily_attendance    integer,          -- 動員数（人）← 2026-07-08 追加
  issues              text,             -- 課題・問題点
  next_actions        text,             -- 翌日への申し送り
  memo                text,             -- 自由記述
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now(),
  UNIQUE(store_partition_key, log_date)
);
```

- `(store_partition_key, log_date)` にユニーク制約 → 同じ日を再保存すると **Upsert（上書き）**
- `actions` は `[{ cat: string, text: string }]` の JSON 配列

### 2-2. `actions` のカテゴリ

| `cat` 値 | 表示ラベル | 意味 |
|---|---|---|
| `promotion` | 🎯 販促・集客 | チラシ配布・試食・声かけ強化 |
| `menu` | 📋 メニュー提案 | 新メニュー導入・セット提案・陳列変更 |
| `service` | 👥 接客・サービス | 接客改善・クレーム対応・待ち時間削減 |
| `environment` | 🏪 環境・設備 | 店内レイアウト・設備修繕 |
| `staff` | 👤 スタッフ | 人員配置・研修 |
| `other` | 📝 その他 | 上記に当てはまらない事項 |

## 3. API エンドポイント

パス: `/foodcourt/daily-logs`  
認証: `x-admin-token` ヘッダー（storeScope 検証つき）

### 3-1. GET — 日報一覧取得

```
GET /foodcourt/daily-logs?store_key=marugoS&from=2026-07-01&to=2026-07-31&limit=90
```

| パラメータ | 必須 | 説明 |
|---|---|---|
| `store_key` | ✓ | 店舗キー（大文字小文字ゆらぎは ilike で吸収） |
| `from` | — | 開始日 YYYY-MM-DD |
| `to` | — | 終了日 YYYY-MM-DD |
| `limit` | — | 最大件数（上限 366） |

レスポンス: `{ logs: [...] }` — `daily_attendance` を含む全フィールド

### 3-2. PUT — 日報保存（Upsert）

```json
PUT /foodcourt/daily-logs
{
  "store_key": "marugoS",
  "log_date": "2026-07-08",
  "handler": "田中",
  "actions": [
    { "cat": "promotion", "text": "試食配布を14〜15時に実施" }
  ],
  "guest_impact": "試食後に購入した客が10組ほど確認できた",
  "sales_impact": "14〜16時の時間帯売上が平日比+20%程度の感覚",
  "weather_note": "晴れ・35℃",
  "event_note": "東京ドームで巨人戦（ナイター）",
  "daily_attendance": 42000,
  "issues": "試食消費速度が想定より早く14時半に在庫切れ",
  "next_actions": "次回は仕込み量を1.5倍にする"
}
```

レスポンス: `{ ok: true, log: { ...保存されたレコード } }`

### 3-3. DELETE — 日報削除

```
DELETE /foodcourt/daily-logs?store_key=marugoS&log_date=2026-07-08
```

レスポンス: `{ ok: true }`

## 5. 動員数の自動連携

### 5-1. 日報 → 分析ページへの反映フロー

```
日報ページで動員数を入力・保存
  ↓
foodcourt_daily_logs.daily_attendance に保存
  ↓
/foodcourt/reports 呼び出し時
  └── loadBaseDailyForReports() が foodcourt_daily_logs を JOIN
        ↓
        baseDaily[date].attendance として返却
  ↓
foodcourt.html のイベントリスト
  └── 日付ヘッダーに「📋 42,000人」の青バッジを表示
```

### 5-2. `loadBaseDailyForReports` の拡張

`admin-api/index.ts` の `loadBaseDailyForReports` 関数は、売上集計データ（`fetchReceiptDailyAggForRange`）に加えて `foodcourt_daily_logs` の `daily_attendance` を日付でマップして結合する。

```typescript
// 日報テーブルから動員数だけを取得してマージ
const { data: attRows } = await supabase
  .from("foodcourt_daily_logs")
  .select("log_date, daily_attendance")
  .ilike("store_partition_key", storeKey)
  .gte("log_date", lo)
  .lte("log_date", hi)
  .not("daily_attendance", "is", null)
// Map<date, attendance> を作り base 配列に注入
```

## 6. Q&A 分析への組み込み

### 6-1. 概要

`/foodcourt/ask` エンドポイントは、質問を受け取る際に直近60日分の `foodcourt_daily_logs` を取得し、`answerFoodCourtQuestion` に渡す。

```typescript
// admin-api /foodcourt/ask ハンドラ内
const { data: dailyLogsData } = await supabase
  .from("foodcourt_daily_logs")
  .select("log_date, handler, actions, guest_impact, sales_impact, ...")
  .ilike("store_partition_key", storeKey)
  .gte("log_date", logsFrom)   // 60日前
  .order("log_date", { ascending: false })
  .limit(60)

const answer = await answerFoodCourtQuestion(
  reports, baseName, question, groqApiKey,
  events, weather, supabase, storeKey, history, forecast, viewingDate,
  dailyLogs,  // ← 第12引数として追加
)
```

### 6-2. `buildDailyLogsContext()` によるテキスト化

`foodcourt_compare.ts` の `buildDailyLogsContext(logs)` が、各日の日報を以下のフォーマットに変換してAIに渡す。

```
▶ 2026-07-05（担当:田中）
  動員数: 42,000人
  天気: 晴れ・猛暑
  イベント: 東京ドームで巨人戦（ナイター）
  実施施策: [販促・集客] 試食配布を14〜15時に実施 ／ [接客・サービス] 声かけ強化
  客数への影響（担当者評価）: 試食後に購入した客が10組ほど確認できた
  売上への影響（担当者評価）: 14〜16時の時間帯売上が平日比+20%程度の感覚
  課題・問題点: 試食消費速度が想定より早く14時半に在庫切れ
  申し送り: 次回は仕込み量を1.5倍にする
```

### 6-3. AI への注入箇所

| AI エージェント | 注入方法 |
|---|---|
| **運営改善専門AI（Grok）** | `opsUser` のプロンプトに `# 現場日報・施策記録` ブロックを追加 |
| **統合AI（最終回答生成）** | `contextBlock` に `# 現場日報・施策記録` ブロックを追加 |
| **統合AIのシステム指示** | 指示(12)を追加：「施策を打った日/翌日の実績と照合し、担当者評価はデータで裏取りしてから採否判断せよ」 |

### 6-4. AI が行う照合ロジック（指示(12)）

```
施策を打った日/翌日の客数・売上が実際にどう変わったか
= 日報の記述 × 日次生データ の突き合わせ

担当者の評価は主観 → 必ずデータで裏取り
→ 整合する場合: 「担当者の評価と実績が一致。施策効果として有力な仮説」
→ 不整合の場合: 「担当者は客数増と評価したが実績は前日比-5%。
                  イベント規模(42,000人)に対して来店比率が下がっているため
                  施策の効果は限定的、またはその日の特異要因が優先の可能性」
```

## 8. AI 分析への接続（経路一覧）

| 経路 | 日報を使うか | 実装 |
|------|----------------|------|
| Q&A `POST /foodcourt/ask` | ✅ 直近60日 | **全専門AI＋統合**。原文＋`日報×実績 効果対照`（コード計算の前日比・同曜日比） |
| 日次サマリー `GET /foodcourt/daily-summary` | ✅ 対象日±14日 | 同上。7見出しの【この日の評価】で施策を引用し実績と照合 |
| 期間サマリー `GET /foodcourt/period-summary` | ✅ 期間内 | 同上 |
| 週次レポート `POST /foodcourt/weekly-report` | ✅ 週内 | `## 施策効果測定` で日報リンク。cron は Bearer `CRON_AUTH_TOKEN` |
| 分析画面動員バッジ | ✅ `daily_attendance` のみ | `loadBaseDailyForReports` |
| 来客予測モデル本体 | ❌ 直接は使わない | イベント「👥予想」→ `tokyo_dome_events.expected_attendance` が別系統 |

### 普段の売上AI分析が日報をどう使うか

1. **原文**: 「こんなことをしてみた」施策・担当者評価（`buildDailyLogsContext`）
2. **効果対照（コード計算）**: 施策日の客数・売上を前日比／同曜日平均比／全日平均比と比較（`buildDailyLogImpactContext`）
3. **プロンプト規則**: 施策を引用 → 数値でどれだけ繋がったか → 主観と実績の整合 → 仮説判定 → 次の一手（`foodCourtNippouPromptRules`）

取得ヘルパー: `admin-api` の `loadFoodCourtDailyLogs`（失敗を握りつぶさない）。  
キャッシュ版: `foodcourt-analysis-ai-v14-nippou-impact`（日報リンク強化で再生成）。
